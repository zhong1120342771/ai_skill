# case 影响评估案例 (case影响评估案例)

## 这个 skill 解决什么

一个线上缺陷影响了**部分**用户（某端 / 某页面 / 某品类），业务方要知道两件事：

1. **单量影响**：这个 bug 到底让我们少成了多少单？（是否影响 + 范畴 + 日均/累计支撑数据）
2. **用户体验影响**：多少用户实际撞上了这个坏体验？（是否影响 + 范畴 + 日均/累计支撑数据）

难点在于：不能直接拿受影响组「故障前 vs 故障中」对比，因为大盘转化本身随季节/活动波动，分不清是 bug 还是自然变化。本 skill 的标准解法是**双重差分（DiD）**——找一个不受影响、但同样经历大盘波动的对照组，用它扣掉大盘因素，剩下才是 bug 净影响。

## 触发前必须向用户确认的输入（不得自行臆测）

以下是**关键事实性输入**，用户没给就必须问，绝不能拿行业惯例/常识代替（见 CLAUDE.md 全局规则）：

| 输入 | 说明 | 例（本案例） |
|---|---|---|
| **故障窗口** | 精确起止时间，来自事故复盘而非推测 | 2026-05-27 00:00 ～ 2026-07-11 17:36 |
| **影响范围** | 端 / 页面 / 组件 / 品类的精确口径 | Android × G1003/G1004 × 手机外类目 × sectionId=2001&sortName=型号 |
| **对照组** | 哪些维度**确认不受影响**，可做对照 | 手机品类（同端干净对照）、iOS（跨端对照） |
| **候选影响上界** | 事故群/复盘确认的候选点击 PV/UV 上界 | 654,727 PV / 97,753 UV |
| **明细数据** | 通常是 页面×品类×端×日 的点击/成单表 | 用户提供的 Excel/CSV |

背景 case 文档（飞书 wiki/docx）通常含前 4 项，先读它。

## 分析方法（固定四步）

### 第 1 步：三期切分
把明细按故障窗口切成 `故障前 / 故障窗 / 修复后` 三期，按 `页面×品类×端` 聚合出人均单量（= 订单 / 点击用户）。

### 第 2 步：双重差分估单量损失
对每个受影响的 `页面×品类` 单元，用**多个反事实口径**交叉验证（结论以一致性判断，不靠单一口径）：

- **跨端 DiD**：`预期人均 = 对照端同类目人均 × (受影响端对照品类 / 对照端对照品类)`。即用不受影响的品类测出两端固有转化结构差，套到受影响品类上。
- **时间 DiD（对照组为趋势）**：`预期人均 = 受影响组故障前人均 × (对照组故障窗 / 对照组故障前)`。用对照组的涨跌幅推受影响组本应有的水平。
- **损失单量** = `(预期人均 − 实际人均) × 受影响组点击用户数`。负值 = 实际≥预期 = 测不出损失。

多口径若一致指向「无损失 / 极小损失」，则结论稳。样本过小（对照组订单量个位/十位数）的单元标注「不可靠、仅供参考」，不下定论。

### 第 3 步：用户体验受损量（带上界区间）
- 候选上界来自事故复盘的**去重设备 UV / 点击 PV**。
- 按受影响子集的**点击结构占比**剔除不受影响部分（如手机品类不受影响，按其点击占比剔除）：`受损上界 = 候选上界 × 受影响类目点击占比`。
- 明确这是**上界**：实际看到坏体验的人数还受触发条件（如地址是否命中、respCode=0 无日志）进一步收窄，通常**不可精确统计**，如实说明。

### 第 4 步：口径纪律（易错点，必须写进报告）
- **点击用户（日度累加）≠ 去重设备 UV**：转化率分母用日度累加点击（同设备多天重复计），体验规模用去重 UV。两者不同口径，报告里不能互换，必须点明。
- 「聚合桶」类目（如"手机外的其他类目"）混入未受影响类目会**稀释信号**，测不出损失既可能真无损失、也可能被稀释到噪声以下，需结合「该功能是否成单必经路径」定性判断。

## 报告结构（固定模板，不得随意增减章节）

**这是本 skill 的核心产物规范。** 每次输出严格按此五段式，模板文件见 `templates/report_template.xml`。

| 章节 | 内容要求 |
|---|---|
| **一、结论** | **结论先行，两张 callout 卡片**：①单量 ②用户体验。每条必须含【是否影响 + 影响范畴 + 支撑数据（日均 + 整体累计）】三要素。单量给损失区间，体验给剔除不受影响部分后的 UV/PV 上界及日均。 |
| **二、case 背景与口径** | 一段根因说明 + 一张口径表（影响端/页面、组件/品类、故障窗口、候选上界）。候选上界要标注「已剔除 XX 后」及原始口径来源。点明有哪些天然对照组。 |
| **三、单量影响** | 先用大白话讲清 DiD 计算逻辑（为什么不能自己跟自己比→对照组扣大盘→举一个反事实实例）。主力单元用**多口径反事实表**（预期/实际/损失）。区分点击用户与去重 UV 口径。小样本单元标注不可靠。收尾解释「为何大候选量没换来成单损失」。 |
| **四、用户体验影响** | 讲清体验受损的性质（功能不可用摩擦、持续多久、是否被监控发现）。给剔除不受影响部分后的受损规模（累计 UV/PV + 日均），标注这是上界、实际不可精确统计的原因。 |
| **五、方法与局限** | DiD 控制组说明、数据口径差异、聚合桶稀释、小样本不可靠——如实列局限，不夸大结论。 |

## 执行流程

1. **读输入**：读 case 背景文档（`lark-doc`）+ 用户明细数据。缺关键输入（故障窗口/对照组/候选上界）→ 先问用户。
2. **跑分析**：改写 `scripts/case_impact_analysis.py`（三期切分 + 多口径 DiD + 体验折算），产出各口径结果。
3. **出图**：改写 `scripts/case_impact_viz.py`，生成 3 张标准图到 `visualizations/<case名>/`。中文字体 `Arial Unicode MS`。
4. **写报告**：套 `templates/report_template.xml`，填五段式。**去 AI 味**（humanizer），红线：只改措辞不改数字/口径/结论。
5. **建文档 + 插图**：`docs +create --api-version v2` 建文档 → 逐图 `media-insert` 到锚点句旁。
6. **P2P 推送**：`im +messages-send --user-id <open_id> --text "..."`，正文给两条硬结论 + 文档链接。默认推钟梦婷（见 memory），不发群。

## 口径与踩坑速查

- **DiD 结论看一致性**：多口径同向才下结论；单口径孤证不采信。
- **负损失 = 无损失**：预期减实际为负，说明实际转化≥预期，是好事不是 bug。
- **候选上界 ≠ 实际失败量**：反复强调，避免把点击候选全算成故障。
- **点击用户 vs 去重 UV** 不可互换（转化率分母 vs 体验规模）。
- **lark-cli**：发消息 `im +messages-send`（P2P 用 `--user-id` 不用 `--chat-id`）；插图 `--file` 只吃 cwd 相对路径，绝对路径静默丢图。

## 历史锚点（首个案例）

- **案例**：[2026-07-11][Android]首页型号筛选无数据（scene=31 与同城专区冲突）
- **背景文档**：https://zhuanspirit.feishu.cn/wiki/GEx9w2uVWivYgNkeslAc5WIxnRh
- **评估产出**：https://zhuanspirit.feishu.cn/docx/EkUhdJBE9oh1Ebx3gQscT7Zzn18
- **结论**：单量基本无影响（三口径 DiD 测不出损失，最坏 ≤约40单/45.7天）；体验有明显影响（剔除手机后累计约 50,453 UV / 337,921 PV，日均约 1,104 UV / 7,393 PV）。

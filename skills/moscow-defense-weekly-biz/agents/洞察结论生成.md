# 莫斯科周报-洞察结论生成

## 基础与定位

本 agent 是流水线的**最后一棒**，产物直接给到业务方。整合 5 种能力：

- **报告撰写**：将复杂的数据洞察转化为清晰、可操作、格式专业的飞书文档
- **XML 渲染**：把 analysis_result 翻译成符合飞书 docs v2 API 的 XML（table/callout/heading 等 block）
- **图表生成**：通过内嵌子 agent `agents/数据可视化.md` 渲染 6 张 PNG 图，并按 manifest 插入文档
- **飞书文档创建**：通过 lark-cli `docs +create --api-version v2` 创建并落 doc_token
- **P2P 推送**：通过 lark-cli `im +messages-send --user-id ... --as user` 推送到钟梦婷个人会话

### 四阶段方法论

**阶段一：理解分析**
- 审查上游 `analysis_result.json` / `analysis_summary.md` / `quality_check.json`
- 识别关键发现的重要性（机会点 > 全景描述 > 维度拆解 > 分业务补充）
- 确定目标受众（业务方）的语言水平（UV-CTR、CVR 缩写可直接用）

**阶段二：报告规划**
- 按 `references/weekly-report-requirements.md` 的固定结构组织
- 每节规划核心数字 + 关键表格 + 异动话术
- quality_check 的 warn/soft 项找到对应章节，准备 ⚠ 标记

**阶段三：内容创建**
- 撰写每个维度的话术（直接用 `dimensions[i].analysis_text`，必要时补充关联段）
- 生成 XML（callout 概览 + 12 列横向漏斗 + 7 列维度表 + 6 列构成表）
- 标 ⚠ 数据待复核到 soft/warn 涉及的条目

**阶段四：质量保证**
- 每个数字可追溯到 analysis_result 具体字段
- 不出现"综上所述""总而言之"等 AI 腔
- 飞书 XML block 嵌套合法（`<table><thead><tr><th>` / `<tbody><tr><td>`）

## 关键约束

### CVR / KPI 兜底

**01_kpi.csv 已废弃**（Spark NPE 持续，known-issue）。KPI 达成率表的数据来自：

- **月均值**：`06_monthly_trend.csv` 的 6 月 `tag_01=整体, wd=整体` 行
- **周均值**：`02_funnel.csv` 的整体行
- **目标值**：硬编码业务目标（CVR=1.26% / DAU=450 万 / 单量=56674）

```python
# 06_monthly_trend.csv 列：tag_01, wd, 月份, 天数, dau_日均, 单量, 商详uv, ..., dau-净支付pv转化率
# 取 6 月行：row['月份'] == '2026-06' and row['tag_01'] == '整体' and row['wd'] == '整体'
```

### 维度数据表格式（7 列）

| 维度项 | 净支付转化率 | 商详渗透率 | 商详转化率 | 曝光渗透率 | 商详到达率 | 下单率 | 支付率 |

单元格格式：`绝对值（+X%）`，不写"环比"二字，无法计算显示 `-`。

### 维度构成表（每个维度紧跟原 7 列表之后）

**端 / 用户来源 — 6 列**：
| 端/用户来源 | DAU（周均） | DAU占比 | DAU周环比 | 单量（周均） | 单量占比 | 单量周环比 |
- DAU占比 = 维度项 DAU / 整体 DAU × 100%，加和 ≈ 100%
- 单量占比 = 维度项 净支付PV / 整体 净支付PV × 100%，加和 ≈ 100%

**场景 — 6 列（无 DAU，曝光UV 用渗透率口径）**：
| 场景 | 曝光UV（周均） | 曝光UV渗透率 | 曝光UV周环比 | 单量（周均） | 单量占比 | 单量周环比 |
- 曝光UV渗透率 = 场景曝光UV / 整体 DAU × 100%，**加和 > 100% 是正确的**（典型 150-200%，一个用户可在多场景被曝光）
- 直接取 `03_dim_dss.csv` 的「曝光渗透率-周均值」列

### 苹果系列漏斗表（h4「6、苹果系列」，数据源 08_apple_funnel.csv）

直接读 `08_apple_funnel.csv`，每行一个维度（`苹果整体` 置顶 + 手机/平板/笔记本/智能手表/耳机），列顺序：

| 维度 | 曝光UV(周日均) | 曝光UV周环比 | 商详UV | 商详UV周环比 | 下单UV | 下单UV周环比 | 支付PV | 支付PV周环比 | 曝光渗透率 | 商详渗透率 | 商详到达率 | 商详转化率 | 下单率 | 支付率 |

- CSV 已算好全部列（含各环比），直接映射，不要在 Python 端重算率
- **口径标注（必写在节首文字里）**：本表走 raw 漏斗明细表(曝光/商详/下单/支付)重算，`支付PV` 为漏斗归因订单数、非大盘净支付ETL口径，两者可能差几个百分点，仅供苹果内部结构参考；渗透率分母为大盘DAU（非苹果专属）
- **苹果整体 ≠ 5 品类加和**：整体是跨品类 distinct token 去重（一个用户看了 iPhone 又看 iPad 只算一次），比加和小 40%+ 属正常，不要"修正"
- 曝光渗透率可能 >100%（周日均节点UV/单日DAU 口径差），与大盘一致，不改
- 分品类话术：抓「逆势涨的品类」+「跌幅最大的品类」各一句，其余合并；驱动环节看商详转化率/下单率/支付率哪个环比拖累最大

### 占比加和合理性检查

| 列 | 期望加和 | 不通过应对 |
|----|---------|------------|
| 端/用户来源 DAU 占比 | 95-105% | 重新核对分母是否用了整体 DAU |
| 端/用户来源 单量占比 | 95-105% | 分母是整体净支付PV |
| 场景 曝光UV 渗透率 | 150-220% | 这是渗透率口径，>100% 正确，不要改成份额 |
| 场景 单量占比 | 95-105% | 分母是整体净支付PV |

### 话术规则

- 每个结论带具体数字（如 `+6.51%`、`CVR=1.129%`）
- quality_check 有 warn / soft 时，对应条目末尾标 `⚠ 数据待复核`
- **不用"综上所述""总而言之""不仅...而且"等 AI 腔**
- 趋势相同的维度项**合并描述**，不要逐项罗列

### 在文档中插入图片

文档创建完拿到 `DOC_TOKEN` 后，遍历 manifest，逐张 `lark-cli docs +media-insert`：

```bash
# 注意：飞书 docs +media-insert 默认在文档末尾插入图片
# 要插到特定段落下方，需先用 docs +fetch 拿到目标段落的 block_id，再用 --after-block-id 定位
# 简化策略：本周报段落顺序固定，按 manifest 中 report_section 字段在已知 h2 锚点后插入即可
python3 -c "
import json, subprocess
WEEK_END = '${week_end}'
manifest = json.load(open(f'/Users/zhongmengting/Downloads/msk_weekly_raw/{WEEK_END}/charts/charts_manifest.json'))
DOC_TOKEN = '${DOC_TOKEN}'
for c in manifest['charts']:
    if c['render_status'] != 'ok':
        continue
    img = f'/Users/zhongmengting/Downloads/msk_weekly_raw/{WEEK_END}/charts/{c[\"file\"]}'
    subprocess.run(['lark-cli', 'docs', '+media-insert',
                    '--doc', DOC_TOKEN,
                    '--file', img,
                    '--as', 'user'], check=False)
    print(f'inserted: {c[\"file\"]} -> {c[\"report_section\"]}')
"
```

如果需要把图精准插在特定段落下，先 `docs +fetch --detail with-ids` 拿到该 h2 / callout 的 `block_id`，再 `docs +media-insert --after-block-id <id>`。当前默认行为是按 manifest 顺序追加到文档尾，因为本周报的 6 个嵌图位天然就在报告末段（KPI/漏斗/搜推/商详商列/电子馆/新客新媒，前 5 维度表无图）。

### 图表失败容错

## 飞书文档创建

### XML 渲染

用 Python 生成 XML（参考 `../scripts/gen_report.py` 模板）：

- 概览段：`<callout emoji="📊" background-color="light-yellow" border-color="yellow">`
- 标题：`<h1>` / `<h2>` / `<h3>`
- 表格：`<table><thead><tr><th background-color="light-gray"><p>表头</p></th></tr></thead><tbody><tr><td><p>单元格</p></td></tr></tbody></table>`
- 强调：`<b>`、`<i>`、`<u>`
- **不要**用 `<tableRow>` / `<tableCell>`（旧错误格式，飞书 v2 不支持）

落到 `~/Downloads/msk_weekly_raw/${week_end}/report.xml` 作为审计产物。

### 创建文档

```bash
DOC_TOKEN=$(lark-cli docs +create --api-version v2 \
  --content "$(cat ~/Downloads/msk_weekly_raw/${week_end}/report.xml)" \
  --title "莫斯科保卫战周报 · ${week_start}–${week_end}" \
  --as user --format json | jq -r '.data.document.document_id')
DOC_URL="https://zhuanspirit.feishu.cn/docx/${DOC_TOKEN}"
```

若 XML 过大（>50KB），改用 `docs +create` 建空文档 + `docs +update --command append` 分块写入。

## 失败处理

- **飞书文档创建失败** → 停止，不发 IM，**不回退发本地路径**
- **文档创建成功但 IM 推送失败** → 仅重推 IM，复用 `doc_url`，**不要重建文档**
- **不得把推送目标改为群聊**，除非编排器显式传入 `group_chat_id`

## 不要做的事

- **不要重新计算指标**——数值已在 analysis_result.json 算好；只有 KPI 达成率允许用 06_monthly 兜底
- **不要无视 quality_check warn**——必须带出 ⚠ 标记
- **不要在报告正文粘贴 SQL 代码**
- **不要把 P2P 改成群聊**
- **不要用 `<tableRow>`/`<tableCell>` 这类旧 XML**——必须 `<tr>/<th>/<td>`
- **不要硬编码 doc_token 给推送脚本**——从创建结果读

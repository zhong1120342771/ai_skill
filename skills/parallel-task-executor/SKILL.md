# Parallel Task Executor（执行型任务拆解编排器）

把「一个包含多个修改点的任务」拆成多个**互不冲突的执行单元**，分派子 agent 并行执行，
回收后统一验证再集成。核心难点不是合并结论，而是**避免并行写冲突**和**处理依赖顺序**。

## 何时使用 / 何时不用

**用**：任务里存在多个可独立落地的改动点，且彼此不争抢同一文件/状态。信号词：
- 「这几处都改一下」「批量重构 X」「顺便把 A/B/C 都做了」
- 「多个模块同时加日志」「把这批文件的 import 都换掉」
- 一次列出 ≥3 个 TODO，且大部分互不依赖
- 手动唤醒词：「拆子agent」「拆子agnet」「拆成子agent」「并行改」→ 用户明确点名，直接进 Phase 1

**不用**（退回顺序执行或别的 skill）：
- 单一改动点，或改动点 <3（并行开销大于收益）。
- 改动点有强顺序依赖（B 必须等 A 的产物）→ 用主流程顺序做，或见 Phase 1 的分波。
- **纯只读分析**（审查/批量分析、不落地写改动）→ 用 `parallel-subagent-dispatcher`。
- 多个改动点会写**同一个文件**且无法拆开 → 该文件必须串行，不能并行分派。

## 与 parallel-subagent-dispatcher 的分工

| | parallel-subagent-dispatcher | 本 skill |
|---|---|---|
| 子 agent 干什么 | 只读、返回 findings JSON | 实际改文件/写代码/跑命令 |
| 核心风险 | 结论去重与合并 | **写冲突** + 依赖顺序 + 集成后回归 |
| 回收后 | merge/dedup/rank 出报告 | 收集 diff → 统一构建/测试 → 集成 |

两者的「context 隔离省主上下文」原理一致，见那个 skill 的 Context Isolation 段，这里不重复。

## Phase 1：拆解任务

### 1.1 列出所有改动点
把请求拆成一张改动点清单，每条含：**要改什么、落在哪些文件、预期产物、验收标准**。
一句「顺便也改下 X」也算一条，不要漏。

### 1.2 判定独立性与冲突（最关键一步）
两个改动点能并行的**充分条件**：写入的文件集合不相交，且不共享可变状态（同一份
config、同一张迁移、同一个全局单例都算共享）。

- **文件集合相交** → 冲突，必须串行（放同一个子 agent，或分到不同波次）。
- **A 的产物是 B 的输入**（B 依赖 A）→ 有依赖，分波。
- **都只读同一文件、各写各的** → 独立，可并行。

据此把清单标成三类：`独立可并行` / `写冲突需串行` / `有依赖需分波`。

### 1.3 分组与分波（DAG → waves）
- 把有依赖的改动点排成 DAG，按拓扑分层：同层无依赖的进同一波并行，跨层顺序执行。
- 同波并发**上限 5–8** 个子 agent，超了拆多波（如 15 个独立点 → 3 波 5/5/5）。
- 写同一文件的改动点合并进**同一个**子 agent（由它内部串行改），绝不拆到两个并行 agent。

产出一张**分派清单（manifest）**：每条 = {单元 id, 负责的文件集, 任务描述, 验收标准, 所在波次, 依赖的单元 id}。这张清单用 TaskCreate 落成任务，边做边更新状态。

## Phase 2：分派子 agent

### 2.1 写自包含的 brief
每个子 agent 看不到本次对话历史，brief 必须能让它冷启动独立完成。每条 brief 含：
1. **目标**：这个单元要达成什么、为什么。
2. **文件边界**：只允许改哪些文件（明确列出），**禁止碰边界外的文件**——这是防冲突的硬约束。
3. **具体改法**：能给到行号/函数名/接口签名就给，别让子 agent 自己猜整体意图。
4. **验收标准**：改完要能通过什么（编译/某条测试/某个命令）。
5. **回传格式**：见 `references/output-contract.md`，要求返回结构化结果而非长篇叙述。
6. 若本波有依赖上游 → 把上游产物（路径/接口）塞进 brief，别让它去翻别的单元。

用 Agent 工具分派。同一波的多个 Agent 调用放在**同一条消息里并行发出**（无依赖才并行；跨波顺序发）。

### 2.2 监控与重试
- 等本波全部返回再进下一波。
- 单个失败（报错/超时/没产出）：带简化 brief 重试一次；仍失败 → 标记该单元 `failed`，
  记原因，**继续其余单元**，最后在集成阶段汇报，别让一个单元卡死整批。

---

## Phase 3：回收、验证、集成

### 3.1 收集
汇总每个子 agent 的结构化回传（改了哪些文件、做了什么、自检结果、遗留项）。
过滤掉 `failed` 单元，单独留档。

### 3.2 统一验证（不可跳过）
子 agent 各自的自检不等于整体没坏。主流程必须做**集成级验证**：
- 跑项目的构建/类型检查（找 package.json / pom.xml / Makefile 等确定命令）。
- 跑相关测试；若改动交叉影响，跑全量或受影响范围。
- **重点查交界处**：并行改的单元虽文件不相交，但可能改了同一接口的两端，集成后才暴露。

验证失败 → 定位是哪个单元引入的，回 Phase 2 修那个单元，别在主流程手糊补丁。

### 3.3 集成与交付
全部通过后，给主流程一份收敛报告（骨架见 `assets/integration-report.md`）：
- 完成的单元清单（改了什么、动了哪些文件）。
- 失败/跳过的单元及原因。
- 集成验证结果（构建/测试通过情况）。
- 遗留 TODO 或需人工确认项。

清理并行过程中产生的临时文件。

---

## Phase 4：质量闸口

交付前逐项确认：
- [ ] 每个成功单元都在其声明的文件边界内改动，没越界踩别的单元。
- [ ] 没有两个并行单元写了同一文件（若有 → Phase 1 分组错了，回退重排）。
- [ ] 集成级构建/测试已实跑并通过（不是只信子 agent 自检）。
- [ ] 失败单元有记录、有原因，未被静默吞掉。
- [ ] 报告自包含，主流程读它就能判断整批是否可交付。

## ❌/✅ 速查

| ❌ Don't | ✅ Do |
|---|---|
| 不查冲突就把 N 个点全并行 | Phase 1.2 先判文件集合是否相交 |
| 两个并行 agent 改同一文件 | 合进同一 agent 串行改，或分波 |
| 依赖任务硬塞进同一波并行 | 排 DAG 分波，跨波顺序发 |
| 一次并发 20+ 子 agent | 上限 5–8，超了分波 |
| 子 agent brief 不给文件边界 | 明确列出可改文件 + 禁止越界 |
| 只信子 agent 自检就交付 | 主流程跑集成级构建/测试 |
| 一个单元失败就整批中止 | 标记 failed、继续其余、最后汇报 |
| 集成报错就手糊补丁 | 定位到具体单元，回去修那个单元 |

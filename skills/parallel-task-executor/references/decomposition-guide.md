# 拆解与冲突判定指南

主 SKILL.md 的 Phase 1 讲了原则，这里给更细的判定方法和例子。

## 一、怎么切「执行单元」

单元 = 一个能被单个子 agent 独立完成、且落在一组明确文件上的改动。切分维度：

| 任务形态 | 单元 = | 例子 |
|---|---|---|
| 多个文件同改一件事 | 一个文件（或一组无关文件） | 给 10 个 handler 各加日志 → 每个 handler 一个单元 |
| 多个独立 feature | 一个 feature | 加登录 / 加导出 / 加分页，各一单元 |
| 一个大重构分区域 | 一个不相交的代码区域 | 前端组件目录 / 后端 service 层，各一单元 |
| 多个独立 bug | 一个 bug | issue #12 / #15 / #18，各一单元 |

## 二、冲突判定：能不能并行

对任意两个单元 A、B，问三个问题：

1. **写入文件是否相交？** A 会写 `x.py`，B 也会写 `x.py` → 冲突。
   - 只读同一文件、各写各的输出 → 不冲突。
2. **是否共享可变状态？** 同一份 config、同一个 DB migration 序号、同一个全局注册表、
   同一个 lockfile → 视为冲突（并行写会互相覆盖或产生竞态）。
3. **是否有产物依赖？** B 的输入是 A 的输出（A 先生成接口、B 再调用）→ 有依赖，不能同波。

三个都为「否」→ 可并行。任一为「是」→ 串行合并或分波。

### 灰色地带的处理
- **同目录不同文件**：默认可并行，但若目录有 `index.ts`/`__init__.py` 这类聚合导出文件、
  两个单元都要往里加一行 → 那一行的改动抽出来，交给集成阶段主流程统一加，或放同一单元。
- **共享类型/接口定义**：若多个单元都要改同一个 interface → 先单独一波把 interface 定稳，
  再并行改各调用方。
- **lockfile / 依赖清单**（package.json、Cargo.toml）：多个单元都要加依赖 → 依赖变更集中到
  一个前置单元，其余单元只写代码不碰 lockfile。

## 三、分波（DAG → waves）例子

任务：加一个新 API endpoint（需先加 model → 再加 service → 再加 route + 前端调用）。
- 有依赖链：model → service → route，前端调用依赖 route 的接口形状。
- 排波：
  - 波 1：改 model（1 单元）
  - 波 2：改 service（依赖 model）
  - 波 3：改 route + 前端调用（两者互不写同一文件，可并行；都依赖 service/route 接口）

任务：把 15 个组件的旧 Button 换成新 Button，彼此无依赖、各在各自文件。
- 全独立 → 按并发上限分波：波 1/2/3 各 5 个，纯为控并发，不是因为依赖。

## 四、常见误判

- 「文件不同就一定能并行」——错，若它们都改同一个共享 config 或都要动 migration 序号，仍冲突。
- 「都在改测试，互不影响」——若共用同一个 fixtures 文件或 snapshot，仍可能冲突。
- 「依赖很弱，应该没事」——只要 B 读了 A 将要改的接口，就按有依赖分波，别赌。

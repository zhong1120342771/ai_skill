# 附属物触发规则

附属物用于提升 PRD 的可理解性和可交付性。触发后必须生成最低可用版本，或明确 N/A 并说明原因。不得写“后续补充”。

## 常见触发

| 需求特征 | 附属物 |
|---|---|
| 页面变化 | 低保真原型 |
| 多步骤、多角色、分支、异步流程 | 流程图 |
| 生命周期或状态变化 | 状态机 |
| 订单、支付、退款、履约、工单、审核、审批等状态流转 | 状态机或主流程图 |
| 数据、表单、配置变化 | 字段表 |
| 接口或前后端交互变化 | 接口说明 |
| 指标、漏斗、实验、行为分析 | 埋点或指标口径 |
| 多角色、可见范围、操作差异 | 权限表 |
| 存量用户、历史数据、核心流程影响 | 灰度 / 回滚方案 |
| PRD 草案或研发交付版 | 测试场景 |

## 页面变化完成标准

必须说明：

- 入口位置；
- 可见性 / 鉴权；
- 动态展示逻辑；
- 填写与校验逻辑；
- 组件形态；
- 默认态 / 空态 / 加载态 / 失败态 / 无权限态。

## 原型最低可用标准

当触发原型时，必须表达：

- 页面结构；
- 入口位置；
- 关键状态；
- 交互后目标画面。

流程图、普通表格或文字说明不能替代原型。

默认输出低保真原型。只有用户明确要求，或交互复杂到文字 / 低保真无法表达时，才生成 HTML 原型。

## 字段变化完成标准

必须说明：

- 生效页面；
- 可见性；
- 前置状态限制；
- 必填 / 选填；
- 枚举值来源；
- 互斥 / 联动关系；
- 历史数据处理。

## 逻辑分支完成标准

涉及逻辑判断时，必须覆盖主要分支，并给出对应场景示例。

不得只写“根据实际情况处理”。

## 外部依赖 / AI / 支付 / 物流 / 风控完成标准

必须说明：

- 超时处理；
- 失败处理；
- 降级策略；
- 兜底方案；
- 人工介入方式，如适用。

## 流程改造完成标准

必须说明：

- 在途数据如何处理；
- 历史数据如何展示；
- 老用户是否受影响；
- 灰度与回滚策略。

## 状态机 / 主流程图强触发

当需求涉及订单、支付、退款、履约、工单、审核、审批等状态流转类对象时，必须生成至少一张状态机图或主流程图。

状态机或主流程图至少覆盖：

- 主路径；
- 异常路径；
- 补偿 / 回滚路径；
- 重复提交或重复操作拦截；
- 关键状态进入和退出条件。

如果未生成状态机或主流程图，不能判定发布候选测试通过。

## 数据观测完成标准

关键功能上线必须说明：

- 业务指标定义；
- 转化 / 流失观测口径；
- 关键动作埋点。

## 测试场景裁剪规则

PRD 草案或研发交付版默认需要测试场景，但测试深度应按需求复杂度裁剪。

轻量需求可以将测试场景简化为验收点，不强制输出完整测试矩阵。

轻量需求至少需要说明：

- 正常验收方式；
- 影响范围；
- 不影响项；
- N/A 原因。

涉及核心链路、存量流程、权限、接口、数据、状态流转、支付、退款、风控、AI、外部依赖的需求，不得用轻量验收点替代完整测试场景。

## 附属物归属

- 条件触发的附属物必须挂在对应核心改动对象下。
- 全局流程图、全局状态机、全局埋点表、全局权限表、灰度 / 回滚方案，也必须在相关核心改动对象中引用。
- 不得把必要原型、流程图、状态机、埋点表、字段表、接口说明、权限表统一堆到附录，导致核心改动对象无法独立阅读。

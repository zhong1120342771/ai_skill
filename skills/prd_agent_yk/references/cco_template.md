# 核心改动对象模板 v0.7.4 CCO candidate

核心改动对象是 PRD 第 4 章的主要组织单位。不要把页面、功能、规则、异常、埋点、验收拆成彼此割裂的大章节；它们应围绕同一个改动对象内聚呈现。

CCO 固定字段是对象内部的小标题 / 章节锚点，不是要求用一张“固定字段 / 内容”的两列表承载全部信息。

## 1. CCO 定义

CCO 是一个完整产品改动单元，而不是页面 / 规则 / 数据 / 验收的分类容器。

一个候选对象成为 CCO，通常应同时满足：

| 判断项 | 说明 |
|---|---|
| 独立产品意图 | 能说明本次为什么要改它，以及它服务哪个业务目标 |
| 明确变化对象 | 有明确被新增、改造、替换、删除或兼容的对象 |
| 可描述行为变化 | 能写出当前逻辑、目标行为、触发条件、主流程、异常与边界 |
| 可闭环交付 | 能形成验收标准、测试建议或下游协作关注 |

页面、规则、数据、验收、原型、埋点通常是 CCO 的内部表达维度，不默认成为独立 CCO。

## 2. CCO 识别顺序

生成第 4 章前，先按以下顺序识别 CCO：

1. 识别本次用户或业务能感知到的核心变化。
2. 判断变化承载在哪个页面、流程、资源位、业务对象、状态或能力上。
3. 以“完整产品改动单元”命名 CCO。
4. 将页面、规则、异常、数据需求、埋点目标、验收和测试挂到该 CCO 内部。
5. 只有另一个候选对象具备独立产品意图或独立交付边界时，才拆成第二个 CCO。

## 3. 拆分与合并原则

### 3.1 建议拆成多个 CCO 的情况

| 拆分信号 | 说明 |
|---|---|
| 独立产品意图 | 两个对象服务不同用户目标或业务目标 |
| 独立用户路径 / 行为场景 | 用户会经历不同主路径，而不是同一模块内的规则分支 |
| 独立上线 / 灰度 / 回滚 | 可以单独上线、单独关闭、单独回滚 |
| 独立验收标准 | 验收对象、通过标准和测试场景显著不同 |
| 独立系统或责任边界 | 涉及不同系统、团队或责任边界，且需要独立评审 |
| 可独立复用 | 该能力可被多个页面或业务复用，不只是当前对象的内部规则 |

### 3.2 应合并到同一个 CCO 的情况

| 合并信号 | 说明 |
|---|---|
| 高度共享触发条件 | 同一条件触发同一产品变化 |
| 高度共享主流程 | 只是同一流程里的页面、规则、数据和验收视角 |
| 高度共享异常回退 | 异常和兜底逻辑几乎相同 |
| 高度共享验收标准 | 验收的是同一个产品行为是否成立 |
| 只是内部维度 | 候选对象只是页面展示、业务规则、数据观测、验收测试、原型或埋点 |

合并不是为了减少字数，而是为了让同一个产品改动在一个 CCO 内闭环呈现。

## 4. 反模式

不要按以下方式机械拆 CCO：

| 反模式 | 为什么不合适 |
|---|---|
| 页面一个 CCO，规则一个 CCO，数据一个 CCO | 容易把同一个产品改动拆散，导致触发条件、回退和验收重复 |
| 原型一个 CCO，埋点一个 CCO，测试一个 CCO | 原型、埋点、测试通常是交付物或验收维度，不是产品改动对象 |
| 只因为内容很多就拆 CCO | 内容多可以用小标题、表格、流程图组织；拆分应基于产品意图和交付边界 |
| 只因为有下游关注就拆 CCO | 下游关注进入第 6 章或 CCO 内部字段，不默认成为 CCO |

示例：

| 需求 | 推荐 CCO | 不推荐拆法 |
|---|---|---|
| 搜索结果页首屏新增快惠选商品承接模块 | 搜索结果页首屏快惠选商品承接模块 | 页面模块 / 商品承接规则 / 数据观测实验分别拆成 3 个 CCO |
| 商卡图片区新增瑕疵图入口并打开图片浮层 | 商卡图片区瑕疵图入口；如果浮层可独立复用，可另拆图片浮层查看能力 | 入口文案 / 点击规则 / 埋点分别拆 CCO |
| 订单退款状态流转改造 | 退款状态流转；必要时按退款发起、审核、支付回退等独立状态机拆分 | 每个字段或每个异常码拆 CCO |

## 模板

### 核心改动对象 {编号}：{名称}

每个核心改动对象必须使用同一组固定字段，不得自创字段替代。如果某项不适用，写 N/A 并说明原因。如果信息不足且影响产品策略，不要在正文里写 `[假设]` / `[阻塞]`，而是进入第 5 章 `R-x`。

硬字段以 `contracts/cco_contract.yaml` 为准，并由 `scripts/prd_linter.py` 校验。生成完整 PRD 时，每个核心改动对象都必须包含以下字段名称。

### 表达形态规则

除“对象信息”可以使用小表外，以下字段应优先展开为独立小标题、段落、规则表、流程图、原型图、数据需求表、埋点目标表、验收表或测试场景表：

- 当前逻辑
- 目标行为
- 触发条件与前置条件
- 主流程
- 业务规则
- 异常与边界
- 页面 / 原型
- 数据需求 / 系统能力 / 权限 / 埋点目标
- 验收标准
- 测试建议

当某一项内容较多时，优先拆成小标题、规则矩阵、状态表、流程图或验收表，不要把页面、规则、异常、数据、埋点和验收混写在同一个表格单元格里。

#### 0. 对象信息

| 字段 | 内容 |
|---|---|
| 对象类型 | 页面 / 流程 / 规则 / 状态 / 数据 / 权限 / 配置 / AI / 文案 / 通知 / 业务对象 |
| 改动性质 | 新增 / 改造 / 删除 / 替换 / 兼容 |
| 优先级 | P0 / P1 / P2 |
| 涉及端 | C 端 / B 端 / 后台 / 数据 / 运营 |
| 是否涉及存量 | 是 / 否 |

#### 1. 当前逻辑

说明当前线上或存量逻辑是什么。历史 PRD 只能作为历史参考，除非业务地图、研发验证或用户明确确认当前仍有效。

不要写内部检索过程，只写与当前对象有关的产品事实和历史约束。

#### 2. 目标行为

说明改完后这个对象应该发生什么。重点写用户可观察行为、系统业务结果和产品希望达成的状态。

复杂策略或存量改造需求可使用行为 Delta 思路辅助表达：说明本对象相对当前逻辑新增、修改或移除了哪些用户可观察行为。不要把内部 Delta 表作为 PRD 一级章节。

#### 3. 触发条件与前置条件

说明什么时候触发、需要满足什么条件。若触发条件仍未拍板，进入第 5 章 `R-x`，正文只保留已确认结论。

#### 4. 主流程

说明正常链路。多步骤、多角色、异步或分支流程需要流程图。

主流程应能覆盖关键 Given / When / Then 场景：在什么前提下，用户或系统发生什么动作，系统产生什么明确结果。

#### 5. 业务规则

说明命中规则、优先级、互斥、频控、兜底、策略判断等。

普通固定规则与策略型规则要区分：

| 类型 | 特征 | 处理 |
|---|---|---|
| 普通规则 | 固定条件 + 固定结果 | 写清触发条件、系统处理和验收即可 |
| 策略型规则 | 存在选择、排序、分配、命中、优先级、强弱判断、资源倾斜或规则计算 | 必须补充策略型最低颗粒度 |
| 核心策略 | 影响主体方案、验收判断、实验结论或业务目标 | 必须给推荐方案并请求拍板；用户不确认则进入第 5 章 |

策略型需求至少覆盖：

- 策略目标
- 命中对象
- 输入条件
- 判断规则
- 优先级
- 兜底逻辑
- 生效范围
- 验收口径
- 观测指标

涉及资源位、流量、内容、权益分配时，资源映射至少说明：

| 字段 | 说明 |
|---|---|
| 策略结果 | 例如“消费电子强兴趣” |
| 承载位置 | 具体资源位 / 页面位置 |
| 展示优先级 | 必须说明相对谁优先，不得只写“高优先级” |
| 替换 / 混排 / 插入 | 说明与原内容关系 |
| 频控 | 不适用写 N/A |
| 冲突处理 | 与运营固定位、商业位、推荐位冲突时如何处理 |
| 兜底 | 资源不可用或内容不足时如何回退 |

#### 6. 异常与边界

说明关键异常、失败、无权限、空态、老数据、兼容、不可用等场景。

关键异常指会影响核心路径、业务规则、验收、数据观测、上线安全或下游协作的异常。普通技术容灾不必强行写入 PRD 正文，除非影响用户或业务。

#### 7. 页面 / 原型

如涉及页面变化，给出最低可用低保真原型或页面结构示意。流程图、普通表格或文字说明不能替代原型。

#### 8. 数据需求 / 系统能力 / 权限 / 埋点目标

本节写产品需要什么数据、系统能力、权限差异和埋点目标；不要臆造具体接口名、VO / Model、schema、数据库字段、入参、出参或异常码。

推荐结构：

| 类型 | 产品需要什么 | 用于判断什么 / 支撑什么 | 下游关注 |
|---|---|---|---|
| 数据需求 |  |  | 研发 / 数据在第 6 章定义具体字段或口径 |
| 系统能力 |  |  | 研发在第 6 章评审实现方式 |
| 权限 |  |  | 权限或角色差异评审 |
| 埋点目标 |  |  | 数据在第 6 章定义具体事件和字段 |

可写：

- 需要识别哪些商品集合；
- 需要判断用户是否命中某个策略；
- 需要记录曝光、点击、转化、回退等行为；
- 需要支持实验归因或看板分析。

不建议写：

- 具体接口字段名；
- VO / Model；
- 数据库字段；
- 入参 / 出参；
- 异常码；
- 具体埋点字段名。

#### 9. 验收标准

验收标准应可执行、可判断、可被测试展开。

验收标准应对应行为场景，而不是只复述功能描述。每个关键新增 / 修改 / 移除行为都应至少有一个可验证的验收点。

不要在验收标准中写“待字段确认后验收”“待接口确认后验收”。若字段或接口定义会影响验收口径，把它写到第 6 章；若它会改变产品策略，把它同步写到第 5 章。

#### 10. 测试建议

说明主流程、关键异常、兼容、权限、数据、回退等测试场景。

测试建议写产品和业务需要覆盖的场景，不替测试同学写完整测试用例。

## 软拆分建议

当单个核心改动对象满足以下情况时，建议拆分：

- 涉及超过 3 个主要页面；
- 涉及超过 5 条 P0 业务规则；
- 涉及超过 1 个独立状态机；
- 涉及多个角色且不同角色流程差异明显；
- 涉及多个系统边界；
- 研发无法独立估时。

这些只是拆分信号，不是自动拆分条件。拆分前仍需确认候选对象是否具备独立产品意图、独立用户路径、独立上线 / 验收 / 复用价值或独立系统边界。

如果只是页面、规则、数据、验收内容较多，优先在同一个 CCO 内用小标题、规则矩阵、流程图、数据需求表和验收表组织。

拆分是软建议，不是额外硬闸门。

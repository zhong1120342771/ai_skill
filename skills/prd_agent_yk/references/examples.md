# 样例与发布候选测试

本文件用于验证 Skill 是否能稳定产出合格 PRD，不是主执行规则。

## v0.7.4 candidate 示例使用总则

以下旧样例中若出现 `[假设]`、`[阻塞]`、`6-Rx`、策略拍板审计摘要进入 PRD 正文、或“下游可启动检查”等表达，均视为 v0.7.3 及以前的历史样例，不作为 v0.7.4 正文输出规范。

v0.7.4 生成 PRD 时统一遵守：

- 第 1-4 章正文不出现 `[假设]`、`[阻塞]`、`6-Rx`、策略拍板审计摘要、linter / contract / retrieval_evidence 等内部状态。
- 影响产品策略的未确认项进入第 5 章 `R-x`。
- 研发、设计、测试、数据需要定义、评审、回归或关注的事项进入第 6 章“下游关注”。
- 产品不定义具体接口字段、VO / Model、schema、数据库字段、入参、出参或埋点字段名。
- 第 2 章指标按“核心结果指标 / 北极星指标、主要过程指标、动作指标、护栏指标”组织。

## CCO 表达形态对比样例

本节只展示表达形态，不提供具体业务答案。完整 PRD 生成时不要照抄样例内容。

### 坏例：把 CCO 写成字段命中表

```markdown
| 固定字段 | 内容 |
|---|---|
| 当前逻辑 | 已有资源位、入口、商品池和落地页；本次新增聚合模块；商品不足回退；埋点待确认；验收见后文。 |
| 目标行为 | 展示新模块。 |
| 业务规则 | 命中展示，不命中回退。 |
| 页面 / 原型 | 见文字说明。 |
| 验收标准 | 正常展示即可。 |
```

问题：

- 当前逻辑、本次改动、异常、埋点、验收混写。
- 读者无法分辨规则层级。
- 研发、设计、测试难以拆任务。

### 好例：把固定字段作为对象内部章节锚点展开

```markdown
### 核心改动对象 1：存量资源位上的商品聚合模块

#### 0. 对象信息

| 字段 | 内容 |
|---|---|
| 对象类型 | 页面模块 |
| 改动性质 | 改造 |

#### 1. 当前逻辑

说明已有资源位、入口、商品池或落地页的当前关系；未确认的线上事实标记为历史参考、用户输入或待研发兜底。

#### 2. 目标行为

说明本次新增或改造后，用户看到什么，系统如何处理，和存量能力是什么关系。

#### 4. 主流程

1. 用户进入目标页面。
2. 系统判断是否满足展示条件。
3. 满足条件时展示新模块。
4. 用户点击模块内对象进入对应承接页。
5. 不满足条件时回退存量逻辑。

#### 5. 业务规则

| 场景 | 新模块 | 存量资源位 | 普通列表 | 说明 |
|---|---|---|---|---|
| 条件满足 | 展示 | 不展示 / 被替换 | 按规则去重 | 主策略 |
| 条件不满足 | 不展示 | 展示 | 原逻辑 | 回退 |
| 数据异常 | 不展示 | 展示 | 原逻辑 | 兜底 |

#### 7. 页面 / 原型

放低保真结构示意，展示新模块与存量资源位、普通列表的相对位置。

#### 9. 验收标准

| 编号 | 验收点 | 前置条件 | 通过标准 |
|---|---|---|---|
| A1 | 条件满足时展示新模块 | 满足展示条件 | 页面出现新模块，存量资源位按规则隐藏或替换 |
| A2 | 条件不满足时回退 | 不满足展示条件 | 不展示新模块，保留存量逻辑 |
```

## v0.7.1 策略型需求增强样例

### 正例：新媒体用户承接

输入摘要：

```text
新媒体用户来自站外渠道。根据站内外行为判断对消费电子、奢侈品、潮玩等业务的兴趣强弱，再根据兴趣强弱做 App 首页资源位倾斜，目标提升 DAU-净支付PV 转化。
```

预期：

- 判定为 `complex` 策略型需求；
- 首次响应先输出方案成立摘要，不直接进入研发交付版；
- 兴趣强弱必须覆盖输入信号、source/status、权重或优先级、阈值、时间衰减、冲突处理；
- 资源位映射必须覆盖具体 surface、display_priority、replace_or_mix、frequency_cap、conflict_handling、fallback；
- 核心策略未拍板时进入 `[阻塞]`，文档状态不得为研发交付版。
- 必须出现 `strategy_signoff`，并输出用户可见的策略拍板卡；用户可见动作只使用“接受推荐 / 修改策略 / 暂不拍板”，不要用 A/B/C 作为动作标签。
- 用户只回复 ok / 好 / 继续 / 生成吧 等模糊确认时，必须追问“接受推荐 / 修改策略 / 暂不拍板”。
- 模糊确认追问必须使用中文动作：`你这里是选择接受推荐、修改策略，还是暂不拍板？`
- 用户选择“接受推荐”只代表策略拍板完成，不自动解除数据源、资源位、指标口径、合规或研发可行性阻塞。
- 用户选择“修改策略”时，必须输出修改后策略摘要；修改仍模糊时继续请求确认。
- 用户选择“暂不拍板”时，生成含 `[阻塞]` 的不可排期草案，并在第 5 节保留策略拍板审计摘要。
- structure_plan 必须保留 `signoff_record`，证明策略拍板卡、用户原始回复、解释后的选择和是否需要追问。

策略拍板卡最低结构：

| 策略点 | 推荐方案 | 可选方案 | 推荐理由 | 不确认影响 | 是否阻塞 |
|---|---|---|---|---|---|

回归路径：

| 路径 | 用户行为 | 预期 |
|---|---|---|
| A | 用户先回复 `ok` | 智能体追问“接受推荐 / 修改策略 / 暂不拍板”，不能直接生成 PRD |
| B | 用户选择“暂不拍板” | 生成含 `[阻塞]` 的不可排期草案，`strategy_signoff.status = skipped_with_blocker` |
| C | 用户选择“接受推荐” | 策略拍板项 accepted，但非策略阻塞仍保留，文档状态按剩余阻塞判断 |
| D | 用户选择“修改策略” | 输出修改后策略摘要，模糊修改不得直接标 modified |

### 负例：资源位文案替换

输入：

```text
把首页资源位标题“新人专享”改成“新人福利”。
```

预期：

- 不触发完整 `strategy_plan`；
- 输出轻量需求说明与验收点；
- 不生成 CCO、流程图、原型、完整埋点附属物。

### 负例：固定入口展示

输入：

```text
会员用户在会员中心固定展示“会员权益”入口。
```

预期：

- 固定条件 + 固定结果，不触发完整策略增强；
- 若生成完整 PRD，可使用极简 `strategy_assessment.triggered=false` 并说明原因。

### 负例：已有明确规则照搬

输入：

```text
按现有后台配置规则，在活动页展示已配置的资源位内容。
```

预期：

- 不重新生成 `strategy_plan`；
- 不要求用户重新拍板策略；
- 必须写明 `rule_source`；无可靠来源时，不影响交付标 `[假设]`，影响研发或验收标 `[阻塞]`。

### 隐性策略正例

输入：

```text
希望新用户进入 App 后，优先看到最可能促成首单的入口，不同用户可以看到不同内容。
```

预期：

- 即使没有推荐、分发、评分等显性词，也应通过决策性质触发；
- 命中 selection、prioritization、personalized_display、goal_optimization；
- 初始可判定为 `standard`；
- 若补充多入口、多信号、多资源、多目标或实验判断，升级为 `complex`。

## v0.7.2 修订模式样例

修订模式测试用于验证已有 PRD 的持续修订、局部 patch、评论分类、覆盖授权、非连续文档处理和策略参数修订。不要把修订模式测试当成首次生成 PRD 测试。

### 正例：新媒体 PRD 修改兴趣评分权重

输入摘要：

```text
基于这份新媒体用户承接 PRD，把兴趣评分权重再调整一下。站内支付和加购应该更重要，站外看过视频只能作为辅助信号。
```

预期：

- 进入修订模式；
- `revision_output_mode` 至少为 `change_plan` 或 `revised_sections`；
- 默认用户可见输出应先展示“修改点 + 推荐策略 + 需要确认”，不要默认铺开全部审计表；
- 正常协作中，即使用户说“修改项分类”，也优先输出轻量变更摘要，不默认展示编号、分类、影响位置、修改类型、是否需查存量、是否影响下游、是否阻塞等内部审计字段；
- 轻量变更摘要推荐表头为“修改点 / 推荐策略 / 需要你确认”；如果需要说明位置，用一句话说明“会改对应策略段落 / 验收段落”，不要把“影响位置”作为默认列；
- 完整修改项分类表和完整参数表用于内部判断、正式评审或测试导出；
- 内部修改项分类表必须包含完整字段：修改意见、来源、影响位置、修改类型、处理动作、是否需确认、是否需查存量、是否影响文档状态、是否影响下游启动；
- 内部策略参数表必须覆盖输入信号、权重、阈值、时间衰减、冲突处理、资源映射、频控、兜底、验收口径；不涉及的参数项写 N/A 和原因，不得省略；
- 内部策略参数表的状态列必须使用 confirmed / recommended_draft / needs_data_calibration / blocker_for_delivery，不得用 `[假设]` / `[阻塞]` 替代；
- 若影响核心策略、验收口径、数据口径或下游启动，复用复杂策略拍板（Complex Strategy Sign-off）；
- 如果用户直接给出具体权重、阈值、上限或业务口径，不必强制输出“接受推荐 / 修改策略 / 暂不拍板”卡，但必须输出策略参数确认摘要（Strategy Parameter Confirmation Summary）；
- 用户确认策略后，不得只显示为 `[假设]`；应说明“产品已确认；待数据校准 / 待研发确认”等交付状态；
- 用户确认后同步更新 strategy_plan、对应 CCO、验收标准、第 5 节阻塞/假设台账、第 6 节下游可启动检查；
- 如果修改项标记影响下游启动，必须输出第 6 节替换片段或 N/A 原因；
- 如果目标文档不是实际完整 PRD，而是 Skill 方案、规则文档、测试样例或发布说明，第 6 节下游可启动检查可以 N/A，但必须说明原因；
- 如果修改项影响附属物，必须输出附属物修订或 N/A 原因；
- 实际输出修订内容后，必须输出修订摘要；
- 不只修改参数表。

### 正例：新媒体 PRD 修改资源位分配策略

输入摘要：

```text
资源位分配策略改一下：不要所有资源位都倾斜同一个业务，弹窗和 Feed 第一位可以强倾斜，中通栏目保留运营配置优先。
```

预期：

- 进入修订模式；
- 识别这是策略参数与资源映射修订；
- 更新资源位映射表中的 surface、display_priority、replace_or_mix、frequency_cap、conflict_handling、fallback；
- 判断是否需要重新拍板；
- 同步更新相关 CCO、验收、埋点或指标口径、下游可启动检查；
- 不默认全篇重写。

### 正例：商卡瑕疵图 PRD 按评论调整入口文案和原型位置

输入摘要：

```text
按这几条评论改一下：入口文案改成“实拍xx 细节xx”；原型不要放附录，放到商卡入口 CCO 里；验收里补充无瑕疵图时不展示入口。
```

预期：

- 评论先分类，不把所有评论直接当已拍板结论；
- 文案修改可直接 patch；
- 原型位置修订应同步到对应 CCO，不堆到附录；
- 异常验收补到对应 CCO 的验收标准；
- 输出修订摘要；
- 不自动写回正式文档。

### 正例：已有 PRD + 多条评审意见

输入摘要：

```text
根据评审意见修订这份 PRD：
研发：字段来源不支持，建议不做；
运营：必须上线；
测试：验收标准缺失。
```

预期：

- 进入修订模式；
- 识别评论来源；
- 输出修改项分类表；
- 识别研发与运营意见冲突；
- 不直接合并成一个结论；
- 输出冲突处理计划并请求用户拍板；
- 测试意见可转成验收补齐项。

### 正例：多个 PRD 同时出现在上下文

输入摘要：

```text
这两个文档都在上下文里。帮我把之前那个 PRD 改一下。
```

预期：

- 不能默认选择最近生成的 PRD；
- 必须询问目标文档；
- 不进入修改正文；
- 不沿用不确定的旧上下文。

### 正例：旧 PRD 升级到 v0.7.1 结构

输入摘要：

```text
这是以前写的一份 PRD，帮我升级成现在 PRD Skill 的结构。
```

预期：

- 进入修订模式；
- 识别这是结构升级，不是业务重新生成；
- 保留原有有效内容；
- 迁移到固定 6 节骨架；
- 将需求详情按 CCO 重组；
- 缺失信息用 `[假设]` / `[阻塞]` / N/A，不编造事实；
- 输出结构升级摘要。

### 负例：覆盖写回授权

输入：

```text
确认
```

上下文：

```text
用户此前只确认了修订内容，但没有表达写回 / 保存 / 覆盖意图。
```

预期：

- 智能体可以生成修订稿或待写回 diff；
- 不得写回正式文档；
- 不得声称已覆盖；
- 必须把“确认”先理解为确认修订内容；
- 必须要求用户明确表达写回 / 保存 / 覆盖意图；
- 普通确认不等于写回授权。

### 正例：明确写回当前原文件

输入：

```text
写回原文件
```

上下文：

```text
当前只有一个目标 PRD，智能体刚输出并获得用户确认的局部修订片段，范围就是“上述局部修订”。
```

预期：

- 视为明确写回意图；
- 不要求用户再复述“确认将上述局部修订写回《文档名》”；
- 允许写回当前原文件的已确认局部修订；
- 写回前或写回后简要说明“只写回刚确认的局部修订，不重写全文”。

### 负例：写回目标或范围不清

输入：

```text
写回吧
```

上下文：

```text
上下文里有多个候选 PRD，或智能体刚给过多个修订方案但用户尚未确认采用哪一个。
```

预期：

- 识别为写回意图；
- 不直接写回；
- 只追问缺失项，例如“写回哪份文档 / 哪个修订方案 / 哪个范围”；
- 不要求用户重复已经明确的信息。

### 短语矩阵：内容确认与写回授权

| 用户回复 | 预期解释 | 处理 |
|---|---|---|
| 接受推荐 | 策略 / 内容确认 | 输出局部修订片段，不写回。 |
| 按你推荐 | 策略 / 内容确认 | 输出局部修订片段，不写回。 |
| 确认 | 内容确认 | 不写回；如需写回，提示需要写回意图。 |
| ok / 可以 / 继续 | 模糊确认或继续意图 | 不写回；按上下文继续生成或追问。 |
| 写回吧 | 写回意图 | 若目标和当前 patch 范围明确，执行写回；否则只追问缺失项。 |
| 写回原文件 | 写回当前目标文档意图 | 若当前目标唯一且 patch 范围明确，执行写回。 |
| 保存到原文档 | 写回当前目标文档意图 | 若当前目标唯一且 patch 范围明确，执行写回。 |

### 负例：轻量修订不是自动覆盖

输入：

```text
把标题里的“用户权益”改成“新客权益”，可以。
```

预期：

- 可以输出替换片段；
- 至少输出一行修改摘要；
- 如果涉及正式文档写回，仍需明确授权；
- 不因为是轻量修改就自动覆盖。

### 负例：评论冲突

输入：

```text
研发评论：字段来源不支持，建议不做；
运营评论：必须上线；
测试评论：验收标准缺失。
```

预期：

- 智能体不能直接合并成一个结论；
- 必须输出冲突处理计划；
- 要求用户拍板；
- 评论 / 批注不自动等于已拍板结论。

## v0.7 正式候选覆盖样例

v0.7 正式候选测试已覆盖：

1. 商卡增加瑕疵图入口；
2. 新媒体用户承接；
3. 轻量文案 / 单点展示；
4. 纯新建 + 多端需求。

其中轻量文案 / 单点展示样例应使用 `scripts/prd_linter.py --light` 检查，不套完整 6 节 PRD，也不生成 CCO。

## 高风险真实生成测试

规则推演通过后，仍需至少选择 2 个历史高风险样例做真实生成测试。

优先选择：

- 新媒体用户承接
- 商卡增加瑕疵图入口

用于验证：

- 策略细化
- 存量判断
- 核心改动对象内聚
- 配套交付物位置
- PRD 结构稳定性

## 真实生成测试通过标准

真实生成测试通过标准应同时检查：

- 是否保留 6 节 PRD 骨架；
- 是否围绕核心改动对象组织详情；
- 附属物是否放在对应核心改动对象内或被对应对象引用；
- 文档状态是否正确；
- 是否正确使用 `[假设]` / `[阻塞]` / N/A；
- 是否存在编造存量事实；
- 是否错误地把历史 PRD 当成当前业务逻辑事实；
- 结构计划中 blockers 列表和 CCO blocker_refs 是否统一使用 6-Rx；
- PRD linter 是否带结构计划运行，使流程图 / 主流程图 / 状态机检查依赖 `required_artifacts`，而不是正文关键词猜测；
- 适用项是否覆盖；
- 不适用项是否 N/A 并说明原因；
- 策略型需求是否给出产品级策略或推荐方案；
- 原型是否满足最低可用标准；
- 下游可启动检查是否真实，而不是机械填“是”。

## 行为 Delta 检查样例

行为 Delta 用于内部判断本次需求改变了哪些用户可观察行为，不作为 PRD 一级章节。

不推荐：

```yaml
behavior_delta_check:
  triggered: true
  scenarios:
    - given: 有候选内容
      when: 用户进入页面
      then: 展示新模块
      status: closed
      handling: no_action
```

问题：只覆盖主场景，遗漏候选不足、无候选、接口失败、与存量资源冲突、下游列表关系等边界场景。

推荐：

```yaml
behavior_delta_check:
  triggered: true
  draft_after_retrieval:
    changed_behaviors:
      - 新增首屏集中承接行为
      - 修改存量资源位展示关系
      - 修改下游列表去重关系
    scenarios:
      - given: 用户进入命中条件页面，且候选内容充足
        when: 页面加载
        then: 展示新承接模块并替代存量表达
        status: closed
        handling: no_action
      - given: 用户进入命中条件页面，但候选内容不足
        when: 页面加载
        then: 是否展示、展示几项、是否回退存量表达尚未明确
        status: needs_signoff
        handling: include_in_signoff
    unresolved_scenarios:
      - 候选不足时的展示数量与回退规则需要用户拍板
  closure_before_prd:
    checked: true
    unresolved_scenarios:
      - 候选不足时的展示数量与回退规则已进入策略拍板或风险台账
    handling_summary:
      - 已拍板的写入第 3 / 4 节；未拍板的写入第 5 节 `[假设]` 或 `[阻塞]`
```

用户可见层不展示完整 Delta，只压缩成少量策略点：

```text
我建议按“命中条件 + 展示数量 + 回退规则 + 与存量资源关系”作为一个策略包拍板。
这里会影响研发和验收，你确认按推荐走，还是调整其中某项？
```

## 需求成立检查点样例

需求成立检查点用于确认背景、用户、目标、范围是否成立。它发生在策略拍板之前，不等同于执行计划，也不能和策略拍板混成同一轮确认。

不推荐：

```text
我会先查询存量，再生成 PRD。

当前需求理解：
- 背景：存量链路需要二期增强
- 用户：命中存量链路的用户
- 目标：提升首屏承接效率
- 范围：改造存量入口和承接模块

推荐策略：
- 方案 A：新增集中承接模块
- 方案 B：复用现有入口

请选择接受推荐、修改策略或暂不拍板。
```

问题：执行计划、需求成立摘要、策略拍板被压在同一轮里。用户确认时容易只确认“可以继续”，但 Agent 误以为同时完成了需求成立和策略拍板。

推荐：

```text
我会先做存量轻扫，再判断这 4 件事是否成立：背景、用户、目标、范围。轻扫前的理解只作为工作假设，不作为需求成立确认。
```

如果是轻量输出、局部修订，且不进入完整 PRD / 复杂策略拍板，可以展示型通过；结构计划应写：

```yaml
demand_establishment:
  status: display_passed
  confirmation_mode: display
  user_action: not_required
```

如果要继续生成完整 PRD 或进入复杂策略拍板，即使四件事主要来自用户明确输入，也应先让用户轻确认。结构计划应写：

```yaml
demand_establishment:
  status: accepted
  confirmation_mode: confirm
  user_action: accepted
```

不要写成：

```yaml
demand_establishment:
  status: accepted
  confirmation_mode: display
  user_action: accepted
```

如果历史 PRD 补出了范围细节，不要把它混进展示型摘要：

```yaml
# 不推荐
demand_establishment:
  status: display_passed
  confirmation_mode: display
  summary:
    users: 搜索某历史类目或具体机型的买家
  inferred_fields: []
```

如果只是轻量输出或局部修订，推荐做法是将历史范围细节外置：

```yaml
demand_establishment:
  status: display_passed
  confirmation_mode: display
  summary:
    users: 搜索结果页浏览商品并决策的买家
  inferred_fields:
    - 历史 PRD 显示曾覆盖某历史类目或具体机型，本期是否沿用需进入待确认项
```

如果要继续进入完整 PRD 或策略拍板，推荐做法是先切到确认型需求成立摘要：

```yaml
demand_establishment:
  status: confirmation_required
  confirmation_mode: confirm
  user_action: pending
  blocks_strategy_signoff: true
```

轻扫后，如果四件事需要用户确认：

```text
我先确认需求是否成立，只看 4 件事：

| 项目 | 当前理解 |
|---|---|
| 背景 | 存量链路需要二期增强，目标不是重做基础能力 |
| 用户 | 命中该存量链路的目标用户 |
| 目标 | 提升关键场景的承接效率 |
| 范围 | 改造指定前台触点，不重做底层商品定义 |

请先确认：以上需求成立吗？
- 接受
- 修改
- 先按假设推进
```

用户确认后，下一轮再输出策略拍板：

```text
需求成立已确认。下面只拍板方案策略：

| 策略点 | 推荐做法 | 为什么 |
|---|---|---|
| 承接方式 | 以一个核心承接对象组织入口、规则和兜底 | 避免把同一行为拆成多个重复改动对象 |

你选择接受推荐、修改策略，还是暂不拍板？
```

## 交互式发布候选测试要求

发布候选测试必须至少包含一次交互式测试，不能只验证最终 PRD 产物。

测试记录必须保留：

1. 用户第一轮输入；
2. 智能体的需求成立摘要；
3. 智能体的方案成立摘要；
4. 智能体识别出的 P0 / `[阻塞]` / 重大方案取舍 / 高风险存量冲突；
5. 智能体的追问、推荐方案请求拍板或降级说明；
6. 用户回答；
7. 最终 PRD 产物；
8. 一审和二审结论。

如果测试只验证最终 PRD 产物，不验证交互过程，只能标记为“产物生成测试”，不能标记为“完整发布候选测试”。

# 用户交互与交付节奏参考

## 用户可见内容

- 需求理解
- 关键问题
- 推荐方案与理由
- 已确认的存量逻辑与缺口
- 产品待确认项 / 产品风险
- 文档状态
- 需要拍板事项
- PRD 交付包
- 下游关注

## 默认隐藏机制

- Gate
- P0/P1/P2
- L0-L3
- C0-C3
- 附属物 if-then 触发规则
- 自检清单

不要播报内部流程日志。用户不需要知道智能体正在执行哪个内部 Gate，只需要知道需求理解、推荐方案、风险、需要拍板什么，以及最终交付物。

## 三段式表达与硬停顿

1. 需求成立摘要
2. 方案成立摘要
3. PRD 交付包

三段式是表达节奏，不是越过检查点的理由。简单或低风险需求可以压缩表达；一旦触发硬停顿，当前回复只能处理当前动作，后续段落必须等用户完成该动作后的下一轮继续。

硬停顿包括：

- 确认型需求成立检查点；
- 复杂策略拍板；
- 正式写回 / 覆盖 / 通知下游 / 进入排期 / 升级研发交付版。

## 需求成立检查点

需求成立检查点只检查四件事：背景、用户、目标、范围。它的用户可见形态是“需求成立摘要”；它不是策略拍板卡，也不是 PRD 正文第 2 章。

执行计划确认是复杂任务中的可选交互，不是所有任务的必经步骤。如果需要先列执行计划，执行计划只能确认用户是否同意 Agent 按某个路径推进；不能确认背景、用户、目标、范围、方案、策略、参数或写回授权。执行计划可以包含一句初步理解，但不要用四件事确认模板；如必须写初步理解，应标注“轻扫后会重新判断，当前不作为需求成立确认”。

需求成立检查点必须输出以下结果之一：

| 结果 | 触发条件 | 用户动作 | 下一步 |
|---|---|---|---|
| 展示型通过 | 轻量输出、局部修订、或不进入完整 PRD / 复杂策略拍板的低风险任务 | 不需要单独确认 | 可进入轻量输出或局部修订；不得直接进入完整 PRD 策略拍板 |
| 确认型待确认 | 四件事中有智能体推断、多个可能方向，且影响方案、验收或下游协作 | 接受 / 修改 / 先按假设推进 | 当前轮只输出需求成立摘要，不输出策略拍板卡 |
| 不成立 / 需补充 | 四件事缺失到无法推进 | 补充信息 | 追问最小必要问题 |
| 先按假设推进 | 用户明确选择先不确认 | 先按假设推进 | 可继续，但不得升级研发交付版 |

完整 PRD 进入策略拍板前，必须向用户展示需求成立摘要，并获得“接受 / 修改 / 先按假设推进”之一。即使四件事来自用户明确输入，也不能只用 `display_passed` 无感越过需求成立确认。展示型通过写入结构计划时，使用 `status: display_passed`、`confirmation_mode: display`、`user_action: not_required`。不要把后续“接受推荐”写回为需求成立 `accepted`。

确认型需求成立摘要模板：

```markdown
我先确认需求成立四件事：

- 背景：{为什么要做，当前问题是什么}
- 用户：{主要影响谁；如果是推断，明确写“我推断为...”}
- 目标：{希望什么变好；如未拆四层指标，说明原因}
- 范围：{本期做什么、不做什么}

其中 {用户 / 目标 / 范围} 包含我的推断。这里的“接受”只代表接受背景、用户、目标、范围理解，不代表接受推荐方案或策略参数。请确认：
- 接受
- 修改
- 先按假设推进
```

不要把以下内容放进需求成立摘要：

- 方案取舍；
- 资源位、数量门槛、排序、兜底等策略细节；
- 存量查询过程和证据表；
- 研发 / 数据 / 测试实现细节；
- 内部 Gate、linter、contract、sign-off 机制。

如果用户选择“接受”，只能进入行为变化草稿、推荐方案或策略拍板，不得直接生成 PRD 正文；如果用户选择“修改”，先输出修改后需求成立摘要，再继续后续流程；如果用户选择“先按假设推进”，相关推断不能写成已确认结论，PRD 状态不得直接升级为研发交付版，必须进入第 5 章待确认项或 structure_plan 的 assumptions / open_items。

如果用户、目标或范围主要来自历史 PRD、空业务地图节点或 Agent 推断，且会影响方案、验收或发布范围，不要用展示型通过。要么先让用户确认需求成立四件事，要么在正文用“本期建议 / 暂按”表达，并将对应事项放入第 5 章待确认项。完整 PRD 只要后续存在策略拍板或 PRD 正文生成，就优先使用确认型需求成立摘要。

`demand_establishment.summary` 不负责承载历史 PRD 推断出的适用范围。摘要优先写用户本轮明确表达，例如“搜索结果页浏览商品并决策的买家”；历史 PRD 补出的范围，例如某类目、具体机型、实验页面、历史适用渠道，应写入 `inferred_fields`、策略适用边界或第 5 章待确认项。

## 轻量需求降级

当用户只提出轻量文案、轻量展示或单点说明调整，且未明确要求 PRD、评审、研发、排期或上线时，优先输出轻量需求说明与验收点，不强制生成完整 PRD 草案。

如果用户明确要求“写 PRD”“评审”“研发”“排期”“上线”，仍按文档状态规则输出 PRD 草案或研发交付版；但轻量需求的测试场景和附属物可以按复杂度裁剪。

## 必须确认的场景

- P0 缺口
- 重大方案取舍
- 高风险存量冲突
- 正式写回
- 通知下游
- 进入排期
- 升级研发交付版

当展示条件、命中条件或生效条件同时影响产品方案成立、页面展示规则和下游实现判断时，必须显式处理。处理方式只能选择以下之一：

1. 给出推荐方案，并请求用户拍板；
2. 进入第 5 章产品待确认项，说明需要确认的问题；
3. 若只属于下游实现或数据定义事项，进入第 6 章下游关注。

不得将这类条件隐式带过，也不得只写在实现细节中。

## 策略型需求拍板

当需求涉及选择、排序、分配、命中、优先级、强弱判断、资源倾斜、规则计算、个性化展示或目标优化时，先判断它是否为策略型需求。

输出策略拍板卡前，必须先完成需求成立检查点：

- 展示型通过：仅适用于轻量输出或局部修订，不得直接进入完整 PRD / 复杂策略拍板；
- 确认型已接受 / 修改后接受：可进入策略拍板；
- 先按假设推进：可进入策略拍板或草案，但相关不确定项必须进入第 5 章待确认项或 structure_plan；
- 确认型待确认、blocked、pending：不得输出策略拍板卡。

下游影响不能单独触发完整策略计划。页面展示、验收或数据口径受影响时，只有同时存在显性策略类型或决策性质动作，才进入策略型需求处理。

策略等级：

| 等级 | 用户体感 | 处理 |
|---|---|---|
| 轻量策略 | 不增加完整 PRD 流程 | 给推荐规则、拍板项或验收点，并说明 `lightweight_reason` |
| 标准策略 | 需要确认关键策略 | 给 `strategy_plan` 摘要；如影响核心方案、研发或验收，则请求拍板 |
| 复杂策略 | 必须先确认方案成立 | 输出方案成立摘要；核心策略未拍板时进入第 5 章待确认项，不得伪装成已确认方案 |

方案成立摘要的用户可见形态：

| 策略点 | 推荐方案 | 为什么推荐 | 不确认的影响 |
|---|---|---|---|
| {策略点} | {推荐规则、权重、阈值、资源映射或冲突处理} | {如何支撑目标} | {是否进入第 5 章待确认项} |

复杂策略未拍板前，不得表现为“方案已成立”。可以输出 `PRD 草案（含待确认项，不可研发排期）`，但必须明确核心策略未确认，不能让下游误以为可以直接排期。

如果用户只说“继续”，但仍存在会影响主体方案、验收判断、实验结论或业务目标的核心策略拍板项，不能默认视为确认；需要简短追问或生成含待确认项的草案。

## 复杂策略拍板（Complex Strategy Sign-off）

当策略等级为 complex 且存在需要用户确认的核心策略项时，智能体在生成完整 PRD 草案前必须输出策略方案拍板摘要。

拍板摘要应来自行为 Delta 草稿中的未闭合关键场景，而不是机械枚举所有潜在变量。先内部检查本次新增 / 修改 / 移除的用户可观察行为；如果某个主场景、边界场景或异常场景无法写出明确结果，且会影响方案成立、研发实现、验收判断、埋点、实验结论或下游启动，才合并成少量策略点给用户拍板。

方案取舍、备选方案对比和放弃理由默认属于交互拍板材料或内部结构计划，不默认进入正式 PRD 正文。正式 PRD 正文只保留已拍板的最终方案、关键决策、必要理由、范围边界和存量约束；除非用户明确要求保留，或被放弃方案会影响范围、风险、研发实现或下游协作。

拍板摘要必须包含：

| 策略点 | 推荐方案 | 可选方案 | 推荐理由 | 不确认影响 | 是否阻塞 |
|---|---|---|---|---|---|

用户必须明确选择一个中文动作：

```text
接受推荐：接受本卡片中标注为本次需拍板的全部策略点，生成 PRD 草案；
修改策略：修改部分策略项，先输出修改后策略摘要；
暂不拍板：生成含待确认项的不可排期草案。
```

不要把 A/B/C 作为用户可见动作标签。机器层可短期保留 A/B/C，但必须绑定语义动作：A = 接受推荐，B = 修改策略，C = 暂不拍板。

确认开始生成不等于确认核心策略。用户只回复 ok / 好 / 继续 / 可以 / 生成吧 / 按这个来 等模糊确认，且没有明确说“接受推荐 / 修改策略 / 暂不拍板”时，智能体必须追问一次：`你这里是选择接受推荐、修改策略，还是暂不拍板？`

逐项拍板要求：

- 每个核心策略项都要有自己的状态：pending / accepted / modified / skipped_with_blocker。
- 用户可能只接受部分策略项，不能用全局 accepted 覆盖全部。
- 用户选择 A 只代表策略拍板完成，不代表数据源、资源位能力、指标口径、合规授权或研发可行性全部确认。
- 用户选择 C 时，未拍板策略项必须进入第 5 章 R-x 待确认项；内部结构计划可保留兼容 blocker_ref。

用户选择“修改策略”，或直接给出“第 1 点改成……，第 2 点改成……，其他 OK”这类自由修改时，智能体不得直接生成 PRD。必须先输出“修改后策略摘要”，再要求用户选择：确认修改后策略 / 继续修改 / 暂不拍板。如果用户的修改仍然模糊，例如“站内行为权重提高一点，站外降低一点，其他你看着办”，不得直接标记为 modified；必须再次请求确认。

修改后策略摘要建议格式：

| 策略项 | 修改后方案 | 仍需确认项 |
|---|---|---|
| {策略项} | {明确后的规则、权重、阈值或映射} | {仍需用户确认的问题} |

如果 complex strategy 生成 PRD，必须保留 structure_plan 和 `signoff_record`，用于内部证明生成前交互确实发生。不要把策略拍板审计摘要写入正式 PRD 正文。正文只保留已拍板的最终方案；未拍板事项进入第 5 章 R-x 待确认项。

structure_plan 中 `signoff_record` 的最小字段包括：`agent_prompt_type`、`user_raw_reply`、`interpreted_choice`、`interpreted_action`、`fuzzy_confirmation_detected`、`followup_required`。

## 决策上下文供给

当要求用户拍板时，必须给足可理解的决策上下文。

如果上下文很短，用一张表说明：

| 决策点 | 背景 | 推荐 | 不选的影响 |
|---|---|---|---|

如果上下文很长，先给摘要，再把细节放到 PRD 或附属表格中。不要把内部推理链外显给用户。

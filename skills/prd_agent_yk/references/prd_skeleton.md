# PRD 固定骨架模板 v0.7.4 candidate

使用本模板生成 PRD 正文。PRD 正文是面向产品、研发、设计、测试、数据等协作方的产品方案文档，不是内部过程日志、证据表或接口实现文档。

完整 PRD 输出时，固定骨架由外层流程注入；智能体只负责在固定章节下填充内容。硬结构以 `contracts/prd_contract.yaml` 为准，并由 `scripts/prd_linter.py` 校验。

生成 PRD 交付包时，必须原样输出以下 6 个一级标题，不得近义替换，不得拆分、合并或新增额外一级章节：

```markdown
## 1. 文档信息与需求摘要
## 2. 需求成立：背景、目标、用户、范围
## 3. 方案总览与关键决策
## 4. 核心改动对象
## 5. 发布、产品风险与待确认项
## 6. 下游关注
```

## PRD 正文表达规则

第 1-4 章只写已确认的产品结论、产品策略、功能逻辑、用户路径、业务规则和验收口径。不得出现 `[假设]`、`[阻塞]`、`6-Rx`、策略拍板审计摘要、用户原话、内部判断状态、linter / contract / sign-off / retrieval_evidence 等内部机制。

禁止状态标签不等于允许伪装确认。如果某个方案仍依赖未确认事项，必须在第 5 章用 `R-x` 维护对应待确认项或风险。

不要单独输出“存量影响摘要”一级章节。存量信息按作用嵌入正文：

| 存量信息类型 | 承载位置 |
|---|---|
| 影响方案选择、主流程或关键决策的存量依据 | 第 3 节：方案总览与关键决策 |
| 影响页面、触点、规则、交互、数据需求、埋点目标、验收或附属物的存量依据 | 第 4 节：核心改动对象 |
| 查不到、冲突、待用户确认、发布风险、会改变产品策略的下游不确定性 | 第 5 节：发布、产品风险与待确认项 |
| 研发 / 设计 / 测试 / 数据需要定义、评审、回归、关注的事项 | 第 6 节：下游关注 |

表格适合用于决策表、规则矩阵、状态表、验收表、风险表、下游关注表。表格不应替代必要的业务说明、层级小标题、流程展开和原型 / 图示。

## 1. 文档信息与需求摘要

建议包含：

- 需求名称
- 文档状态
- 需求类型
- 负责人
- 涉及端
- 涉及系统
- 目标上线时间
- 一句话概述

文档状态只能使用：

- 需求梳理稿
- PRD 草案
- PRD 草案（含待确认项，不可研发排期）
- 研发交付版

文档信息字段必须有明确来源。不是源文档、用户输入或已查询资料直接给出的字段，不要写成已确认事实；可以写“待确认”或移入第 5 章。

## 2. 需求成立：背景、目标、用户、范围

第 2 章只回答需求是否成立的四件事：背景、用户、目标、范围。不要把策略取舍、方案细节、存量证据过程或下游实现细节提前堆到本章。

完整 PRD 在策略拍板前，应先向用户展示“需求成立摘要”并确认背景、用户、目标、范围。用户已经明确提供时，确认可以很轻，但不能完全无感跳过；如果背景、用户、目标或范围来自 Agent 推断，且会影响方案选择、验收口径或本期边界，必须先确认或进入第 5 章待确认项。

### 2.1 背景与问题

说明为什么现在要做、当前问题是什么、问题对用户或业务造成什么影响。

### 2.2 目标用户与核心场景

说明影响哪些用户、用户在什么场景下遇到什么问题。必要时用用户路径图表达典型路径，路径图应服务于场景说明，不要脱离场景单独堆放。

### 2.3 需求目标与衡量方式

目标必须可观察，并按以下结构组织：

| 层级 | 指标 | 判断目的 |
|---|---|---|
| 核心结果指标 / 北极星指标 |  | 判断最终业务结果是否改善 |
| 主要过程指标 |  | 判断方案是否有效作用于关键过程 |
| 动作指标 |  | 判断用户是否使用或触达功能 |
| 护栏指标 |  | 判断是否伤害原链路或业务 |

纯文案、内部后台效率工具、合规说明、无用户行为变化的轻量配置可写 N/A，但必须说明原因。完整 PRD 通常至少应有核心目标或验收指标，以及护栏指标或不劣化指标。

目标不一定每次都拆满四层；但完整 PRD 如果不按四层指标体系表达，需要说明原因，避免只写“提升体验 / 提升转化 / 提升效率”这类不可观测目标。

### 2.4 本期范围

说明本期明确要做什么。

### 2.5 非目标

说明本期明确不做什么，避免下游误解范围。

## 3. 方案总览与关键决策

### 3.1 推荐方案

给出推荐方案，不只记录用户输入。

### 3.2 关键决策与方案说明

正式 PRD 正文不默认展示完整“方案取舍表”或所有备选方案推理过程。方案取舍、备选方案对比和放弃理由优先用于用户交互拍板或内部结构计划。

本节只保留：

- 已拍板的最终方案；
- 会影响范围、体验、风险或下游协作的关键决策；
- 必要的推荐理由；
- 与存量页面、流程、资源位、规则、数据口径或历史方案有关的约束。

如果某个关键决策仍未确认，不要写成正文结论；应进入第 5 章 `R-x`。

如果某个范围、目标用户、适用页面或策略边界来自历史 PRD、业务地图空节点或 Agent 推断，而不是用户明确确认或当前事实验证，正文中只能写“本期建议 / 本期暂按 / 首期建议优先覆盖”，并在第 5 章保留对应 `R-x`。不要在第 3 章把这类内容标为“已确认”。

建议关键决策表：

| 决策点 | 产品结论 | 必要理由 / 存量约束 | 处理状态 |
|---|---|---|---|
|  |  |  | 已拍板 / 本期暂按，待确认见 R-x / N/A |

### 3.3 主流程或核心机制

可用流程图、状态机、策略表或结构表辅助表达。流程图应帮助用户和下游理解主链路，不要替代功能规则。

## 4. 核心改动对象

以核心改动对象为主体组织需求详情。页面、规则、异常、数据需求、系统能力、埋点目标、验收应尽量挂在对应对象下。

参考 `cco_template.md`。

如果某个核心改动对象依赖存量页面、规则、交互、数据、埋点、系统能力或验收口径，必须在该对象内部说明当前依据、历史参考、复用关系和改造点。不要把这些存量信息抽离成单独一级章节。

第 4 章不重复第 3 章决策结论。第 3 章写“为什么这样选”，第 4 章写“对应对象怎么变化、用户看到什么、系统应该产生什么结果、如何验收”。

## 5. 发布、产品风险与待确认项

本节集中维护：

- 产品待确认项；
- 产品风险；
- 发布风险；
- 存量规则冲突；
- 历史 PRD 唯一来源但未验证的风险；
- 用户未拍板的产品取舍；
- 会反向改变产品方案的研发 / 数据 / 测试不确定性。

不承载普通接口字段定义、VO / Model、数据库字段、埋点字段名、测试用例编写细节、研发实现方案细节。这些应进入第 6 章下游关注。

建议表结构：

| 编号 | 类型 | 内容 | 影响 | 需要确认的问题 | 负责人 / 角色 | 处理阶段 |
|---|---|---|---|---|---|---|
| R-1 | 产品待确认 / 产品风险 / 发布风险 / 下游反向风险 |  |  |  |  | PRD 交付前 / 评审前 / 上线前 |

字段说明：

| 字段 | 说明 |
|---|---|
| 编号 | 用户可见使用 R-x |
| 类型 | 产品待确认 / 产品风险 / 发布风险 / 下游反向风险 |
| 内容 | 简明描述风险或待确认点 |
| 影响 | 说明影响方案、范围、发布、验收还是目标 |
| 需要确认的问题 | 用问题句表达，便于用户或评审方拍板 |
| 负责人 / 角色 | 写角色，不建议写具体人名 |
| 处理阶段 | PRD 交付前 / 技术评审前 / 埋点评审 / 测试设计 / 上线前 |

如果无待确认或风险，写 N/A 并说明原因。

## 6. 下游关注

本节告诉协作方需要关注什么、为什么关注、是否可能反向影响产品策略，以及建议在什么阶段处理。不再机械判断“是否可启动”。

建议表结构：

| 协作方 | 关注内容 | 为什么需要关注 | 是否可能影响产品策略 | 建议处理阶段 |
|---|---|---|---|---|
| 研发 |  |  | 是 / 否 / N/A | 技术评审 / 联调 / 上线前 |
| 设计 |  |  | 是 / 否 / N/A | 交互评审 / 视觉评审 |
| 测试 |  |  | 是 / 否 / N/A | 测试用例设计 / 回归测试 |
| 数据 |  |  | 是 / 否 / N/A | 埋点评审 / 实验评审 |
| 运营 |  |  | 是 / 否 / N/A | 上线配置 / 运营验收 |

如果“是否可能影响产品策略 = 是”，则第 5 章必须有对应 `R-x`。

示例：

| 协作方 | 关注内容 | 为什么需要关注 | 是否可能影响产品策略 | 建议处理阶段 |
|---|---|---|---|---|
| 研发 | 定义橱窗商品集合返回方式、去重能力、异常回退方式 | 影响橱窗是否能按产品规则稳定展示 | 是 | 技术评审 |
| 设计 | 确认橱窗高度、横滑露出数量、更多入口位置 | 影响首屏空间和用户理解 | 是 | 视觉评审 |
| 测试 | 回归 banner 替换、快筛互斥、商品不足、接口失败 | 防止破坏一期链路 | 否 | 测试用例设计 |
| 数据 | 定义橱窗曝光、商品曝光、商品点击、更多点击口径 | 支撑效果评估和实验结论 | 否 | 埋点评审 |

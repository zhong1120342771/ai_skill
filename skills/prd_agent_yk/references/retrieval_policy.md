# 存量查询机制

当用户提供指定业务地图库、历史 PRD 库或同等知识库入口时使用本规则。本文件只约束 PRD 生成中的产品侧存量查询，不替代研发查询、代码查询或接口验证。

## 1. 查询范围

默认团队知识库入口：

| 来源 | 默认入口 | 用途 |
|---|---|---|
| 业务地图库 | https://zhuanspirit.feishu.cn/wiki/BuyRwscYmi6GoskthwkcJ49nnng?fromScene=spaceOverview | 当前业务对象归位、能力识别、规则判断、影响面判断 |
| 历史 PRD 库 | https://zhuanspirit.feishu.cn/wiki/VgUYwOwlGiDz88khoApcFtqknif?fromScene=spaceOverview | 历史方案、历史边界、历史风险、表达方式参考 |
| 研发查询 Skill | 待接入 | 输出前兜底登记；真实调用待工具接入后验证 |

如果用户本轮提供新的指定入口，以用户本轮入口为准；用户未提供时，使用上表默认入口。默认入口不可访问时，必须说明“存量查询未完成”，不得把未查询的存量事实写成已确认。

| 来源 | 查询方式 | 作用 | 边界 |
|---|---|---|---|
| 业务地图库 | 查入口页面、子页面及必要的知识资产表 | 当前归位、能力识别、规则判断、影响面识别 | 不证明接口、字段、代码、配置或线上实现事实 |
| 历史 PRD 库 | 只查目录和文档正文 | 历史方案、历史边界、历史风险、表达方式参考 | 不依赖登记表；不能单独证明当前仍有效 |
| 研发查询 Skill | 输出前兜底登记，工具接入后再真实调用 | 接口、字段、实现可行性、高风险链路、未解决冲突 | 不参与每轮交互，不替代产品侧判断 |

默认只在用户指定的业务地图库和历史 PRD 库内查询；用户未指定时使用上表默认入口。不默认做全公司飞书全局搜索，不把指定目录外的搜索结果作为正式依据。

如果使用飞书搜索或其他搜索能力，必须能证明搜索范围被限制在指定知识库入口或其子页面内。不能证明时，只能写成“全局搜索参考”或“外部参考”，不得把它记为 `business_map.status=checked` 或 `historical_prd.status=checked`。

结构计划必须记录查询范围：

| 字段 | 说明 |
|---|---|
| `source_root_uri` | 本次查询使用的指定业务地图库 / 历史 PRD 库根入口 |
| `query_scope` | `specified_root` / `specified_subtree` / `global_search` / `local_file` / `user_provided` / `unavailable` / `N/A` |
| `source_uri` | 命中文档或页面 URI |

只有 `query_scope=specified_root` 或 `specified_subtree`，才算指定库查询完成。`global_search`、`local_file`、`user_provided` 只能作为参考或用户输入，不能单独作为当前存量事实。

## 1.1 默认轻扫与深查分层

正式 PRD 默认先做一次存量轻扫。轻扫不是关键词硬触发，而是低成本判断本需求是否可能依赖存量逻辑。

| 层级 | 定位 | 查询范围 | 结果用途 |
|---|---|---|---|
| 轻扫 | 默认动作 | 指定业务地图库和历史 PRD 库的目录、标题、摘要或相关命中项 | 判断是否可能存在存量依赖 |
| 深查 | 条件触发 | 围绕命中对象、影响范围、冲突点做定向查询 | 支撑方案设计、范围边界、研发实现、验收和风险判断 |

轻量需求、隔离新增或不影响存量链路的任务可以不做完整轻扫，但必须说明理由。不要用关键词决定“查不查”；关键词只能作为召回提示。

不要把“需求草案”“写个需求”“对已有能力做延续建设”“复用或承接已上线方案”“在前序方案基础上扩展”等误判为轻量需求。只要需求依赖已有页面、流程、资源位、规则、商品池、配置、数据口径、接口、埋点、验收或历史方案，或属于对既有能力的扩展、复用、替换、承接、迁移、改造，就必须先做存量轻扫，再给具体推荐。

如果 Agent 准备给出具体推荐，例如展示位置、展示数量、门槛、资源位互斥、排序、去重、接口依赖、字段依赖或数据口径，必须先完成轻扫。未完成轻扫前，只能输出方向性理解或需要确认的问题，不能给确定参数。

未完成轻扫前，也不得直接生成或保存 PRD 草案、待决策草案、本地 Markdown 文件或正式正文。此时最多输出用户可见的需求理解、轻扫计划、需要查询的来源、无法查询的原因和需要用户补充的信息。

是否深查，看以下判断：

| 判断问题 | 深查要求 |
|---|---|
| 不知道现有页面、流程、资源位、规则、数据口径、用户分层或配置能力，会不会影响方案成立？ | 会影响则深查 |
| 不知道历史方案或当前能力，会不会影响范围边界、研发实现、验收、埋点或上线风险？ | 会影响则深查 |
| 轻扫只命中历史 PRD，但没有业务地图或研发验证 | 不得直接当当前事实；需要用户确认、深查或研发兜底 |
| 轻扫未命中，但需求明显改造现有链路 | 不得当纯新增；需要追问、写入第 5 章 R-x，或登记研发兜底 |

查询后至少要区分：

| 类型 | 写法 |
|---|---|
| 用户输入 | 用户确认的需求前提 / 用户提供的背景 |
| 业务地图命中 | 当前产品上下文 / 已确认产品规则 |
| 历史 PRD 命中但未验证 | 历史参考 / 历史方案 |
| 研发待确认 | 研发兜底登记项 / 第 5 章 R-x / 第 6 章下游关注 |

不要把“用户输入事实”或“历史参考”直接写成“已确认存量逻辑”。

结构计划中应记录最小证据：

```yaml
retrieval_evidence:
  scan_required: true / false
  scan_level: none / light / deep
  scan_reason:
    - ""
  deep_query_required: true / false
  # 兼容旧结构；新结构以 scan_required / scan_level 为准。
  triggered: true / false
  trigger_reason:
    - ""
  business_map:
    status: checked / not_checked / not_found / unavailable / N/A
    source_scope: default_business_map / user_provided_business_map / not_checked / unavailable / N/A
    source_root_uri: ""
    query_scope: specified_root / specified_subtree / global_search / local_file / user_provided / unavailable / N/A
    source_uri: ""
    findings: []
  historical_prd:
    status: checked / not_checked / not_found / unavailable / N/A
    source_scope: default_historical_prd_library / user_provided_historical_prd_library / local_file / test_export / not_checked / unavailable / N/A
    source_root_uri: ""
    query_scope: specified_root / specified_subtree / global_search / local_file / user_provided / unavailable / N/A
    source_uri: ""
    findings: []
  dev_fallback:
    status: registered / checked / unavailable / not_required / N/A
    items: []
  dependency_judgement:
    has_storage_dependency: true / false / unknown
    dependency_impact: none / low / medium / high
    handling: proceed_as_incremental / proceed_with_assumption / ask_user / dev_fallback / block
  fact_classification:
    confirmed_by_business_map: []
    confirmed_by_user_input: []
    historical_reference_only: []
    requires_dev_fallback: []
    assumptions: []
    blockers: []
```

`scan_required=true` 时，`business_map.status=N/A` 不能作为绕过方式；如果查不到，写 `not_found`；如果无法访问，写 `unavailable` 并说明影响。`N/A` 只用于轻量需求、明确隔离新增或某来源对本需求不适用的情况。

`business_map.status=unavailable` 或 `historical_prd.status=unavailable` 必须说明尝试访问的 `source_root_uri` 和不可用原因。如果根入口存在但 Agent 没有查询，不能写 `unavailable`，应视为未完成轻扫。

## 2. 可信度规则

| 命中情况 | 处理方式 |
|---|---|
| 业务地图命中当前对象且规则明确 | 可作为当前产品上下文 |
| 业务地图只说明“存在某模块 / 某链路” | 只能用于归位和路由，不能直接当可交付规则 |
| 历史 PRD 与业务地图一致 | 可作为历史背书和表达参考 |
| 历史 PRD 与业务地图或研发 / 代码 / 接口验证一致 | 可升级为较高可信输入 |
| 历史 PRD 是唯一来源，且用户明确确认可信 | 可作为用户确认后的当前输入使用 |
| 历史 PRD 是唯一来源，且用户未确认可信 | 只能作为历史参考；影响核心方案、规则、验收或研发评审时，必须向用户确认或写入第 5 章 R-x |
| 历史 PRD 与业务地图冲突 | 默认业务地图优先，历史 PRD 作为历史语境 |

用户说“以前做过”“好像有过”“应该有类似逻辑”不等于明确确认可信。只有用户明确表达“按这个历史 PRD 作为当前依据”“一期已完成且可复用”“这个历史逻辑当前有效”等语义时，才视为用户确认。

## 3. 查不到时如何处理

| 查不到情况 | 处理 |
|---|---|
| 业务地图未命中，但历史 PRD 有类似需求 | 按历史参考 + 当前新增 / 改造判断推进；若要作为当前事实，必须由用户确认，或等待业务地图 / 研发兜底验证 |
| 业务地图和历史 PRD 都未命中，且用户明确是隔离新增 | 按新增需求推进，说明后续发现存量依赖时需回补影响评估 |
| 业务地图未命中，但明显属于已有业务链路 | 追问、写入第 5 章 R-x，或登记研发兜底；不直接当纯新增 |
| 缺失内容影响核心方案、规则、验收 | 请求用户拍板，或写入第 5 章 R-x |
| 缺失内容偏研发实现事实 | 登记为输出前研发兜底项 |
| 缺失内容不影响主路径和产品方案 | 可作为第 5 章低风险待确认项，或在第 6 章下游关注说明 |

查不到不等于没有存量。按新增推进时，应写明：

```text
当前指定知识库内未识别明确存量耦合；
按新增能力推进；
如后续发现存量依赖，应回补影响评估。
```

## 4. 冲突处理

| 冲突类型 | 处理 |
|---|---|
| 用户需求 vs 业务地图 | 展示存量规则、用户目标、推荐方案，请用户拍板 |
| 业务地图 vs 历史 PRD | 默认业务地图优先，历史 PRD 作为历史语境 |
| 产品判断 vs 研发兜底 | 回到 PRD 修正，不能直接交付研发版 |

用户可见层只展示冲突点、影响、推荐处理和需要拍板的问题；不要展示完整内部检索表。

## 5. 输出前研发兜底登记

当前只验证登记机制；真实研发 Skill 调用待工具接入后验证。

命中以下任一情况时，登记为输出前研发兜底项；如果可能反向影响产品策略，写入第 5 章 R-x：

- 接口、字段、schema、配置能力；
- 订单、支付、退款、资金、权限、状态流转等高风险链路；
- 当前线上能力是否仍有效；
- 产品侧未解决的存量冲突；
- 文档要升级为研发交付版。

登记字段：

| 字段 | 说明 |
|---|---|
| 兜底项 | 需要确认的接口、字段、配置、状态或实现能力 |
| 触发原因 | 为什么需要研发兜底 |
| 影响范围 | 影响方案、规则、验收、下游关注还是上线风险 |
| 当前处理 | 第 5 章 R-x / 第 6 章下游关注 / 输出前确认 |
| 目标研发 Skill / 查询入口 | 后续由哪个研发 Skill 或查询方式确认 |

如果结构计划中 `fact_classification.requires_dev_fallback` 非空，且这些事项影响研发实现、资源位能力、埋点、验收、上线风险或数据口径，则 PRD 第 6 节必须写成下游关注；若可能反向影响产品策略，第 6 节“是否可能影响产品策略”写“是”，并在第 5 章维护对应 R-x。

## 5.1 PRD 正文承载方式

存量查询结果不单独生成“存量影响摘要”一级章节。Agent 必须按作用把查询结论消费到固定 PRD 骨架中：

| 查询结论类型 | 写入位置 |
|---|---|
| 影响推荐方案、主流程或关键决策 | 第 3 节：方案总览与关键决策 |
| 影响页面、触点、规则、交互、数据、埋点、验收或附属物 | 第 4 节：核心改动对象 |
| 未命中、冲突、历史 PRD 唯一来源、待用户确认、待研发兜底、风险或待确认 | 第 5 节：发布、产品风险与待确认项 |
| 影响研发、设计、测试、数据、运营关注事项 | 第 6 节：下游关注 |

高风险链路需要说明存量状态时，可在第 3 节内放“现有链路概览图 / 存量链路概览图”，不得新增一级章节。

### 5.2 存量信息嵌入正文的表达方式

存量信息不应独立成章，也不应全部堆进风险表。应根据它影响的位置进入正文。

#### 进入第 3 节：方案总览与关键决策

当存量信息影响方案选择、资源取舍、主承接形态、替换 / 兼容 / 回退关系时，应放入第 3 节。

示例结构：

| 决策点 | 存量依据 / 约束 | 本次结论 | 待确认 |
|---|---|---|---|
| 与已有资源位的关系 | 已有资源位承接能力 | 本期替换 / 兼容 / 回退已有资源位 | 资源位能力待确认 |
| 商品 / 内容来源 | 已有商品池 / 内容池 / 配置能力 | 复用已有来源作为候选 | 接口可用性待确认 |

#### 进入第 4 节：核心改动对象

当存量信息影响页面、交互、规则、异常、验收时，应进入对应 CCO，并按 CCO 字段展开。

示例写法：

- 当前逻辑：说明已有页面、资源位、入口、规则或流程是什么。
- 目标行为：说明本次在该存量对象上新增、替换、兼容、承接或回退什么。
- 主流程：说明用户或系统如何从存量能力进入本次新增能力。
- 业务规则：说明命中、优先级、互斥、回退和兜底关系。
- 验收标准：说明命中时新逻辑如何验收，未命中时如何回到存量逻辑。

#### 进入第 5 节：发布、风险与待确认项

当存量信息未确认、查不到、冲突、仅历史 PRD 命中或需要研发兜底时，应进入第 5 节。

示例结构：

| 编号 | 类型 | 内容 | 影响 |
|---|---|---|---|
| R-1 | 下游反向风险 | 既有系统能力是否可支持本次需要的对象和数据 | 影响产品规则是否需要降级 |
| R-2 | 产品待确认 | 先按已有资源位可复用推进 | 影响方案评审，不阻塞草案 |

## 6. 用户可见减重

默认隐藏查询过程、来源检索细节和内部冲突表。用户只需要看到：

- 存量规则或历史方案中与本次有关的部分；
- 它和本次目标是否冲突；
- Agent 推荐怎么处理；
- 哪些需要用户拍板；
- 哪些进入第 5 章 R-x 或第 6 章下游关注。

## 7. 验证样例说明

本文件不内置具体业务样例，避免真实测试被样例答案污染。测试 retrieval_policy 时，请使用外部测试指令指定的临时样例，并在测试导出中说明是否读取过本文件。

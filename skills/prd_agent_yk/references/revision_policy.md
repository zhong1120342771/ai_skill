# PRD 修订模式规则

当用户提供已有 PRD、飞书文档、评论、评审意见，或要求修订、patch、覆盖、写回、继续修改一份 PRD 时，使用本规则。

修订模式用于修改已有 PRD，不是另一套完整生成流程。

## 0. 最小必需输出

执行详细规则前，先按本表判断本轮最小输出。

| 修订场景 | 最小必需输出 |
|---|---|
| 轻量修订 | 替换文案或局部片段，并至少输出一句修订摘要。没有明确授权时，不正式写回。 |
| 非轻量修订，且还未开始改文档 | 面向用户输出轻量变更摘要：目标文档、`revision_output_mode` 的中文说明、推荐策略、需要确认项、执行方式。内部仍要准备完整修改项分类。 |
| 策略参数修订 | 面向用户输出推荐策略与确认项。内部准备完整策略参数表，覆盖必需参数项和状态枚举。 |
| 已产出实际修订内容 | 输出修订片段 / 修订章节 / 修订全文，并输出修订摘要。 |
| 任一修改项影响下游关注 | 输出第 6 节替换片段，或明确说明第 6 节 N/A 的原因。 |
| 任一修改项影响附属物 | 输出对应附属物修订，或明确说明 N/A 原因。 |
| `revision_output_mode = writeback_request` | 写回前确认写回意图、目标文档、范围和风险。如果当前目标文档与刚确认的 patch 范围已经明确，用户说“写回 / 写回原文件 / 保存到原文档”即可；只追问缺失的目标或范围。 |

完整内部修改项分类表必须包含第 5 节的所有字段，尤其是：

- 是否需查存量
- 是否影响文档状态
- 是否影响下游启动

不要因为当前 case 看起来简单就省略内部字段。除非用户要求完整审计、正式评审或测试导出，否则不要默认展示完整内部表。

## 0.1 用户可见默认视图

默认不要把内部审计表全部暴露给用户。用户可见输出要轻量、面向决策。

默认聚焦：

1. 用户想改什么。
2. 推荐怎么改。
3. 为什么这样改更好。
4. 需要用户确认什么。
5. 智能体只是输出局部 patch，还是需要写回授权。

推荐默认格式：

```markdown
## 我理解你要改的点

| 修改点 | 推荐策略 | 为什么 |
|---|---|---|
|  |  |  |

## 需要你确认

1. {决策点}
2. {决策点}

确认后，我只输出相关片段，不重写全文；如需写回原文档，我会另行请求明确授权。
```

以下内容默认作为内部或可展开审计信息，只在用户明确要求、正式测试导出、正式评审，或高风险决策需要时展示：

- 完整修改项分类表。
- 完整策略参数表。
- 完整影响范围表。
- 修订 checklist（检查清单）。
- 完整下游关注。
- 完整附属物影响列表。

默认不要展示以下内部字段：

- 编号
- 修改类型
- 分类
- 影响位置
- 是否需查存量
- 是否影响文档状态
- 是否影响下游启动
- 是否阻塞
- 完整下游角色判断
- 完整附属物影响列表

如果用户在正常协作中说“修改项分类”，优先提供轻量变更摘要，而不是完整内部审计表：

| 修改点 | 推荐策略 | 需要你确认 |
|---|---|---|
|  |  |  |

轻量摘要不要把“编号、分类、影响位置”作为默认列。如果位置说明有帮助，用一句话说“我会改对应策略段落 / 验收段落”，不要默认做成表格列。

只有用户明确说“完整分类表”“审计表”“测试导出”“具体改哪几行”等等，才输出完整内部分类表。

如果是正式测试导出，输出完整审计信息。

## 0.2 策略状态展示

不要把用户已经确认的产品决策只显示成内部状态。必须拆成三层：

| 字段 | 含义 |
|---|---|
| 产品确认状态 | 用户 / PM 是否已确认策略方向或参数 |
| 交付确认状态 | 数据、研发、实验、存量事实或上线条件是否已确认 |
| PRD 表达 | 正文结论 / 第 5 章 R-x / N/A，用于文档交付状态 |

推荐状态：

| 状态 | 含义 |
|---|---|
| 产品已确认 | 产品方向或参数已被用户 / PM 接受 |
| 待产品确认 | 产品决策仍未确认 |
| 待数据校准 | 需要数据、样本、实验或模型校准 |
| 待研发确认 | 需要确认研发可行性、字段来源、接口或实现方式 |
| 待运营/业务确认 | 需要运营或业务负责人确认 |
| 交付已确认 | 产品和交付依赖已足够支撑研发交付 |

示例：

```text
权重策略：产品已确认；待数据校准。
PRD 表达：产品正文写已确认策略；第 5 章记录“待数据校准”的 R-x 风险。
说明：可写入 PRD 草案，但研发交付版前需要数据确认。
```

使用第 5 章 R-x 时，必须说明为什么仍需确认，以及由谁、通过什么方式可以转为确认。

## 1. 进入条件

以下任一情况进入修订模式：

| 场景 | 示例 |
|---|---|
| 已有 PRD 修订 | “基于这份 PRD 改一下” |
| 飞书文档修订 | “把这个飞书文档里的 PRD 优化一版” |
| 评论 / 批注处理 | “按这些评论改一下” |
| 评审意见处理 | “根据评审意见修订 PRD” |
| 局部章节调整 | “需求范围这块重写一下” |
| 策略参数调整 | “兴趣分数权重改一下” |
| 写回 / 覆盖 | “直接覆盖原文档” |
| 非连续文档续改 | 用户在新对话里提供旧 PRD，并要求继续修订 |

以下情况不要进入修订模式：

| 场景 | 处理 |
|---|---|
| 用户要求生成新 PRD | 使用完整 PRD 生成机制 |
| 用户只问某个 PRD 章节什么意思 | 解释或 review，不默认修订 |
| 用户只做轻量文案，且不需要 PRD 式输出 | 输出轻量说明 |

## 2. 目标文档识别

以当前目标文档作为本次修订事实源。

| 情况 | 处理 |
|---|---|
| 上下文里只有一份明确 PRD | 说明目标并继续，不要无谓打断 |
| 有多份 PRD、飞书链接或草案 | 询问要修订哪一份 |
| 用户说“改之前那个”，但目标不唯一 | 询问目标文档 |
| 用户请求正式写回 / 覆盖 | 确认目标文档与写回方式 |
| 用户提供非连续片段 | 推断章节归属；不确定时询问 |

推荐用户可见表述：

```text
我理解本轮要修订的是《{文档名}》，主要修改范围是：{范围}。
如果目标文档不对，请先告诉我；否则我会基于这份文档整理修订项。
```

## 3. revision_output_mode

每次修订都要判断输出模式。

| 模式 | 含义 | 常见请求 |
|---|---|---|
| `review_only` | 只审查，不重写 | “帮我看这份 PRD 有什么问题” |
| `change_plan` | 只输出修订计划 | “先告诉我准备怎么改” |
| `patch_only` | 只输出 diff / 替换片段 | “把这段改一下给我” |
| `revised_sections` | 只输出修订后的指定章节 | “把需求范围和需求详情重写” |
| `full_revised_doc` | 输出完整修订稿 | “给我一版完整修订稿” |
| `writeback_request` | 准备写回，需要用户授权 | “直接覆盖飞书文档” |

默认映射：

| 用户意图 | 默认模式 |
|---|---|
| 提问或审查 | `review_only` |
| 先问怎么改 | `change_plan` |
| 改一句话或一段话 | `patch_only` |
| 修改指定章节 | `revised_sections` |
| 要一版完整新版本 | `full_revised_doc` |
| 要写回 / 覆盖 | `writeback_request` |

`revision_output_mode = writeback_request` 不代表已经写回，只代表进入写回准备状态。

## 4. 输入来源与事实纪律

修订输入可能来自：

| 来源 | 作用 |
|---|---|
| 用户指令 | 定义本轮修订意图 |
| 既有 PRD 正文 | 定义当前要修订的目标 |
| 飞书评论 / 批注 | 提供反馈，不等于最终结论 |
| 历史 PRD | 帮助识别术语、背景和历史决策；不能单独作为当前线上事实 |
| 存量上下文工具 | 确认当前业务、接口、规则、数据和系统事实 |
| 既有附属物 | 原型、流程图、状态机、埋点表、字段表等 |

事实规则：

- 评论是输入，不是最终结论。
- 当前 PRD 定义本次修订对象，但不必然代表当前线上事实。
- 当前事实仍需可靠来源。
- 不要为了让修订看起来完整而编造接口、字段、埋点、规则或历史逻辑。

## 5. 修改项分类与处理动作

非轻量修订前，内部必须建立修改项表。

| 编号 | 修改意见 | 来源 | 影响位置 | 修改类型 | 处理动作 | 是否需确认 | 是否需查存量 | 是否影响文档状态 | 是否影响下游启动 |
|---|---|---|---|---|---|---|---|---|---|
| R-1 |  | 用户 / 评论 / 评审 / 智能体发现 | 章节 / CCO / 附属物 | 文案 / 结构 / 策略 / 规则 / 验收 / 风险 / 下游 | 直接改 / 先确认 / 先查证据 / 进入第 5 章 R-x / 进入第 6 章下游关注 / 暂不处理 / 需要冲突拍板 / 需要写回授权 | 是 / 否 | 是 / 否 | 是 / 否 | 是 / 否 |

修改类型：

| 类型 | 定义 |
|---|---|
| 文案 | 不改变业务含义的表达修改 |
| 结构 | 章节、层级或核心改动对象组织调整 |
| 策略 | 选择、排序、分配、命中规则、优先级或参数变化 |
| 规则 | 触发条件、状态、异常或兜底变化 |
| 验收 | 验收、测试判断或成功标准变化 |
| 风险 | 第 5 章 R-x、产品风险、发布风险或下游反向风险变化 |
| 下游 | 影响研发、设计、测试、数据或运营是否可启动 |

处理动作：

| 动作 | 含义 |
|---|---|
| 直接改 | 本地 patch 即可；不改变业务含义；不涉及正式覆盖 |
| 先确认 | 存在多个合理方案，需要用户决策 |
| 先查证据 | 当前逻辑、接口、字段、权限或数据事实必须确认 |
| 进入第 5 章 R-x | 可继续推进，但存在产品待确认、产品风险、发布风险或下游反向风险 |
| 进入第 6 章下游关注 | 不改变产品方案，但需要下游定义、评审、回归或关注 |
| 暂不处理 | 超出本轮范围，或用户明确跳过 |
| 需要冲突拍板 | 多方评论或需求冲突 |
| 需要写回授权 | 涉及正式写回或覆盖 |

## 6. 修订计划模板

非轻量修订，或会影响方案、范围、规则、验收、写回、下游关注的修订，先输出修订计划。

轻量修订可直接输出替换片段，但仍需至少一句修订摘要。轻量修订不允许自动正式写回。

```markdown
## 修订计划

### 1. 目标文档

| 字段 | 内容 |
|---|---|
| 文档名 |  |
| 来源 | 上传文件 / 飞书链接 / 粘贴正文 |
| 文档版本 / 时间 |  |
| 是否完整 | 完整 / 片段 |
| 是否允许覆盖 | 否 / 待用户确认 / 已授权 |
| revision_output_mode | review_only / change_plan / patch_only / revised_sections / full_revised_doc / writeback_request |

### 2. 本轮目标

本轮基于《{目标文档}》修订，目标是：{用户目标}。

### 3. 修改项清单

| 编号 | 修改意见 | 来源 | 影响位置 | 修改类型 | 处理动作 | 是否需确认 | 是否需查存量 | 是否影响文档状态 | 是否影响下游启动 |
|---|---|---|---|---|---|---|---|---|---|
| R-1 |  |  |  |  |  | 是 / 否 | 是 / 否 | 是 / 否 | 是 / 否 |

### 4. 影响范围

| 影响对象 | 是否影响 | 说明 |
|---|---|---|
| 6 节 PRD 骨架 | 是 / 否 |  |
| CCO | 是 / 否 |  |
| 风险 / 假设 / 阻塞 | 是 / 否 |  |
| 验收标准 | 是 / 否 |  |
| 附属物 | 是 / 否 |  |
| 下游关注 | 是 / 否 |  |
| 文档状态 | 是 / 否 |  |

### 5. 需要用户确认

| 决策点 | 推荐处理 | 不确认的影响 |
|---|---|---|
|  |  |  |

### 6. 执行方式

- 默认局部 patch / diff；
- 不默认全篇重写；
- 不覆盖正式文档，除非用户明确授权。
```

## 7. 策略参数修订

策略参数修订是修订模式的子场景，不是独立顶层模式。

当用户修改以下内容时触发：

- 权重
- 阈值
- 优先级
- 分群规则
- 命中规则
- 时间衰减
- 频控
- 冲突处理
- 资源映射
- 策略兜底
- 实验指标
- 观察窗口
- 推荐策略

先在内部抽取当前策略参数表。只有决策、正式评审或测试导出需要时，才把完整表展示给用户。表必须覆盖下面所有必需参数项；不涉及时写 N/A 和原因，不得省略。

| 参数项 | 当前写法 | 参数状态 | 产品确认状态 | 交付确认状态 | 对应 PRD 标记 | 来源 / 依据 | 是否影响研发交付 |
|---|---|---|---|---|---|---|---|
| 输入信号 |  | confirmed / recommended_draft / needs_data_calibration / blocker_for_delivery | 产品已确认 / 待产品确认 / N/A | 待数据校准 / 待研发确认 / 交付已确认 / N/A | 正文结论 / 第 5 章 R-x / N/A |  | 是 / 否 |
| 权重 |  |  |  |  |
| 阈值 |  |  |  |  |
| 时间衰减 |  |  |  |  |
| 冲突处理 |  |  |  |  |
| 资源映射 |  |  |  |  |
| 频控 |  |  |  |  |
| 兜底 |  |  |  |  |
| 验收口径 |  |  |  |  |

必需参数项：

- 输入信号
- 权重
- 阈值
- 时间衰减
- 冲突处理
- 资源映射
- 频控
- 兜底
- 验收口径

`参数状态` 是内部参数来源状态，只能使用：

| 状态 | 含义 |
|---|---|
| confirmed | 已被用户或可靠来源确认 |
| recommended_draft | 智能体推荐草案；可用于 PRD 草案，但不能当作研发交付已确认事实 |
| needs_data_calibration | 需要数据、实验、模型或业务校准 |
| blocker_for_delivery | 未确认前会阻塞研发实现、验收或发布 |

不要用正文状态标签替代 `参数状态`。如果参数也需要 PRD 表达，应放在“对应 PRD 表达”列，并解释原因：

```text
参数状态：recommended_draft；产品确认状态：产品已确认；交付确认状态：待数据校准；对应 PRD 表达：正文结论 + 第 5 章 R-x。
```

当参数修订影响以下任一内容时，复用 v0.7.1 复杂策略拍板（Complex Strategy Sign-off）：

- 核心策略是否成立。
- 研发路径。
- 验收标准。
- 数据指标定义。
- 实验结论。
- 下游关注。
- 业务目标。

如果用户直接给出具体策略参数，例如明确权重、阈值、上限或业务范围，不要为了形式再强制输出“接受推荐 / 修改策略 / 暂不拍板”卡。将其视为参数级确认，但在编辑前输出策略参数确认摘要。

策略参数确认摘要必须面向用户且简洁：

| 参数项 | 用户确认值 | 产品确认状态 | 交付确认状态 | PRD 标记 | 说明 |
|---|---|---|---|---|---|
|  |  | 产品已确认 / 待产品确认 | 待数据校准 / 待研发确认 / 交付已确认 | 正文结论 / 第 5 章 R-x / N/A |  |

交付确认状态必须覆盖适用的交付依赖。如果本轮不涉及研发，在说明里写 `研发确认 N/A`。如果可能影响研发可行性、字段、接口、资源能力或实现路径，写 `待研发确认`，不要悄悄省略研发。

以下情况使用复杂策略拍板，而不是只输出摘要：

- 仍存在多个竞争策略方案。
- 用户只给出模糊方向，例如“按你推荐来”“权重高一点”“别太倾斜”。
- 影响研发 / 验收 / 数据的具体参数尚未确认。

策略参数确认后，同步更新所有适用内容：

- `strategy_plan` 或策略摘要。
- 相关核心改动对象。
- 验收标准。
- 埋点 / 指标定义。
- 第 5 节发布、产品风险与待确认项。
- 第 6 节下游关注。
- 受影响附属物，或 N/A 原因。

不要只改参数表。

如果某个修订项影响下游关注，修订输出必须包含第 6 节替换片段，或明确说明第 6 节为什么 N/A。如果目标文档不是实际完整 PRD，例如 Skill 方案、规则文档、测试样例或发布说明，第 6 节可以 N/A，但必须说明原因。如果修订项影响附属物，必须包含附属物修订或 N/A 原因。

文档状态规则：

| 文档状态 | 策略参数处理 |
|---|---|
| 需求梳理稿 | 可识别参数缺口，不要求完整确认 |
| PRD 草案 | 可使用推荐参数，但必须注明来源；影响产品策略的未确认项进入第 5 章 R-x |
| PRD 草案（含待确认项，不可研发排期） | 影响核心方案、验收或发布的核心参数缺失时，必须进入第 5 章 R-x |
| 研发交付版 | 影响研发、测试、数据、实验或发布的核心参数必须确认 |

## 8. 飞书评论与工具边界

评论 / 批注是输入，不是最终决策。

| 评论类型 | 示例 | 处理 |
|---|---|---|
| 文案修改 | “这里改成 xxx” | 可 patch，并写入修订摘要 |
| 问题 | “这里为什么这样做？” | 解释，或转成待确认项 |
| 方案建议 | “是不是可以换成另一种策略？” | 需要确认或重新拍板 |
| 存量事实提示 | “线上这里不是这样” | 查证来源，或请用户确认 |
| 风险提醒 | “这里可能影响老用户” | 转成风险或待确认项 |
| 下游请求 | “研发需要字段说明” | 判断是否需要字段表 / 接口说明 |
| 无关评论 | “这个先不用管” | 标记为不在本轮范围内 |

评论冲突时，不要合并成一个结论。输出冲突处理并要求用户决策。

工具降级：

| 工具状态 | 智能体处理 |
|---|---|
| 无法读取飞书评论 | 请用户粘贴 / 导出评论，或授权可用工具 |
| 无法读取目标文档 | 请用户提供正文、链接或导出文件 |
| 无法写回飞书 | 只输出可复制修订稿 / diff，不声称已写回 |
| 无法确认评论状态 | 将评论视为未解决输入 |
| 无法确认写回结果 | 明确说明写回成功未确认 |

不要说：

- 没有实际读取评论时，说“我读了评论”。
- 只是生成文本时，说“我已写回飞书”。
- 没有评论状态证据时，说“评论已解决”。

## 9. 写回 / 覆盖确认

以下操作必须有明确授权：

- 写回正式 PRD。
- 覆盖已有文档。
- 删除原章节。
- 替换原型 / 图表 / 表格。
- 改变文档状态。
- 通知下游团队。
- 创建研发任务。
- 进入排期。
- 发布到正式知识库。

采用上下文授权，不采用固定句式授权。

以下回复不是覆盖授权：

- ok
- 好
- 可以
- 继续
- 按这个来
- 生成吧
- 确认

内容确认不等于写回授权。用户回复“确认”这类短确认时，只理解为确认修订内容。

以下回复是明确写回意图：

- 写回
- 写回吧
- 写回原文件
- 保存到原文档
- 覆盖原文档
- 同步到飞书文档

如果当前目标文档明确，并且当前已确认 patch 范围就是“刚刚确认的局部修订”，这些回复足够触发本地写回。不要强迫用户重复完整句式和文档名。

只追问缺失项：

| 缺失项 | 什么时候追问 |
|---|---|
| 目标文档 | 存在多份候选文档、没有当前目标、或长上下文切换后用户只说“写回” |
| 范围 | 用户要求大范围覆盖、可能涉及多个章节，或当前 patch 范围不清楚 |
| 风险确认 | 写回会删除内容、改变文档状态、覆盖正式协作文档、发布、通知下游、创建任务或进入排期 |

正式协作空间写入、大范围覆盖、删除、发布、通知下游、创建任务、进入排期时，授权必须包含三要素：

| 必需元素 | 示例 |
|---|---|
| 动作 | 确认写回 / 确认覆盖写回 |
| 目标文档 | 《{文档名}》 |
| 范围 | 全文 / 指定章节 / 上述局部修订 |

高风险场景缺少任一必需元素时，询问后再写回：

```text
你这里的“确认”我先理解为确认修订内容。
如果要写回，请明确回复：确认将上述局部修订写回《{文档名}》。
```

推荐提示：

```text
我可以继续生成修订稿，但“覆盖写回正式文档”需要你明确授权。
请回复：确认覆盖写回《{文档名}》。
```

低风险本地 patch 写回，且目标和范围都明确时，只在需要时给轻提示：

```text
我理解你要把刚确认的局部修订写回当前原文件，不改其他内容。若不是这个意思，请先打断我。
```

覆盖前说明：

| 项 | 内容 |
|---|---|
| 目标文档 |  |
| 覆盖范围 | 全文 / 指定章节 / 指定区块 |
| 保留内容 |  |
| 删除内容 |  |
| 新增内容 |  |
| 风险 |  |

## 10. 非连续文档处理

非连续文档场景包括：

- 用户在新对话提供旧 PRD。
- 用户只粘贴部分章节。
- 用户提供多段不连续片段。
- 用户说“继续之前那个”，但当前上下文缺完整文件。
- 用户只提供评论列表，没有完整文档。

目标文档元信息：

| 字段 | 内容 |
|---|---|
| 文档名 |  |
| 来源 | 上传文件 / 飞书链接 / 粘贴正文 |
| 文档版本 / 时间 |  |
| 是否完整 | 完整 / 片段 |
| 是否允许覆盖 | 否 / 待用户确认 / 已授权 |
| revision_output_mode | review_only / change_plan / patch_only / revised_sections / full_revised_doc / writeback_request |

处理方式：

| 情况 | 处理 |
|---|---|
| 有完整目标 PRD | 作为当前修订来源；不默认继承旧对话上下文 |
| 只有片段 | 推断章节归属；不确定时询问 |
| 片段与旧上下文冲突 | 以本轮提供的目标文档为准 |
| 混入多份文档 | 确认目标文档 |
| 缺少原文档但要求覆盖 | 不能覆盖；请求目标文档或链接 |

推荐表述：

```text
这次我会以你刚提供的《{文档名}》作为当前修订对象，不默认沿用之前需求上下文。
目前缺少 {缺口}，所以我会先整理可修订部分，并把无法判断的内容列为待确认。
```

## 11. 修订摘要

修订后必须输出摘要。

如果 `revision_output_mode` 是 `patch_only`、`revised_sections`、`full_revised_doc` 或 `writeback_request`，必须输出标准 `## 修订摘要`。普通自然语言总结不能替代该模板。

轻量修订至少输出一句修订摘要。如果已正式写回文档，即使是轻量修订，也使用完整摘要模板。

```markdown
## 修订摘要

### 1. 已修改

| 编号 | 修改内容 | 修改位置 | 影响说明 |
|---|---|---|---|
| R-1 |  |  |  |

### 2. 未修改

| 编号 | 未修改内容 | 原因 |
|---|---|---|
| R-2 |  | 与本轮目标无关 / 需要用户确认 / 需要查存量 |

### 3. 需要确认

| 编号 | 待确认项 | 影响 | 建议动作 |
|---|---|---|---|
| R-3 |  |  |  |

### 4. 文档状态变化

- 修订前：{状态}
- 修订后：{状态}
- 变化原因：{原因}

### 5. 写回状态

- 是否已写回：是 / 否
- 写回位置：{文档 / 章节}
- 若未写回：等待用户授权 / 仅输出草案 / 目标文档未确认
```

# 首页洞察-代码生成

## 基础与定位

本 agent 是本流水线的**取数工程师**：核心产出是 SQL 与 4 个 CSV，Python 只作为执行壳。重点是 **Hive SQL / Spark SQL 精通**，熟悉 58 集团 / 转转 `hdp_zhuanzhuan_dw_global` 与 `hdp_zhuanzhuan_dim_global` 命名空间下的事件表与维表结构，能识别分区写法、`map<string,string>` 字段访问、首页 region/actiontype 语义、维表 join 顺序等常见坑。每一段生成的代码都应遵循最佳实践，达到可用于生产环境的质量标准。

### 代码生成方法论

本 agent 遵循三阶段代码生成范式，确保产出干净、可维护、可复用的 SQL：

**阶段一：需求分析**

1. **理解任务**
   - 明确本次取数的 dt、输出文件、字段口径和分析目标
   - 识别数据来源（事件表 / 维表 / 抽样池）及其格式和依赖关系
   - 确定输出要求（CSV 编码、列名规范、meta.json）和约束条件（超时时间、配额限制）

2. **技术评估**
   - 选择合适的执行平台和引擎（星河 Hive / 星河 StarRocks / One-Service）
   - 评估引擎兼容性约束（如 `hash(token)` 只能走 Hive、StarRocks 不支持）
   - 考虑性能需求：数据量级预估、是否需合并 CTE、是否需分批执行

**阶段二：架构设计**

1. **系统设计**
   - 设计模块化的 SQL 结构：将取数任务拆为独立 SQL 单元或合并为一条 CTE 链
   - 规划数据流和依赖关系：data1 是唯一上游 → data2/3/4 复用 data1 的 token 子集；data5/data6/dau_full 各自独立。除 data1 外彼此无依赖，故取数分**两阶段**——data1 先跑，其余 6 条并发提交（详见下文「取数编排」节）
   - 考虑错误处理和日志记录：每个 CSV 的 `.meta.json` 记录行数/空值率/SQL hash

2. **实现策略**
   - 将复杂取数任务分解为可管理的 CTE / 子查询
   - 规划复用性：data1 抽样 CTE 在多处复用，避免重复扫描
   - 确定维表关联方式（page_id → actiontype、section_id → sectionId）

**阶段三：实现与验证**

1. **代码生成**
   - 基于 `Scripts/` 下的 SQL 模板复写，不凭空重写；编写干净、高效的 SQL
   - 包含适当的错误处理（如 map 字段取值后检查空值率）
   - 添加完善的注释：每个 CTE 上方用 `--` 写用途说明

2. **质量保证**
   - 使用小样本数据测试 SQL 正确性（取 1 个 token 跑全链路验证 join 条件）
   - 验证边缘情况：维表 join 无匹配时的 NULL 处理、分区为空时的返回
   - 每个 CSV 产出附带 `.meta.json`（行数、列数、空值率、SQL hash）供下游审计
   - 行数为 0 或用户标签命中率 < 95% 视为失败，不交付空文件

## SQL 能力要求

本 agent 的工作核心是 SQL，不是 Python。生成代码时必须熟练掌握以下要点（这些是 58 集团 hive/spark 集群的常见坑）：

### 集群/表结构特化知识

- **分区取数**：所有事实表先看 `dt`，默认 `dt='${outFileSuffix}'`（即 t-1）。漏写分区会扫全表，平台会拒绝执行。
- **datapool map 字段**：`hdp_zhuanzhuan_dw_global.dw_log_lego_action_1d` 的 `datapool` 是 `map<string,string>`，取值用 `datapool['key']`，不是 `.key`。
- **action 与 region**：首页 `actiontype in ('G1001','G1002','G1003','G1004')`、`region='g'`。仅当看 G1001 整体时才限定到 G1001。
- **pagetype 语义**：`zpmshow` 区域/元素曝光、`Areaexposure` 区域曝光、`explosureGoods` 商品曝光、`explosureItems` 组合元素曝光、`zpmclick` 点击、`AppStart`/`AppEnd` 启停、`LengthOfStay` 时长。
- **维表无 dt 分区**:`hdp_zhuanzhuan_dim_global.dim_zpm_page_info_full_1d_0p` 与 `dim_zpm_page_section_info_full_1d_0p` 名字带 `_1d_0p` 但**实际不带 dt 分区**,直接 `SELECT MAX(name) ... GROUP BY id` 去重,**不要加 `WHERE dt=...`**——加了反而查不到行。这是历史踩过的坑。
- **section_name 映射**：page 维表用 `page_id` 关联事件表 `actiontype`；section 维表 `link_id` 既可以是页面也可以是子页面，需要注意 join 条件。

### SQL 代码质量标准

- **模块化设计**：将复杂查询拆为小而专注的 CTE，每个 CTE 完成一个明确的转换步骤。CTE 命名清晰反映其职责（如 `user_sample_pool`、`exposure_with_page_name`）。
- **join 下推（2026-07-10 硬约束，口径已验）**：抽样 token 过滤必须**下推到 datapool 解析同层**——在扫大表 `dw_log_lego_action_1d` 的 CTE 里用 `LEFT SEMI JOIN data1 d ON ev.token=d.token` 与 `WHERE dt/pagetype` 同层过滤，让 `datapool['xxx']` 只对抽样存活行解析；**绝不能**先对全天全量行解析 datapool、再在外层 `inner join data1` 降采样（那样对约 339 倍的行做无用 map 解析）。末层再 `INNER JOIN data1` 取 user_source/user_type（同 token 集，不改行数）。经 2026-07-09 新旧对照实测：行数/token集/8模块UV·PV/访问时长总和**全部 0 误差**（口径未变）。**关于墙钟**：三条并发净墙钟均约 670s、彼此几乎相同，说明真瓶颈是全天分区扫描+shuffle+并发排队（三条共用），不是 datapool 解析——本优化省的是 CPU/内存与无用解析、并发忙时更稳，**不承诺墙钟提速**，勿据此写"实测提速"。data2-2/3-2/4-2 已固化为 `Scripts/data{2-2,3-2,4-2}_*_优化装配版.sql`，直接用、勿重拼。
- **datapool 字段裁剪**：只 SELECT 下游用到的字段。曝光/点击保留 sectionId/sortName/sortId/goodsList/indexList/tabName/tabNameList/eventduration/timestamp；已确认可裁 subSectionId/subSectionName/firsttab/infoid/sortIdList/tabId（报告与 exploration JSON 0 引用）。每裁一个少一遍全行 map 查找。
- **注释规范**：每个 CTE 上方用 `--` 写一行用途说明；关键字段的取值逻辑用行内注释标出。
- **列名英文 snake_case**，中文映射列加后缀 `_zh`（如 `section_name_zh`）。
- **类型安全**：`map<string,string>` 字段取值后注意类型转换；`hash(token)` 结果确认引擎兼容性（StarRocks 无此函数，必须走 Hive 引擎）。

### 性能优化

- **分区裁剪**：始终带 `dt` 分区过滤，这是 Hive/Spark 的第一道防线
- **小表广播**：data1（~1w 行）作为 build table，利用 mapjoin 优化
- **去重策略**：维表无 dt 分区时用 `MAX(name)...GROUP BY id` 而非 `ROW_NUMBER() OVER()`（更多引擎兼容）
- **CTE 复用**：data1 在 4 个查询中被重复 join，推荐合并为一条 SQL 用 CTE 复用

4. stdout 打 `[done] ... source=fresh` 或 `[done] ... source=fallback_from:X`；exit 1 时打 `[fail] ... 近14日无成功产物可兜底`。

### data6 — 近 28 天模块日度基线（软产物，喂 Step2 去周期异动判定）
1. 直接跑固化脚本：`python3 ~/.claude/skills/数据洞察agent_淑芬/Scripts/run_module_baseline.py ${dt}`（内部读 `Scripts/模块日度基线sql.sql`，从 `References/section-to-module.json` 生成 `${moduleCaseWhen}`、算窗口 `${startDt}=dt-28`/`${endDt}=dt`，走星河 **SparkSQL engine=2**——与 conv_aov 同引擎，SparkSQL 支持 `hash()/pmod()` 且解析 `CASE datapool['x'] WHEN..` 正常；engine=5 Hive 对 map下标+CASE 组合会 ParseException）。**不要即兴重写这段 SQL**。
2. 落地：`~/.claude/data_storage/淑芬/module_daily_baseline/module_daily_baseline_${dt}.csv`，列 `dt, page_id, module, exposure_uv, exposure_pv, click_uv, click_pv, uv_ctr`，覆盖逐页 home_overall + 11 模块 × 29 天（dt-28..dt，含 `page_id` 列）。**口径铁律**：每天在**当天范围内**对 token 去重（SQL 里 `GROUP BY dt`），**绝不跨天去重**——跨天去重得到的是"这段时期的去重人数"，不是日 UV；历史各天复用 **1/339 哈希桶**（`pmod(hash(token),339)=0`）与当天同口径。
3. **软产物（不阻断）**：这张表是异动判定的增强项、不是硬依赖。脚本内置容错：
   - 当天取数带 3 次重试（间隔 20s）。
   - 重试全失败 / 0 行 → 写一份 `meta.status=unavailable` + 空 CSV 占位，**退出码 0**（不阻断主流水线）。Step2 读不到基线就退回 D-1 单基线判异动并在报告标注"历史窗不可用"。
   - 正常成功 `meta.status=ok`。
4. stdout 打 `[done] module_daily_baseline_${dt}.csv rows=<N> days=<D> status=ok` 或失败时 `[warn] ... status=unavailable`（软失败，继续）。

## 取数编排：data1 先跑，其余并发提交（关键性能项）

> **优先直接跑固化脚本，不要即兴新建 `run_step1_<日期>.py`**：Step1 的两阶段编排（data1 阻塞 → data2-2/3-2/4-2/dau_full 并发）已固化为参数化脚本 [Scripts/run_step1.py](../Scripts/run_step1.py)：
> ```bash
> python3 ~/.claude/skills/数据洞察agent_淑芬/Scripts/run_step1.py --dt ${dt}          # 常规
> python3 ~/.claude/skills/数据洞察agent_淑芬/Scripts/run_step1.py --dt ${dt} --force  # 口径/SQL 变更当天强制重取
> ```
> 它内置了 data1 命中率校验、硬产物同 dt 幂等 `[skip]`、excel/csv 全量下载与预览截断防护。data5(conv_aov)、data6(baseline) 仍各自单独跑 `run_module_click_conv_aov.py` / `run_module_baseline.py`（引擎不同）。**历史上每天新建一个 `run_step1_<日期>.py` 快照的做法已废弃**——那些脚本逐字雷同只差 DT 常量，徒增 `Scripts/` 噪声、迁移体积虚高。dt 只是入参，别再复制脚本。下面的两阶段说明是这套编排的原理，供理解与排障，不是让你重写一份。

Step1 的 7 个产物有且只有一处依赖：**data1（用户抽样池）是上游，其余全部下游**。data2-2/data3-2/data4-2 都要 `inner join data1` 拿 token 子集与用户标签；data5(conv_aov)、data6(baseline) 各自独立成条；dau_full 无任何依赖。data2/3/4 之间、以及它们与 data5/data6/dau_full 之间**彼此无依赖**。

因此正确的编排是**两阶段**，不是 7 条串行排队：

1. **阶段 A（串行，阻塞）**：先跑 data1，落盘并通过命中率校验（user_source 命中率 ≥ 95%）后才进阶段 B。data1 没跑通不许往下——下游 join 会全空。
2. **阶段 B（并发提交）**：data1 就绪后，把其余 6 条**并发提交给星河**（data2-2 / data3-2 / data4-2 / dau_full / data5 conv_aov / data6 baseline），而不是一条跑完等结果再提下一条。星河侧各 execute_id 并行排队执行，本地只需并发发起 + 各自 `wait_and_get_result`。

**为什么这么排**：串行时 Step1 ≈ 各条耗时之和（实测 ~34 分）；两阶段并发后，Step1 ≈ data1 耗时 + max(其余 6 条耗时)，理论压到 ~12-15 分。这是 Step1 最大的一笔性能收益。

**实现要点**：
- 并发用线程池（`concurrent.futures.ThreadPoolExecutor`）分别提交，每个任务内部走 `client.run_sql(...)` 拿 execute_id 再 `wait_and_get_result`。星河 API 是每条独立 execute_id，天然支持并行排队。
- **失败隔离**：阶段 B 任一条失败按各自既有失败策略处理（硬产物 data2/3/4/dau_full 失败 → Step1 失败停；data5 走重试+近14日兜底；data6 软失败不阻断）。一条失败不影响其余已提交任务，收集完所有结果再判定 Step1 整体成败。
- **并发度**：6 条一次性提交即可，星河侧自行排队；无需人为限流，除非平台报并发配额拒绝，那时再降到 3-4 条一批。
- data6 baseline runner 自带**同 dt 幂等**：当天已有 `status=ok` 基线时 `run_module_baseline.py` 直接 `[skip]` 复用、不重扫 28 天窗（`--force` 可强制重跑）。所以重复触发 Step1 不会白扫历史窗。
- **硬产物同 dt 幂等（重跑省算，2026-07-15 新增）**：提交任一硬产物查询（data1/data2-2/data3-2/data4-2/dau_full）前，先检查 `~/.claude/data_storage/<该文件>_淑芬_${dt}.csv` 是否已存在**且** `.meta.json` 校验通过（`rows>0`；data1 再查 user_source 命中率 ≥95%）。通过则 `[skip]` 复用、不重跑；只对缺失或 meta 不达标的产物重取。这样流水线在 Step3/4/5 失败后重跑 Step1 时，不会把每条约 670s 的全天分区扫描整段重刷一遍，重跑只补缺口。**例外**：`--force`（或用户显式要求重取）时无视已有产物、全部重跑；口径/SQL 模板变更当天也应 `--force` 一次，避免复用旧口径产物。data5/data6 的幂等已由各自 runner 内置（见上条），本条覆盖 5 个硬产物。

### 备选：合并成一条 SQL（CTE）
若不走并发，退而求其次可把 data1 抽样作为 CTE 复用，整体一条 SQL 出 data2/3/4（或一条宽表），省掉 data1 重复扫描。但 data5/data6 因引擎不同（SparkSQL engine=2）无法并进这条 Hive SQL，仍独立跑。分析步骤要 4 张表分开消费时就分开落，方便审计。并发编排优先于合并 CTE——前者收益更大且不牺牲可审计性。

## 输出规范

- 编码：UTF-8 with BOM（防 Excel 打开乱码）。
- 列名英文 snake_case；中文映射列加后缀 `_zh`（如 `section_name_zh`）。
- 每个 CSV 同时写一个 `.meta.json`：行数、列数、空值率、生成 SQL 的 hash（SHA256）。
- 完成后 stdout 打一行 `[done] ~/.claude/data_storage/<file>.csv rows=<N>`（5 个硬产物各一行，含 dau_full；data5 再加一行带 `source=fresh` 或 `source=fallback_from:X`），方便编排器判断是否进入下一步。
- 禁止在输出中存储敏感信息（凭证、内网 IP、token 原文）。

## 错误处理与失败策略

### 通用错误处理原则

- **输入验证**：执行前验证 data1 抽样 SQL 是否正常返回、维表 join key 是否有 NULL。
- **数据清洗**：map 字段取值后检查空值率，异常偏高（>20%）时 warn 但不阻断。
- **优雅降级**：优先星河 → 超时 15 分钟切 One-Service → 仍失败则停。

### 常见问题及处置

| 问题 | 现象 | 处置 |
|---|---|---|
| 漏写分区 | 平台拒绝执行 / 超时 | 检查所有事实表是否带 `WHERE dt='...'` |
| map 字段取值为 NULL | 字段空值率异常 | 确认用 `['key']` 语法而非 `.key` |
| StarRocks 引擎不兼容 | `hash(varchar)` 报错 | 切 Hive 引擎 (engine=5) |
| 维表 join 无结果 | page_name/section_name 全 NULL | 检查 join key 是否匹配（page_id vs actiontype, section_id vs sectionId） |
| One-Service 任务 PENDING | 超 15 分钟无返回 | 取消任务，切到星河重试一次 |

### 失败处理

- SQL 报错：把报错原文 + 出错那段 SQL 写到 `data_storage/error_淑芬_${dt}.log`，退出码非 0。
- 行数为 0 / 用户标签命中率 < 95%：视为失败，不要把空文件交给下游。
- 严禁静默重试：每次失败必须写 log + stdout，等人工介入。

## 不要做的事

- 不要把所有 6 段 SQL 都跑一遍——`Scripts/` 里两份维表文件是 `CREATE TABLE` 建表语句，**只是结构参考**，不要执行。
- 不要扩大维度（比如加二级 tab、商品 id 详情），那是后续分析步骤的事。
- 不要修改 References；那是同步飞书文档的真源。
- 不要即兴重写 SQL 模板——`Scripts/` 下的 SQL 已经过业务验证，直接复用它生成的字段名、join 条件、过滤逻辑。改动 SQL 前先确认是否业务口径发生了变化。
- 不要在代码中硬编码凭证或内网地址——从环境变量读取，保持代码可安全提交到版本控制。

## 与其他 Agent 的协作上下文

本 agent 是流水线第 1 步，产物被下游 3 个 agent 直接消费。输出质量决定了整个流水线的数据基础：

- **数据分析 agent**：依赖 4 个 CSV 的字段完整性和 token 子集正确性；缺失字段或 token 不一致会导致分析结果不可信

- **洞察结论生成 agent**：依赖 dau_full CSV 做全量推广；缺失时会阻塞全量推广产出

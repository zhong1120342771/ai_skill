# 首页洞察-机会计算器（Step 5）

## 目的

第 4 步「洞察结论生成」已经给出了机会点清单（每条带现象、样本量级、全量量级、建议、待验证项）。但业务方真正要的是**"先做哪个"**——本 agent 把这些机会点量化成可比较的影响数，找出每个测算里最不确定、最致命的假设，再按"重要 × 紧急"两维排出 P0/P1/P2，让钟梦婷打开就知道本周该投哪个坑位。

本 agent 是流水线**最后一棒**，产物直接给业务方做决策，所以：
- **不重新算底层指标**——曝光 UV / 点击 UV / UV-CTR / 分层 χ² 都已经在 `exploration_淑芬_${dt}.json` 里算好，本 agent 只读取、组合、按公式推影响、排序。
- **不臆造数字**——每个影响测算的每个组成部分都必须标注来源：`data-backed`（来自 exploration JSON / dau_full）还是 `assumption`（估计）。assumption 越多，置信度越低。
- **一天数据不下因果结论**——优先级会受"待验证"条件影响；只有 1 天信号的机会，紧急度要相应打折，并在判定逻辑里写明需要几天序列 / A/B 才能定性。

## 价值口径（首页业务专用，必读）

通用的 opportunity-sizer 用美元金额（$）量化机会。本 agent 的**主价值口径是「增量点击 UV / 增量点击次数」**——首页是流量分发中枢，"让看到模块的人里多点一次"就是它最直接、最可信的价值代理。**在此基础上强制叠加「增量订单数 / 增量 GMV」折算**（见下「GMV 折算」），对齐业务方对单量与 GMV 提升的关注——业务方要求预估收益必须带单量与 GMV，`module_click_conv_aov` 由 Step1 保证产出（重试+近14日兜底），所以**每个提升型机会都要给出单量/GMV 折算，不再有"只给点击UV"的降级**（真正无乘数可用时 Step1 已失败停流水线，不会走到这里）。

### 主口径：增量点击（唯一必算）

沿用第 4 步报告正文已经给出的全量机会量（不要重算，直接引用或用同一公式核对）：

```
增量点击 UV（全量/日） = exposure_uv_sample × (uv_ctr_target − uv_ctr_actual) × ratio
```

- `exposure_uv_sample`：该模块样本曝光 UV，读 `exploration.modules[].exposure_uv`。
- `uv_ctr_actual`：该模块当前 UV-CTR，读 `exploration.modules[].uv_ctr`。
- `uv_ctr_target`：对齐目标 = **primary_page(G1001) 有曝光模块 UV-CTR 中位（剔除 capped venue_tab）**——capped 值是埋点修复占位，纳入会拉低中位、低估机会；首页无品类tab / 品牌墙曝光，实际参与中位的仍是原那批非 cap 模块集。目标值在第 4 步报告里已算出，直接复用；若报告没显式给，从 `exploration.modules[]`（primary_page G1001 的 11 模块）取有曝光模块的 uv_ctr、剔除 `exposure_capped` 非空的那个、对剩余取中位。
- `ratio`：`dau_full.uv / exploration.n_users`，读 `dau_full_淑芬_${dt}.csv` 与 `exploration.n_users`，**不许硬编码**。
- **比例口径（UV-CTR / 覆盖率）本身不乘 ratio**——它是样本与全量一致的比率，只有 UV/PV/点击次数这类绝对量才乘 ratio。

> 只对 `uv_ctr_actual < uv_ctr_target` 的模块算正向"提升机会"。已经高于中位的模块（如搜索框、金刚位）不是"待提升机会"，而是"守住基本盘"——它们进 P2「维持监控」，不参与增量点击的提升排序。

### GMV 折算（强制：读 `module_click_conv_aov` 的 data-backed 乘数，每个提升型机会必算单量/GMV）

GMV 折算需要两个乘数：「点击→净支付转化率」和「客单价」，都从 `module_click_conv_aov` 实测表取，**不允许自己拍**。

**读 `data_storage/淑芬/click_conv_aov/module_click_conv_aov_${dt}.csv`（Step1 保证产出，几乎总存在）。**
这张表按四页 × 10 核心模块给出「有点击 vs 无点击」用户的**净支付 PV 转化率（订单/用户）**与**客单价（pay_price 口径）**实测值，正是测算「单量提升 + GMV 提升」需要的乘数，且带因果对照（有点击组 vs 无点击组的差值）。CSV 含 `page_id` 列，**GMV 折算乘数取 page_id=G1001 的行**（主排页）。业务方主诉求是**策略上线后的单量与 GMV 增量**，所以本节按下面两条主线算：

```
增量订单数（全量/日，估算）= 增量点击 UV × Δ(PV转化率)
增量 GMV（全量/日，估算）   = 增量订单数 × 笔均客单价
```

- **Δ(PV转化率)（点击带来的净支付订单转化率增量）**：取该模块的 `pv_conv_rate_diff`（有点击 PV 转化率 − 无点击 PV 转化率）。PV 转化率分子是**订单数**，所以乘出来直接就是**增量订单数**，对齐业务方「单量提升」诉求。标 `data-backed`。
- **笔均客单价**：取该模块 `clicked_aov_per_order`（有点击组笔均净支付额，元，pay_price 口径）。乘增量订单数得增量 GMV。标 `data-backed`。人均口径 `clicked_aov_per_user` 仅作交叉校验，不用于按订单的 GMV 折算。
- **增量点击 UV**：沿用主口径（见上「主口径：增量点击」）算出的全量增量点击 UV。
- 模块名按 `section-to-module.json` 对齐（搜索框/场馆tab/品类tab/品牌墙/大促banner/金刚位/回收模块/新人条/栏目区/商卡feed流/feed轮播图），CSV 的 `module` 列与之一致，直接 join；join 时同时对齐 `page_id`（GMV 折算取 G1001 行）。
- **口径警示（必须在报告里写明）**：这是**当日单日的相关关系**，不是因果——有点击组转化率高，部分来自「高转化意愿用户本就更爱点」的选择偏差，不能全记到「引导点击」头上。所以单量/GMV 折算列**始终标 `MEDIUM` 上限置信度**，并注明「含选择偏差，需 A/B 校准点击的真实因果增量」。
- 场馆tab 受埋点 cap 影响（见下游 venue cap 说明），其折算带 ⚠，不进 P0。

**乘数时效（读 meta.source）**：Step1 取数当天失败时会用近 14 日兜底，`module_click_conv_aov_${dt}.csv.meta.json` 的 `source` 字段标明来源：
- `source=fresh` → 当日实测乘数，正常。
- `source=fallback_from:YYYY-MM-DD` → 当天星河没跑出，乘数取自该历史日。**报告与飞书消息的单量/GMV 折算处必须加一句「转化率/客单价乘数取自 ${源日期}（当日取数失败兜底），非当日实测」**，置信度仍 MEDIUM 不再额外降（模块转化率/客单价短期稳定，近14日兜底可接受）。

**无乘数可用的情形**：`module_click_conv_aov` 由 Step1 保证产出（重试+近14日兜底），正常流程里本 agent 总能读到。若真的读不到（近14日都无成功产物，Step1 本应已 exit 1 停在上游），本 agent 也**停下报错等人工，不硬编、不拍「3% 转化、200 元客单价」之类的数**。用户在当次对话显式另给转化率+客单价参数时才可用用户值（标 `assumption`，置信度降档）。

按下面顺序读：

1. **`final_report/首页洞察_淑芬_${dt}.md`** — 第 4 步报告。**机会点清单是本 agent 的主输入**：每条的现象、样本量级、全量量级、建议、待验证项，都在这里。本 agent 在它基础上做量化排序，不推翻它的结论。

3. **`analysis_reports/hypotheses_淑芬_${dt}.md`** — 每个机会点对应假设的类型（描述/相关/因果）、反向条件、原优先级。**因果/预测类假设的"待验证"直接决定本 agent 的紧急度打折**。
4. **`analysis_reports/quality_check_淑芬_${dt}.json`** — `warnings` 数组。受 warn 影响的机会点，置信度降档、报告条目带 ⚠。

6. **`data_storage/淑芬/click_conv_aov/module_click_conv_aov_${dt}.csv`**（必读）— 四页×11 模块「有点击 vs 无点击」净支付转化率与客单价（含 `page_id` 列）。**做单量/GMV 强制折算的 data-backed 乘数来源**（见上「GMV 折算」），GMV 折算取 page_id=G1001 的行；Step1 保证产出。读 `.meta.json` 的 `source` 判断是否兜底（fresh / fallback_from:X）。
7. **`analysis_reports/app_experience_opportunities_淑芬_${dt}.json`**（可选）— Step1.5 真人 App 体验机会点。**轨道 B 的排序数据源**：读 `opportunities[]`，配合 hypotheses 的「app体验机会点验证」小节，对 app 体验机会点单独排 P0/P1/P2（见下「第 7 步：app体验机会点排序（轨道 B）」）。缺失 / `status=skipped_no_change` / `status=unavailable` 时**跳过轨道 B**，报告轨道 B 保持 Step4 的占位句，飞书消息不加 `▍app体验机会点` 段。

## 工作流

### 第 1 步：抽取机会点，建影响模型

从第 4 步报告的「机会点清单」逐条提取机会，对每条建一个统一的影响模型。首页机会的核心公式（增量点击口径）：

```
影响 = 受影响用户(曝光 UV) × 提升幅度(uv_ctr_target − uv_ctr_actual) × 全量倍率(ratio)
```

把每个组成部分拆清楚、标来源：

| 组成部分 | 算什么 | 从哪取 | 来源标注 |
|---|---|---|---|
| 受影响用户 | 该模块曝光 UV（看到这个坑的人） | `exploration.modules[].exposure_uv` | data-backed |
| 提升幅度 | UV-CTR 距 primary_page 有曝光模块中位（剔 capped）的差（pp） | `uv_ctr_target − exploration.modules[].uv_ctr` | data-backed（目标=中位）/ 若用行业基准则 assumption |
| 全量倍率 | `dau_full.uv / n_users` | `dau_full.csv` ÷ `exploration.n_users` | data-backed |

**复合机会**：有的机会有多条价值通道，分别列、分别标置信度：
- 直接通道：本模块 UV-CTR 提升 → 增量点击（高置信，data-backed）。
- 分层通道：某分层（如 z0 新人）响应显著高 → 在该层强化入口的增量（中置信，依赖 χ² 显著 + 效应量）。
- 间接通道：点击→下游转化/GMV（低置信，需 assumption；默认不量化，只定性提示）。

间接通道一律标 LOW 并注明"需补充假设"。

### 第 2 步：算基准情形（base case）

对每个"提升型"机会（`uv_ctr_actual < uv_ctr_target`）：

1. 直接复用第 4 步报告正文已给的「日多产出点击 UV ≈ X 万次」（全量量级）。**先核对一遍**：用第 1 步公式重算，与报告数对得上（容差 ±2%，四舍五入差异）才用；对不上说明上游口径有出入，在报告里标注并以 exploration JSON 重算值为准。
2. 用多种单位表达，便于业务感知：
   - 增量点击 UV（全量/日）— 主指标
   - 折算到月 = 日值 × 30（若机会非时间受限）
   - 占该模块当前点击 UV 的比例 = 增量 / (click_uv × ratio) — 让业务知道是"翻倍"还是"+5%"
3. **提升幅度务必给区间，不要点估计**。默认三档目标：
   - 保守：对齐到 primary_page 有曝光模块 UV-CTR 的 25 分位
   - 基准：对齐到 primary_page 有曝光模块 UV-CTR 中位
   - 乐观：对齐到 primary_page 有曝光模块 UV-CTR 75 分位
   （分位数从 exploration 的 primary_page 有曝光、非 capped 模块 uv_ctr 现算。）

### 第 3 步：敏感性分析（找最致命的假设）

对每个机会，找出 1~2 个"低置信 × 高杠杆"的假设，测它们变动时影响怎么变。首页场景最常见的脆弱假设：

- **目标 UV-CTR 取值**：用中位 vs 25/75 分位，机会量级差多少？（杠杆通常很高）
- **抽样代表性**：`ratio` 落在 [330,350] 才健康；若 quality_check 标了 ratio 偏差 warn，全量量级要打问号。
- **单日 vs 趋势**：当前 UV-CTR 是当天值。若 D/D-1 异动大（如栏目区 -25.4%），说明 actual 本身在波动，base case 不稳。
- **分层效应量**：分层机会依赖 χ² 显著 + Cramér's V。V 偏小（如 <0.1）时，"分层差异可放大"这个假设是低置信的。

**单变量敏感性表**（每个关键假设一张）：

```markdown
### 敏感性：[假设名]
| 假设取值 | 增量点击 UV(全量/日) | vs 基准 |
|---|---:|---:|
| [保守: 25分位目标] | X | -Y% |
| **[基准: 中位目标]** | **X** | **base** |
| [乐观: 75分位目标] | X | +Y% |
```

**盈亏平衡（break-even）**：对每个机会找一个"做不做的临界点"，回答"什么条件下这个机会不值得做"：
- "只要该模块 UV-CTR 真实距中位 > N pp，提升就值得投。"
- "若 D/D-1 下行是趋势（非噪声），actual 还会继续掉，机会量级会变大；若是噪声，对齐空间被高估。"

### 第 4 步：情景分析（三档）

把每个机会的不确定假设捆成三个情景：

| 情景 | 假设组合 | 增量点击 UV(全量/日) |
|---|---|---:|
| 悲观 | 目标取 25 分位 + ratio 取偏差下限 | X |
| **基准** | 目标取中位 + ratio 实测值 | X |
| 乐观 | 目标取 75 分位 + ratio 上限 | X |

- 三档结论一致（都"值得做"或都"不值得"）→ 量化稳健，置信度可上调。
- 三档发散（基准值得、悲观不值得）→ 在判定逻辑里显式标"结论对假设敏感，建议先小成本验证再投入"。

### 第 5 步：优先级评分与 P0/P1/P2 分级

这是本 agent 的核心交付。**按「重要 × 紧急」两维定级，P0 在前。**

**重要度（影响 × 置信度）**：
```
重要度原始分 = 增量点击 UV(全量/日, 基准) × 置信度系数
置信度系数：HIGH=0.8 / MEDIUM=0.5 / LOW=0.3
```
置信度由数据质量、assumption 数量、敏感性稳健度、quality warn 共同决定（评定规则见下「置信度评定」）。

**紧急度**：综合三个信号，取最高档：
- 当前是否在恶化：D/D-1 或 7d 异动触发下行（如栏目区 -25.4%）→ 紧急度高（在掉，不救会继续掉）。
- 数据是否可信到能立刻动手：受 quality warn / 埋点 cap 影响、必须先修数据/埋点才能判读（如场馆tab）→ 紧急但**动作是"修数据"而非"改业务"**，单列。
- 是否需要长周期验证才能动：纯单日因果假设、需 A/B 才能定性 → 紧急度降档（先排期验证，不是本周直接改）。

**P0/P1/P2 判定矩阵**：

| 级别 | 判定条件 | 典型动作 |
|---|---|---|
| **P0** | 重要度高 **且** 紧急度高（量级大 + 正在恶化 / 或数据可信度受损需立即修复） | 本周必做：要么救下行、要么修埋点解锁判读 |
| **P1** | 重要度高、紧急度中（量级大但稳定，不在恶化，可规划） **或** 重要度中、紧急度高 | 本迭代规划：排期下钻 + 坑位实验 |
| **P2** | 重要度中低、紧急度低（量级小 / 置信度低需先验证 / 或已是高位基本盘只需维持） | 持续监控 / 长周期 A/B / 维持现状 |

**优先级评分（用于同级内排序）**：
```
优先级分 = 重要度原始分 × 紧急度系数
紧急度系数：高=1.0 / 中=0.6 / 低=0.3
```
同一级别内按优先级分从高到低排。投入（effort）若用户提供了工程量估计则纳入（分母），未提供则标 "TBD — 需工程评估"，不要自己拍 effort。

### 置信度评定（每个机会一档）

| 档位 | 系数 | 条件 |
|---|---|---|
| HIGH | 0.8 | 影响模型全部组成部分 data-backed；无 quality warn；敏感性三档结论一致；非纯单日因果（有多日/统计背书） |
| MEDIUM | 0.5 | ≤1 个关键假设；或 χ² 显著但效应量偏小；或敏感性三档量级差但结论方向一致 |
| LOW | 0.3 | ≥2 个关键变量是 assumption；或受 quality warn / 埋点 cap 直接影响；或敏感性三档结论发散（值不值得做都不定） |

> 通用规则：超过 3 个关键变量靠假设 → 置信度强制 LOW，建议从"立即投入"降级为"先验证"。

### 第 6 步：三角校验（出结论前强制，防误导性排序）

排好序后、写报告前，每个 P0/P1 机会过一遍合理性核对——避免把一个算错或被辛普森悖论误导的机会排到 P0：

- **分段优先**：这个机会的"提升空间"在分层上一致吗？会不会聚合看是机会、拆到 z0/z1-z3/z4-z5 某层反而已经很高？（用 `exploration.modules[].by_user_type` 核对。若某层已达标、只是另一层拖低，机会应改述为"针对 X 层"。）
- **内部一致**：增量点击 UV 重算值与第 4 步报告对得上吗（±2%）？比例没被错乘 ratio 吗？分层之和与整体对得上吗？
- **量级合理**：某个机会的增量点击 UV 是否 > 该模块当前全量点击 UV 的数倍？（>3 倍要警惕——多半是 actual 取值异常或 cap 没处理干净。）反之 < 当前点击的 1% 则机会太小，应进 P2。
- **分母/口径**：UV-CTR 的"下降"是真的转化变差，还是曝光 UV（分母）涨了？（结合 D/D-1 异动里的 exposure 与 click 分别看。）

任何一条 FAIL → 在该机会条目里显式标注，并据此下调置信度 / 调整级别；不要把存疑的机会硬留在 P0。

### 第 7 步：app体验机会点排序（轨道 B，两来源合并区分）

前 6 步排的是**数据侧机会点（`source=data_flow`）**，进结论层轨道 A。本步单独处理 **app 体验机会点（`source=app_experience`）**，进结论层轨道 B——**两轨道分开排序、分开成表，不混排**。这是修改4 的核心：真人体验结论与数据侧结论在文档里并列区分。

**触发条件**：`app_experience_opportunities_淑芬_${dt}.json` 存在且 `status=="ok"`。否则跳过本步，报告轨道 B 保持 Step4 占位句，飞书消息不加 app 段。

读该 JSON 的 `opportunities[]` + hypotheses「app体验机会点验证」小节的 APP-H{n} 结论，逐条按 `verifiable` 分两类定级：

1. **`verifiable==true`（有 `mapped_module`，能用首页 SQL 量化）**：
   - 走**与轨道 A 相同的增量点击 UV 公式**（`exposure_uv × (uv_ctr_target − uv_ctr_actual) × ratio`，模块指标从 exploration 取 `mapped_module` 那条），并同样用 `module_click_conv_aov` 强制折算单量/GMV。产出 `impact_incremental_click_uv_full` 等，标 `source=app_experience`。
   - 置信度**受真人侧 `evidence_strength` 与 `sample_caveat` 双重约束**：真人侧多为 4 轮模拟器小样本（方向性线索），即使数据侧 CONFIRMED，置信度上限也压在 **MEDIUM**（除非数据侧有独立的多日/χ² 强背书）；数据侧 REJECTED（打脸真人发现）→ 置信度 LOW 且 `decision_logic` 写明分歧。
   - 紧急度参考 wiki 优先级 + 数据侧是否在恶化。
2. **`verifiable==false`（`mapped_module=null`，商详/搜索结果/跨路径类）**：
   - **不量化**：`impact_incremental_click_uv_full` / `impact_incremental_orders_full` / `impact_gmv_full` 全部 `null`。
   - **优先级沿用 wiki 原级**（`wiki_priority`，不重新量化排序）——真人侧 P1 就落 P1。
   - `decision_logic` 写「真人体验证据强度=${evidence_strength}，SQL 无对应首页指标，收益待真人/埋点验证」。
   - `module` 记 `null`，`strategy` 用 wiki 的 `suggestion`。

**排序**：`source=app_experience` 的机会点**单独排一组** P0/P1/P2（可量化的按量化影响×紧急度定级，不可量化的按 wiki 原级），与 `data_flow` 组**互不干扰**。最终 `opportunities[]` 数组里两组都在，各自 `source` 标清，读取方（报告/飞书）按 source 分轨道取用。

**红线**：
- **不改 wiki 的优先级/证据强度，不臆造 app 机会点**——只搬运 + 对可量化的补量化。
- 不把 `verifiable=false` 的硬凑成可量化（首页埋点确实覆盖不到，硬造数据侧证据就是编数）。
- app 体验可量化机会点的置信度**不高于 MEDIUM**（真人小样本 caveat 决定），除非有数据侧独立强背书。

## 不要做的事

- **不要重算底层指标**——曝光/点击 UV、UV-CTR、χ²、ratio 都在上游产物里，本 agent 只读取与组合。
- **不要把比例指标乘 ratio**——UV-CTR 是比率，乘了就是把比例当次数，业务方一眼看出错。
- **不要硬编码 DAU / ratio**——读 `dau_full_淑芬_${dt}.csv`。
- **不要自己拍 GMV 折算参数**——乘数只来自 `module_click_conv_aov_${dt}.csv`（Step1 保证产出，重试+近14日兜底）的转化率增量+客单价。提升型机会强制算单量/GMV；真读不到（Step1 本应已 exit1 停在上游）就停下报错等人工，绝不凭空填"3% 转化、200 元客单价"。
- **不要给高位基本盘模块编"提升机会"**——搜索框、金刚位已高于中位，它们是 P2「维持」，不是待提升项；强行算"对齐到 75 分位还能涨"是过度量化。
- **不要无视 quality warn / 埋点 cap**——场馆tab 这类受埋点影响的，动作是"先修数据"，不能直接拿 capped 占位值排进业务提升机会的 P0。
- **不要把单日因果当定论**——D/D-1 单日异动只提示"在动"，方向定性要 7 日序列或 A/B；紧急度可因"在恶化"上调，但策略动作要写"先验证趋势"而非"直接改"。
- **不要另发第二条飞书**——本 agent 建一次文档、推一次 P2P，四要素结论就是那唯一一条，不打扰业务方两次。
- **不要把存疑机会硬留 P0**——三角校验 FAIL 的，降置信度、降级，并写明存疑点。

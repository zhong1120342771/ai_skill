# 首页洞察-洞察结论生成

## 基础与定位

本 agent 将两种专家能力合为一体，是流水线第 4 步（收口在 Step5 机会计算器）。产物先交给 Step5 回填优先级/收益、建文档并推送，本步不直接对业务方发布。

### 报告撰写能力

面向业务方产出报告，覆盖高管摘要、技术报告、商业智能报告，把复杂数据洞察转成清晰可操作的文档。工作按「理解分析 → 规划 → 撰写 → 自检」推进：先从 exploration JSON 与 summary.md 提炼洞察并按重要性排序（机会点 > 全景 > 模块 > 分层），再对照 References 10 问搭大纲，逐节落数字与配图，最后按下方「报告质量自检清单」核验。具体的报告三层结构、CTR 口径、样本→全量推广、场馆tab cap 处理、写作风格都在下面各正式小节里定义（以那些为准，本段不重复）。

### 数据可视化能力

出版级数据可视化，把复杂洞察转成一眼能读的图并配合叙事。图表选型对着 exploration 的数据类型走：分类比较用横向条形图、多变量关系用气泡散点、矩阵用热力图、趋势对比用双向条形、分组分布用多系列条形；每张图只讲一个结论，不过载。具体的 5 张基础图清单、SWD 一图一事配色/去杂/行动标题规则、中文字体设置都在下面「必产出的可视化」小节里定义（以那节为准，且一律调 `render_charts.py`，不即兴 matplotlib）。

### 核心约束

合在一起，在首页业务上盯准：**严格按 References 的 10 问输出报告 + 5 张基础图 + 1 个可选交互 dashboard**。本 agent 是流水线第 4 步（收口在 Step5），产物先交给 Step5 回填优先级/收益再发布，因此：不重新算指标（指标已经在 exploration JSON 算好）；必须把 quality_check 的 warn 显式带出；一天数据下不出因果结论，机会点必须带"待验证"项；**不建飞书文档、不推 IM**（那是 Step5 的事）。

## pp / % 单位口径（必读）

比率型指标（CTR、曝光渗透率、商详到达率、下单率、支付率、净支付转化率、留存率等本身就是百分比的指标）的同环比"绝对差"必须用 **pp（百分点）**，不能写成 %。例：转化率 1.086%→1.307%，写"+0.22pp"，不写"+0.22%"（后者会被读成相对涨千分之二，口径错误）。绝对量指标（DAU、单量、曝光 UV、点击 UV、GMV 等）的同环比用 **%**。

比率指标可在 pp 之外再补一个相对 %（如"+0.22pp（相对 +20%）"）帮助判断分量；非强制。注意小基数下相对 % 会放大观感，**报告以 pp 为主口径**，相对 % 只作辅助参考。

## CTR 口径（必读，定义见口径真源.md §一）

**唯一 CTR 口径 = UV-CTR**（`click_uv / exposure_uv`），业务读法"看到这个模块的人里有多少点了一下"——业务方说"首页 CTR"指的就是这个。**PV-CTR 已废弃**：报告/图表/schema 不出现 `pv_ctr` 字段或"PV-CTR"字样，旧报告迁移时删该列；`exposure_pv` / `click_pv` 仍采集作量级，但不算 PV-CTR。

**本 agent 就地要点**：机会点 gap 测算的"中位"分母 = **primary_page(G1001) 有曝光模块 UV-CTR 中位、剔除 capped venue_tab**，随天浮动、当日实算不硬编（首页无品类tab/品牌墙曝光，实际参与中位的仍是原那批非 cap 模块）。

## 场馆tab 曝光埋点 cap（必读）

场馆tab（section_id=106）是首页常驻 tab，**曝光 UV 理论上应 ≈ 首页曝光 UV**；现网 zpmshow 自动埋点对场馆tab 漏报严重（2026-06-14/15/16 三天比例稳定在 5–7%）。本 agent 的处理方式：

**判定**：Step 2 sub-agent 在写 `modules[]` 前先检查 `venue_tab.exposure_uv / home_overall.exposure_uv`，若 < 0.90 触发 cap（默认触发，差距太大才放心）。

**替代**：
- `venue_tab.exposure_uv` 改记为 `home_overall.exposure_uv`（全量首页曝光 UV，作为 UV-CTR 的分母）。
- `venue_tab.exposure_pv` / `click_pv` **保留原始值**（仅作量级展示；PV-CTR 已废弃故不存在"置 null"问题）。
- `venue_tab.uv_ctr` 用新分母重算 = `click_uv / home_overall.exposure_uv`。
- `by_user_type` 各档同样规则，分母换成对应分层的 `home_overall.by_user_type[layer].exposure_uv`。
- 新增 `exposure_capped` 字段记录原始值与触发原因（schema 见 [`../References/output-schemas.md`](../References/output-schemas.md) §一）。

**报告标注要求**：
1. §1.2.1 11 模块表中场馆tab 行：exposure_uv 列写 `8,514 (capped)`、备注列写"分母用首页曝光 UV（原始 section106 曝光 UV=590 仅占首页 6.93%，埋点漏报）"。表中**不再有 PV-CTR 列**；曝光 PV / 点击 PV 列照常显示场馆tab 自身的原始 PV 数，只是不参与 CTR 计算。
2. §1.3 分层差异表：UV-CTR 各层值用新分母重算后的（z0=4.51% / z1-z3=3.79% / z4-z5=3.91%）；spread 远比原始小。
3. 附录新增「埋点 cap 修复 changelog」段，贴 raw vs capped 对照表 + 工程修复 owner / 时间。
4. **报告正文必须显式标注（不只是 agent 内部判断）**：场馆tab 用首页 UV 作分母后，cap 后的读数默认可信、可以直接下业务结论——不用等 section106 曝光埋点修复完成再做判读。**报告正文对场馆tab 那一段必须写清两点**：① 分母改用首页曝光 UV（备注"原始 section106 曝光 UV 仅占首页 6.93%，埋点漏报"）；② 该读数默认可信、据此下业务结论、无需等待埋点修复。示范措辞：「场馆tab 曝光埋点漏报，本报告用首页曝光 UV 作分母重算其 UV-CTR；**该读数默认可信，据此下业务结论，无需等待 section106 埋点修复**（埋点修复列为附录工程待办）。」报告里照常给场馆tab 的覆盖、点击 UV、cap 后 UV-CTR 等业务结论。埋点修复仅作为一条工程待办列在附录 changelog（不阻塞业务结论），**不再把它当作"业务结论的前置条件"**。
5. 中位计算：表头说明写清中位口径 = **primary_page(G1001) 有曝光模块 UV-CTR 中位**；做 gap 测算的对齐目标用 **剔除 capped venue_tab 后的中位**，因为 capped 值是修复占位、不应纳入"对齐目标"分母——含 cap 会拉低中位、低估机会。首页无品类tab / 品牌墙曝光，实际参与中位的仍是原那批非 cap 模块。

不触发（比例 ≥ 0.90）时：不做修改，但报告附录仍记录"已检查未触发"以便审计。

## 样本 → 全量推广（必做）

业务方关心的不是 9k 抽样下的几十次点击差，而是这些信号反推到全量后到底是多少万次。所以报告**正文统一用全量推广量级，样本层数据放附录**：

- **正文（结论区 + 各模块章节）**：所有"个数类"绝对量（曝光/点击 UV·PV、点击次数、机会点覆盖人数、增量点击 UV）只呈现**全量推广值**（样本绝对量 × `ratio`），不再样本/全量双写。**比例/统计量**（UV-CTR/覆盖率/spread/χ²/jaccard）与样本/全量无关（分子分母同比放大后数值不变），正文直接用样本计算值、**不乘 ratio**。
- **附录（抽样与推广口径）**：保留样本层数据供追溯——样本规模 N=${n_users}（1/339 哈希桶）、当日 ratio 及其来源（dau_full_淑芬_${dt}.csv / dau_query.sql 实跑值）、关键指标样本原始绝对量。并写明：**正文全量量级 = 样本绝对量 × ratio；统计显著性（χ²/连续天数）在样本上验证，是全量数字的置信背书。** 正文干净用全量、可信度靠附录背书。

### 推广算法

```
ratio = dau_full.uv / exploration.n_users
exposure_uv_full = exposure_uv_sample × ratio
exposure_pv_full = exposure_pv_sample × ratio
click_uv_full    = click_uv_sample    × ratio
click_pv_full    = click_pv_sample    × ratio
uv_ctr_full      = uv_ctr_sample       # 保持（分子分母同比放大，比例不变，正文直接用）
gap_per_day_full = exposure_uv_sample × (uv_ctr_target − uv_ctr_actual) × ratio   # 唯一口径机会量
```

健康抽样 ratio 应在 [330, 350]（339 桶）。超出即在正文全量量级处加一句"⚠ 抽样代表性偏差，全量量级仅作量级感参考"，并在附录说明。

### 正文与策略建议一律只给全量量级（不并排样本数）

正文各模块结论与「策略建议」「机会点行动项」都只写推广到全量后的覆盖范围与量级（如"覆盖约 X 万 DAU""日多产出点击约 Y 万次"），**不要并排标注样本数字**（如"抽样 1400 次 → 全量 47 万次"那种双写）。业务方在正文只需要一个能直接对话的量级，两个数并列反而要他自己换算、容易读错。样本原始绝对量、N、抽样口径统一留在**附录**供溯源；统计可信度（χ²/连续天数）在样本上验证过，作为全量数字的背书写进附录即可。

## 报告结构（固定三层：结论 / 正文 / 附录）

报告从上到下**固定三层**，顺序硬约束。业务方点开先看结论层，想追数据看正文，要溯源翻附录。完整骨架见 [`../assets/report-template.md`](../assets/report-template.md)——按那份模板填充，每节占位符 `${...}` 都来自 `analysis_reports/exploration_淑芬_${dt}.json` 与 `data_storage/dau_full_淑芬_${dt}.csv`（字段定义见 [`../References/output-schemas.md`](../References/output-schemas.md) §一与§三）。**不要重写模板结构**；要调整章节，先改 assets 模板再来调用。

> **文档标题硬约束**：报告 md 的**首行 H1 必须写 `# 【${dt}】首页数据洞察日报`**（例：`# 【2026-06-30】首页数据洞察日报`）。飞书 docx v2 从 markdown 导入时，文档标题取正文首个 H1、会覆盖 `--title` 参数——首行 H1 若写别的（或缺失），飞书文档标题就会变成 `Untitled`。所以首行 H1 与 `feishu_publish.py` 的 `DOC_TITLE_FMT`（`【{dt}】首页数据洞察日报`）必须一字不差对齐，二者任何一处漏改都会让标题回退 Untitled。

### 第 0 块「核心机会汇总（置顶总表）」（整份文档最前面）

模板最前面有一张置顶总表，表头固定 `模块 | 机会 | 策略 | 优先级 | 收益`，是业务方点开文档看到的第一块内容。**本 agent（Step4）只留骨架 + 一句占位「优先级/收益由 Step5 回填」**，不自己填——因为优先级与收益要等 Step5 量化排序后统一回填（两轨道机会点合并进这一张表，按 P0→P1→P2）。保持模板里的骨架行原样即可，不要删这块、不要提前拍数。

### 第一层「结论」（最前，给业务方先看）

**结论层分两条并列轨道**（顺序硬约束：轨道 A 在前、轨道 B 在后），每条轨道各自成套「①机会点 ②策略建议 ③优先级 ④指标提升」四块。app 体验来的结论与数据侧结论**并列区分、不混排**——业务方一眼看清哪些是埋点数据挖出来的、哪些是真人体验挖出来的。

**轨道 A · 数据洞察机会点（常规 SQL 数据侧）**——现有四块，数据源=exploration/hypotheses/quality_check：

1. **机会点**：按优先级排，每条一句话现象 + 全量量级（绝对量 × ratio；UV-CTR/倍数直接用）。受 quality warn 影响的条目末尾 `⚠ 数据待复核`。
2. **对应的策略建议**：每个机会点配一条**具体**的产品功能/策略动作，不空泛。这份「机会点 → 策略建议」清单是下游 Step5 的主输入。
3. **优先级（P0/P1/P2）**：**本 agent 只留结论层骨架和位置（P0/P1/P2 表格空位），由下游 Step5「机会计算器」量化排序后追加/回填**（仅 `source=data_flow`），本 agent 不自己拍优先级。
4. **指标提升情况（点击 UV / 单量 / GMV 三个量）**：
   - **点击 UV**：增量点击 UV（绝对量，全量推广值 = 样本 ×ratio），主口径必给。
   - **单量**：如有下单/成交口径（`module_click_conv_aov` 或业务提供转化率）可折算则给全量量级，无参数则占位"待业务提供转化率参数"（由 Step5 有数据时回填）。
   - **GMV（铁律）**：**用户没提供转化率/客单价参数（或无 `module_click_conv_aov` 数据）时，不许硬编 GMV**——只给增量点击 UV，GMV 位填占位符 + 一句"GMV/单量折算待业务提供转化率与客单价参数"，绝不臆造数字。

**轨道 B · app体验机会点（真人 App 体验）**——数据源=`app_experience_opportunities_淑芬_${dt}.json` + hypotheses 的「app体验机会点验证」小节：

1. **机会点（真人体验）**：按 wiki 原优先级排，每条带 **wiki 优先级 + 证据强度（高/中高/中/低）+ round 证据 + 是否可量化（verifiable）**，并引 hypotheses APP-H{n} 的数据侧交叉验证结论。轨道开头统一说明一次全局 `sample_caveat`（真人侧多为小样本模拟器体验，方向性线索）。
2. **策略建议（真人体验）**：原样带出 wiki 的「建议方向」（`suggestion`，不改写）+ 可落地细化。
3. **优先级（P0/P1/P2·真人体验）**：留骨架，由 Step5 单独回填（与轨道 A 分开的表）——`verifiable=true` 按量化影响定级，`verifiable=false` 沿用 wiki 原优先级。

### 可视化设计原则

本流水线的图表遵循 **SWD（Storytelling with Data）一图一事**原则——每张图只讲一个结论，把无关元素全部弱化，只让"讲故事的那个数据点"跳出来。`render_charts.py` 已把这套风格固化（配色、去杂、高亮、行动标题都在脚本里），sub-agent 不需要也不应该即兴改样式；理解原则是为了在报告正文里给每张图配一句与图表行动标题一致的解读。

**核心原则（脚本已实现，理解即可）：**

- **一图一事**：一张图只承载一个判断。如果一张图不改变任何决策，就不该放进报告。单个关键数字宁可用加粗大字写进正文，也不画图。
- **灰化 + 单色高亮**：默认全灰（背景数据用浅灰 `#E5E7EB`），只给焦点上色——主高亮用 **Action Amber `#D97706`**（最该被关注的机会点），负向/下滑用 **Accent Red `#DC2626`**。一张图最多 2 种颜色（外加灰）。这样业务方一眼就知道该看哪。
- **行动标题（标题陈述要点，不是描述）**：标题写"大促banner 利用效率最低，是首页头号机会点"，而不是"11 模块 UV-CTR 排行"。前者告诉读者该怎么想，后者只说图是什么。脚本已按当日数据动态生成行动标题。
- **去杂**：去掉图表外框、上/右边框、冗余网格线、图例（改用数据上的直接标签）、数值已直接标注时去掉对应坐标轴刻度。背景统一暖米白 `#F7F6F2`。
- **色觉无障碍**：Action Amber 与 Accent Red 在红/绿色盲下仍可区分，且颜色始终配合直接标签做第二编码通道——绝不单靠颜色传达含义。

## 写作风格

本 agent 面向业务方产出，写作风格应以**商业智能报告**为基准（简洁、以业务为中心、行动导向），同时保留**技术报告**的数据精确性（每个结论带量级数字和统计依据）。

### 写作标准

- **像分析师写给业务方**，不是像 ChatGPT 写给所有人。少用"综上所述""总而言之"；多用具体数字。面向业务方的技术深度：将复杂的统计概念转化为业务语言，关注实际影响和建议。
- **每个结论都给量级**："金刚位 UV-CTR 39.35%，处于首页 11 模块中第 3"，而不是"金刚位表现一般"。数字是业务方判断的依据，形容词不是。
- **CTR 唯一写法 = "UV-CTR"**：旧报告里的"PV-CTR"已废弃，迁移时删除该列；新报告不要出现 `pv_ctr` 字段或"PV-CTR"字样。
- **机会点与建议正文只给全量量级**：正文各模块结论与「策略建议/行动项」都只写全量推广量级（绝对量 × ratio）与覆盖范围，不并排样本数，避免业务方换算混淆；比例/统计量（UV-CTR/χ²）与样本一致直接用。样本原始绝对量、N、χ²/连续天数背书统一放附录供溯源（见「样本 → 全量推广」§正文与策略建议一律只给全量量级）。
- **机会点要带"待验证"**：避免只看 1 天数据就下因果结论。引用 hypotheses_淑芬_${dt}.md 中的反向条件。
- **质量 warn 必须带出**：如果质量检查有软失败，对应模块的结论要标注「⚠ 数据质量待复核」。

### 准确性要求

- **统计准确性**：报告中所有数字必须在 exploration JSON 中有据可查。写进去的每一个 %、每一个 UV/PV 数都可以追溯到 exploration JSON 的具体字段。
- **逻辑一致性**：机会点的证据链条完整——"观察到的现象 → 量级 → 统计依据 → 与中位/历史的对比 → 假设 → 待验证条件"。
- **术语一致性**：全文对同一个概念使用同一个名称（如"金刚位"不要同时写成"icon 区""快捷入口"）。

## 不要做的事

- 不要重新算指标——指标已经在 exploration JSON 里算好了。本 agent 只读、组织、可视化、按 ratio 上推。
- **不要硬编码 DAU**（如 300 万 / 311 万都不行）——必须读 `data_storage/dau_full_淑芬_${dt}.csv`，缺了就先跑 SQL。
- **不要把 UV-CTR 也乘 ratio**——UV-CTR 是比例，样本与全量保持一致（分子分母同比放大）。乘了就是把比例当成了次数，业务方一眼能看出错。
- **不要再产出 PV-CTR**（`pv_ctr` 字段、"PV-CTR" 列、"PV 口径中位"备算章节都已废弃，理由见口径真源.md §一）。`exposure_pv` / `click_pv` 仍上报作量级，但不算 PV-CTR。
- 不要无视 quality_check 的 warn——下游的人会信报告，我们必须把不确定性显式写出来。
- 不要把所有 页面×模块×分层 的组合都堆到正文——挑显著的，其它放附录或交互式图。
- 不要在正文里贴长 SQL/代码——附录里给，或者放一行链接到 generated_code/。
- 不要用 3D 图表或过度装饰——3D 扭曲比例、装饰分散注意力，违反数据墨水比原则。

## 与其他 Agent 的协作上下文

本 agent 是流水线第 4 步，承接上游全部产物，产出业务报告 + 飞书文档，并把机会点清单交给第 5 步「机会计算器」做量化排序：

- **上游 — 代码生成 agent**：依赖 `dau_full_淑芬_${dt}.csv` 做全量推广（ratio 计算）；若文件缺失，需先补跑 `Scripts/dau_query.sql`
- **上游 — 数据分析 agent**：依赖 exploration JSON（指标溯源）、summary.md（报告叙事骨架）、hypotheses.md（机会点推理与待验证条件）
- **上游 — 质量检查 agent**：依赖 quality_check JSON 的 `warnings` 数组——每条 warn 必须在报告对应位置显式标 ⚠；`passed=false` 时本 agent 不应被调起
- **下游 — 机会计算器 agent（Step 5）**：本 agent 的「机会点清单」是 Step 5 的主输入，Step 5 在其基础上量化影响、排 P0/P1/P2 优先级。配合约定：
  1. **机会点要给全量量级**（曝光 UV、点击 UV、对齐中位的日增量点击），Step 5 直接复用核对，不必重算。
  2. **每个机会点必须配一条对应的产品功能 / 策略业务建议**（2.3）：不止说"X 模块利用效率低"，还要给出可落地的产品或运营动作，例如"大促banner 覆盖广但 CTR 倒一 → 建议做素材 A/B（动态 vs 静态）+ 按用户分层换不同活动主题"、"z0 新用户停留长但低位模块点得多 → 建议给 z0 单独配新人向的坑位排序"。建议要具体到「改什么功能 / 调什么策略」，不要停在"建议优化"这种空话。
  3. **机会点 + 配套业务建议一起交付给机会计算器**（2.4）：在报告里单列一个「机会点 → 业务建议」清单（每条含：模块、现象、全量量级、对应产品/策略建议、待验证条件），这份清单就是 Step 5 的主输入。Step 5 据此量化 impact、排优先级，并把产品/策略建议带进最终的优先级文档，不重写建议本身。
  4. **飞书由 Step5 收口，本 agent 不碰飞书**：因为最终飞书文档里的**优先级与优化后收益要由 Step5 回填**，文档必须在回填后才建，所以本 agent（Step4）**只出本地报告 md + 5 张图 + P2P 文本骨架，不建文档、不推 IM**。Step5 拿到报告后：回填结论层优先级/收益到报告 md → 调 `feishu_publish.py --skip-push` 建文档拿 doc_url → 把推送正文改写成「机会点+策略+优先级+优化后收益」四要素结论 + 文档链接 → `--skip-doc` 推一条 P2P。这样业务方一天只收到一条完整消息，且文档里带着完整优先级。

# 数据洞察agent_淑芬 使用说明书

转转 App 首页每日数据洞察的一条流水线。它每天把四页（G1001 首页 + G1002 奢品馆 + G1003 兴趣圈 + G1004 数码集）的 11 个核心模块的曝光、点击、利用效率跑一遍（首页为主，场馆页作结构参考），产出「机会点 + 策略建议 + 优先级 + 优化后收益」的结论，建成飞书文档推给业务方。这份说明书重点讲清楚一件事：这条流水线是由 6 个各管一段的子 agent 接力完成的，它们之间怎么交接、靠什么约束彼此。

## 一句话定位

`SKILL.md` 本身只是个**编排器**，不干具体活。真正的业务逻辑分散在 6 个子 agent 里，编排器只做三件事：按顺序启动子 agent、校验它落盘的产物、通过了才放行下一步。每个子 agent 跑在自己独立的上下文空间里，不占编排器的预算，也互相看不见对方的中间过程。它们唯一的沟通方式是**磁盘上的文件**。

触发词：「跑一下今天的首页洞察」「首页有没有机会点」「首页模块利用效率怎么样」「按淑芬的口径出一版」，以及每天 09:30 的定时任务。非首页主题（商详、搜索结果、转化漏斗）不走这条线。

## 流水线全景

```
dt (默认 t-1)
   │
   ▼
[Step 1] 代码生成 ──────► 5 个 CSV + dau_full（硬产物）
   │                      + module_click_conv_aov（软产物）
   ├──────────────┐
   ▼              ▼
[Step 1.5]      [Step 2] 数据分析 ──► exploration.json + summary.md
 app体验机会点     │                    + hypotheses.md
 （读飞书wiki，    │
  软产物，        ▼
  不阻断）      [Step 3] 质量检查 ──► quality_check.json【闸口】
   │              │                   passed=true 且 hard_failures 空才放行
   │              ▼
   └──────────► [Step 4] 洞察结论生成 ──► 报告 md（优先级/收益留空位）
                  │                       + 5 张图 + P2P 文本骨架
                  │                       （不建文档、不推送）
                  ▼
                [Step 5] 机会计算器 ──► 回填优先级+收益 → 建飞书文档
                                        → 改写四要素消息 → 推一条 P2P
```

关键约束：**严格串行**，前一步产物落盘校验通过，才启动下一步；任一步失败就停在原地等人工，不静默重试、不跳过。

## 核心设计：为什么拆成 6 个隔离子 agent

一件复杂的分析，如果塞进一个 agent 从头做到尾，上下文会越滚越长，前面取的数、中间的假设、后面的结论全挤在一起，容易串味、也容易超预算。淑芬把它切成 6 段，每段一个独立子 agent：

- **上下文隔离**：每个子 agent 的输入就是它要读的那几个文件，产出就是它要写的那几个文件。它不需要知道上一步是怎么算出来的，只认磁盘上的产物。编排器的主上下文因此始终干净，只存路径和校验状态。
- **产物即契约**：agent 之间不直接对话，全靠文件交接。文件长什么样由 `References/output-schemas.md` 的 JSON schema 钉死，谁也不能随手改字段名。
- **失败即停**：每一步都有明确的产物校验，尤其 Step 3 是硬闸口。数据不可信就不往下走，不会让脏数据一路污染到业务方的文档里。
- **子 agent 类型固定 general-purpose**：6 步全部用 `Agent` 工具启动，`subagent_type` 一律传 `general-purpose`，prompt 就是「Read 你的 agent 定义文件并严格执行」。业务逻辑全在 .md 文件里，不依赖任何专用 agent 预设。

## 子 agent 之间怎么配合（重点）

这条链的关键在交接。下面按数据怎么一步步长大来讲。

### 交接靠三样东西

1. **落盘产物**：上一步写文件，下一步读文件。目录统一在 `~/.claude/` 下（`data_storage/`、`analysis_reports/`、`visualizations/${dt}/`、`final_report/`）。
2. **JSON schema 契约**：机器读的产物（exploration / quality_check / opportunity_priority / app_experience）字段名和结构由 `References/output-schemas.md` 规定，上下游按同一份 schema 读写，不各写各的。
3. **业务规则真源**：口径定义（10 个业务问题、四页/11 模块切分、用户分层、CTR 口径）放在 `References/`，与飞书文档同步。多个子 agent 都读它，保证大家用的是同一套定义。改口径的顺序是：飞书文档先改 → References 同步 → 再改子 agent 实现。

### 数据在链上怎么长大

**Step 1 代码生成** 是地基。它按 `Scripts/` 下已经过业务验证的 SQL 模板取数，落 5 个硬产物（data1 用户抽样池、data2-2 曝光、data3-2 点击、data4-2 页面时长、dau_full 全量 DAU）。data1 是个约 9000 人的 1/339 哈希抽样池，后面三张表都靠 inner join data1 的 token 把范围压下来，避免全表扫描。dau_full 是全量 DAU，是后面把抽样数字放大到全量的分母，绝不能硬编码。它还顺手跑一个保证产出 `module_click_conv_aov`（四页 × 11 模块有点击 vs 无点击用户的净支付转化率和客单价，含 page_id 列），专门喂给 Step 5 做 GMV 折算（主排页取 G1001）。这个跑失败只 warn，不拖累主流程。

**Step 2 数据分析** 接过 4 个 CSV，把它们切成「四页 × 11 模块 × 3 档用户分层」的指标矩阵，算 UV-CTR、覆盖率、分层差异、feed 深度这些，并产出四页对比的 `pages[]` 块。它做两件下游依赖的关键事：一是对异动模块做「剥洋葱」根因下钻（确认是不是数据假象 → 分解到哪个分层/坑位 → 隔离责任方），把「X 模块跌了」收窄成「X 模块跌 25%，68% 由 z0 新增用户稀释」这种能直接派活的结论；二是按业务 10 问生成候选假设，每条都带证据、反向条件和优先级。产出三份：机器读的 `exploration.json`（指标长表）、人读的 `summary.md`（一页纸摘要）、`hypotheses.md`（假设清单）。**它只到「数据 + 假设」为止**：不画图、不下因果结论、不给优化建议，那些是下游的事。

**Step 3 质量检查** 是全链唯一的硬闸口，只判定、不修复。它复算 CTR 一致性、校验 token 是 data1 子集、检查 11 模块与四页覆盖是否齐全，这是数据层。更关键的是结论层校验：辛普森悖论（整体涨但分层全跌）、分母漂移、相关当成因果、多重比较假阳性。命中就写进 `quality_check.json` 的 warnings 或 soft_failures。**铁律是 `passed = (hard_failures 为空)`**：硬失败非空就停，编排器不进 Step 4。结论层的 warn 不阻断，但会一路传下去，让 Step 4 在报告里标 ⚠、让 Step 5 把对应机会的置信度压到 MEDIUM/LOW。

**Step 4 洞察结论生成** 是把数据翻译成人话的一棒。它读齐上游全部产物，按固定三层结构写报告：第一层结论（机会点 → 策略 → 优先级位 → 指标提升）、第二层正文（框架图 → 整体 → 模块 → 分层 → 坑位下钻）、第三层附录（原始样本 → 抽样质量 → 数据源）。它做两个重要动作：一是**样本→全量推广**，把抽样的绝对量（曝光/点击 UV、次数）乘 ratio（= dau_full.uv / n_users）放大到全量，正文只给全量量级，样本数放附录；比例类指标（UV-CTR、覆盖率）不乘 ratio。二是给每个机会点配一条具体的策略建议，这份「机会点 → 策略」清单就是 Step 5 的主输入。它还调 `render_charts.py` 出 5 张图。**注意它不建飞书文档、不推送**：因为最终文档里的优先级和收益要等 Step 5 回填，所以结论层里「优先级」「优化后收益」两块留空位，只出本地报告 md + 5 张图 + 一个 P2P 文本骨架，把飞书那一整段交给 Step 5。

**Step 5 机会计算器** 是收口的最后一棒。它不重算任何底层指标，只做量化排序：把每个机会点按「增量点击 UV = 曝光 UV × (目标 UV-CTR − 当前) × ratio」算出全量影响，做敏感性分析（目标取中位/25分位/75分位差多少），按「重要 × 紧急」排出 P0/P1/P2。如果 Step 1 的 `module_click_conv_aov` 表在，就叠加 GMV 折算（增量订单 = 增量点击 UV × 转化率差；增量 GMV = 增量订单 × 笔均客单价），这条链对应业务方最在意的单量和 GMV 提升。但因为是单日相关、含选择偏差，置信度上限锁死 MEDIUM。排完序后它回填 Step 4 报告的空位（置顶核心汇总表 + 结论层优先级和收益），渲染汇总表配图，再按顺序建飞书文档拿链接、把消息改写成四要素结论、推一条 P2P 给钟梦婷。

### 两条并列轨道：数据侧 × 真人体验侧

除了主链，还有一个软分支 **Step 1.5 app体验机会点**。它跟主链并行，只读一份飞书 wiki（真人在 App 里跑体验产出的机会点报告），把里面已有的机会点原样搬进来，不跑真机、不臆造。它用 wiki 的 revision_id 去重：wiki 没更新就跳过，平日近零开销。

这一路机会点会跟数据侧**分两条轨道并列走完全程**，不混排：

- Step 2 对能映射到首页模块的（`verifiable=true`）用 SQL 指标做交叉验证，写进 hypotheses 的独立小节；映射不到的（商详、搜索结果页这类首页埋点覆盖不到的）保留定性。
- Step 4 报告结论层分**轨道 A（数据洞察）**和**轨道 B（app 体验）**，各一套机会点/策略/优先级/收益。
- Step 5 两轨道分开排序，可量化的走增量点击 UV 公式，不可量化的沿用 wiki 原优先级、标「待真人/埋点验证，无法量化收益」。app 体验可量化机会点的置信度也封顶 MEDIUM，因为真人侧多是小样本模拟器体验，只能算方向性线索。

这样业务方一眼能分清：哪些机会是埋点数据挖出来的，哪些是真人体验发现的。

## 支撑资产：真源与固化脚本

子 agent 不各自造轮子，公共能力沉在两个目录里：

**References/（真源，人读 + 机读契约）**
- `代码生成要求和说明.md` / `分析要求和说明.md`：业务规则真源，跟飞书文档同步。
- `output-schemas.md`：exploration / quality_check / feishu_doc / opportunity_priority / app_experience 的 JSON schema。上下游按同一份读写。
- `section-to-module.json`：11 模块切分常量 + 四页范围配置（pages/primary_page/strip/cap），子 agent 直接当字典用，不重新推断 section_id。

**Scripts/（SQL 模板 + 固化 Python）**
- 6 份事件 SQL 模板 + 维表映射 + `dau_query.sql`：Step 1 直接复用，不重写。
- `qa_check.py`：Step 3 的数据层闸口，阈值集中在脚本里。
- `render_charts.py`：Step 4 出 5 张图、Step 5 出汇总表配图，SWD 一图一事风格固化在里面。
- `feishu_publish.py`：Step 5 建文档 + 推送，`--skip-push` 只建文档、`--skip-doc` 只推送。
- `模块点击转化客单价sql.sql` + `run_module_click_conv_aov.py`：Step 1 的软产物 data5，喂 Step 5 的 GMV 折算。

红线：子 agent 要画图/跑 QA/发飞书，直接调这些脚本，不即兴写 Python。这些脚本是产物契约的一部分。

## 失败处理与闸口

- 前一步是后一步的硬依赖，产物缺失或 agent 报错，编排器打出失败步骤和缺失路径，停在那里等人工。
- **Step 3 是硬闸口**：`quality_check.json` 的 `passed=false` 或 `hard_failures` 非空，必须停，不进 Step 4。
- **Step 4 只出本地产物**：报告 md 或 5 张图任一缺失就算失败，停在 Step 4。
- **Step 5 收口飞书**：先回填报告 md，再 `--skip-push` 建文档，建失败就停、不回退发本地路径；文档建好但推送失败，只用 `--skip-doc` 复用已有链接重推，不重建文档。
- **软产物不阻断**：Step 1.5（app 体验）和 Step 1 的 conv_aov 表读不到/跑失败都只 warn，主流程照常走，下游按占位处理。

## 关键红线速查

- 凭证只走环境变量（星河、One-Service）和 `lark-cli config`（飞书 appSecret），脚本/SQL/日志一律不写明文。
- 飞书当前只推钟梦婷一人 P2P（open_id `ou_5e572adca6deef8ef21c3b18dfade573`），纯文本、不推群；董亚坤已暂停，等明确放开再恢复双推。文档默认仅创建者可见。
- DAU 必须当日实跑 `dau_query.sql`，不能硬编「300 万」这种常识值，大促低谷能浮动 20%+。
- CTR 唯一口径 = UV-CTR（看到模块的人里有多少点了），PV-CTR 已废弃，schema/报告/图表都不再出现。
- 场馆tab（section_id=106）曝光埋点漏报严重，曝光 UV / 首页曝光 UV < 90% 就触发 cap，用首页曝光 UV 顶替分母重算 UV-CTR，报告显式标注。
- 正文只给全量推广量级（绝对量 × ratio），样本原始量放附录；比例/统计量不乘 ratio。
- 无转化率/客单价数据时，GMV/单量只占位、不硬编。
- app 体验机会点只搬运 wiki 结论，不改优先级、不改证据强度、不臆造。

## 外部依赖与迁移打包

这条流水线跑起来，除了 skill 目录本身，还要用到几样本机上的东西。把 skill 拷到别的电脑，光复制目录不够，得把这些一起备齐。

| 依赖 | 位置 | 作用 | 能否随包带走 |
|---|---|---|---|
| `xinghe-data` skill | `~/.claude/skills/xinghe-data/` | 主取数通道（星河）。`run_step1.py`、`run_module_click_conv_aov.py` 硬引用 `xinghe_client` | 能，已进包 |
| `oneservice_cli.py` | `~/.claude/scripts/`（全局小写目录） | 兜底取数 + dau_query 执行 | 能，已进包 |
| `humanizer` skill | `~/.claude/skills/humanizer/` | 对外产出去 AI 味的全局强制规范 | 能，已进包 |
| `lark-cli` | `/opt/homebrew/bin/lark-cli`（v1.0.43） | 建飞书文档 + P2P 推送 | 装不进包，目标机 brew 单独装 |
| 环境变量凭证 | `~/.zshrc` | 星河 / One-Service 认证 | 不进包，目标机自己 export |

前三个依赖已经按 `~/.claude` 的相对结构备份进 skill 的 `_bundled_deps/` 目录，随压缩包一起走。目标机解压后：

```bash
cd 数据洞察agent_淑芬/_bundled_deps
bash install_deps.sh          # 把 3 个依赖还原到 ~/.claude 规范位置，幂等
```

脚本把依赖还原到规范位（而非就地引用），是因为 `run_step1.py` 里的路径硬编码成 `~/.claude/skills/xinghe-data`，放回规范位才不用改代码。装 lark-cli、配环境变量、`pip3 install requests` 这三件包里带不了的事，`_bundled_deps/README_迁移部署.md` 有完整步骤和部署自查清单。

打包这个 skill 时用 Python `zipfile` 并强制 UTF-8 文件名标志（`flag_bits |= 0x800`），不要用 macOS 自带的 `zip` 或 `ditto`——它们不给中文文件名置 UTF-8 flag，换到别的系统解压会出现乱码目录名。

## 手动跑一次

```
跑一下今天的首页洞察
# 或指定日期
跑 2026-06-29 的首页洞察
```

编排器会从 Step 1 依次调度到 Step 5，中间任一步失败会停下报告。跑完业务方收到一条 P2P，包含四要素结论（机会点 + 策略 + 优先级 + 优化后收益）、汇总表配图和完整文档链接。

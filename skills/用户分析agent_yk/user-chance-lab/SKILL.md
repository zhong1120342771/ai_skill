# user-chance-lab

## 定位

`user-chance-lab` 是 `user-chance` 的批量实验组织 Skill。它负责设计多轮实验、生成每轮任务卡、推动连续执行、维护轻量实验清单，并基于多轮报告输出聚合体验结论和机会点。

它不直接替代 `user-chance` 操作 App。正式实验每一轮都必须由 `user-chance` 真实运行 App，不能用纯对话、想象路径或静态分析替代。

```text
user-chance = 单轮模拟用户
user-chance-lab = 批量实验负责人
```

## 默认能力

| 项 | 默认 |
|---|---|
| 默认 App | 转转，除非少爷指定其他 App |
| 默认有效样本数 | 5 轮，可由少爷调整 |
| 最大尝试次数 | 有效样本数 + 3；默认 8 次 |
| 每轮执行 | 必须真实跑 App |
| 失败处理 | 工具 / 样本 / 模式失败自动补跑 |
| 第一版重点 | 多角色、多任务批量体验 |
| 主交付 | 聚合机会点报告 |

不要把 `user-chance-lab` 做成后端 Runner、数据库、复杂状态机或平台 UI。第一版在 Codex 当前对话内串行推进，用本地 Markdown 文件做轻量记录。

## 文件分工

按需读取，不要一次性加载全部引用。

| 文件 | 负责 | 何时读取 |
|---|---|---|
| `references/experiment-design.md` | 目标约束槽位解析、角色生成、多任务设计 | 设计批量实验计划、分配角色或任务 |
| `references/lab-workflow.md` | 连续执行、失败补跑、轻量清单、单轮任务卡 | 真正启动批量实验 |
| `references/aggregation-report.md` | 多轮报告聚合、机会点分级、竞品 / 路径对比 | 生成最终汇总报告 |
| `templates/batch_plan.md` | 批量实验计划模板 | 输出待确认计划 |
| `templates/lab_run_manifest.md` | 批量实验清单模板 | 记录轮次、报告路径和纳入状态 |
| `templates/lab_report.md` | 聚合报告模板 | 输出最终报告 |
| `scripts/check_skill_contract.sh` | Skill 契约校验 | 新建或修改本 Skill 后 |

运行真实 App 前，必须同时使用 `user-chance` Skill，并按 `user-chance` 要求读取它的 `SKILL.md` 和必要引用。

## 输入方式

少爷可以自然语言输入，不要要求少爷手写内部字段。

示例：

```text
用 user-chance-lab 批量跑转转 App：
目标是观察用户找备用机的体验问题。
默认 5 轮，可以自动分配不同角色和任务。
失败自动补跑。
最后输出聚合机会点报告。
```

可选信息：

| 输入 | 说明 |
|---|---|
| App / 竞品 App | 转转、闲鱼、京东等 |
| 实验目标 | 想研究什么体验问题 |
| 角色范围 | 新用户、老用户、价格敏感、风险敏感等 |
| 任务范围 | 单任务、多任务、指定路径或竞品对比 |
| 有效样本数 | 默认 5，可调整 |
| 最大尝试次数 | 默认有效样本数 + 3 |
| 禁止边界 | 下单、支付、客服、资料修改等 |
| 报告意图 | 机会点、体验报告、竞品调研 |

## 核心原则

- 先设计实验，再跑 App；超过 3 轮的批量实验，默认先给少爷确认批量计划。
- 角色分配只定义用户差异，不预设入口、路径或替代方向。
- 入口、浏览深度、升级 / 降级、横向替代，由每轮 `user-chance` 根据角色、目标、页面和用户状态动态推导。
- 每轮必须生成 `user-chance` 可直接执行的自然语言任务卡，不把 lab 私有字段丢给 `user-chance`。
- 失败补跑只补工具失败、样本无效、模式无效或报告契约失败；用户真实找不到、犹豫、放弃，通常是有效体验结果。
- 最终聚合只纳入有效样本；被剔除样本可作为工具风险或样本限制记录，不能当作产品体验强结论。
- 样本有效性和证据强度分开判断：一轮可以是 `valid`，但某些结论仍需要标注截图可见、XML 可见、XML 屏外或推断限制。
- 聚合时不得把 XML 屏外内容、历史残留页面、坐标误点或工具读到的信息写成“用户已看到/已理解”。
- 每轮一旦已有候选、关键证据和用户状态，必须先收口写 `report.md`，不能为了“更充分”无限继续操作 App。
- subagent 长时间静默时，主线程应先要求状态回报；若已有足够证据，应切到收口报告而不是继续等待或继续点击。
- 如果前一个执行者只留下证据没有报告，新的执行者可以基于既有真实证据接手收口；证据不足时才补跑。
- 接手任务如果已经明确“接手 / 收口 / 读取现有目录”，执行者不要再输出确认计划，应直接读取证据、写报告和更新清单。

## 标准流程

1. **理解实验目标**：确认 App、目标、边界、轮数、报告意图和是否指定路径 / 竞品。
2. **读取实验设计引用**：加载 `references/experiment-design.md`。
3. **目标约束槽位解析**：拆解目标对象、使用场景、商品参数、商品状态、风险保障、价格价值、时效履约、决策产出。
4. **生成批量计划**：默认设计 5 个有效样本；少爷可调整轮数、角色或任务。
5. **展示待确认计划**：除非少爷明确要求直接执行，否则先确认。
6. **读取执行引用**：加载 `references/lab-workflow.md`。
7. **创建实验目录和清单**：使用 `lab_run_manifest.md` 记录轮次、任务卡、报告路径、纳入状态。
8. **逐轮调用 `user-chance`**：每轮用自然语言任务卡真实跑 App 并导出单轮报告。
9. **单轮收口**：若已形成候选、关键证据和用户状态，先写 `report.md`；不要继续无限探索。
10. **标注证据 caveat**：区分截图可见、XML 可见、XML 屏外、推断和工具噪声。
11. **校验单轮结果**：判断是否有效、是否需要补跑或只重写报告。
12. **自动补跑**：直到达到目标有效样本数，或达到最大尝试次数。
13. **读取聚合引用**：加载 `references/aggregation-report.md`。
14. **生成聚合报告**：输出高频体验问题、机会点、证据索引、样本限制和后续建议。

## 每轮任务卡契约

给 `user-chance` 的每轮任务卡必须是自然语言，并至少包含：

| 字段 | 要求 |
|---|---|
| 轮次信息 | `lab_run_id`、第几轮、尝试次数 |
| App | 要体验的 App，默认转转 |
| 用户角色 | 能驱动行为，不只是标签 |
| 任务目标 | 用户要完成或判断什么 |
| 禁止边界 | 不下单、不支付、不联系客服等 |
| 行为倾向 | 价格 / 风险权重、平台 / 品类熟悉度、初始耐心 |
| 判断标准 | 性价比、风险、保障、状态、时效等如何影响判断 |
| 目标可变空间 | 哪些参数可比较，哪些不能擅自改变 |
| 报告要求 | 本轮后续用于批量聚合，需输出样本有效性和结构化摘要 |

`user-chance-lab` 可以内部使用结构化槽位，但交给 `user-chance` 时必须翻译成人话。

## 有效样本与补跑

样本有效性分三档：

| 档位 | 含义 | 聚合处理 |
|---|---|---|
| `valid` | 真实执行、模式匹配、关键证据足以支撑用户状态 | 可作为完整有效样本纳入 |
| `partial_valid` | 真实执行但覆盖不完整，例如未进详情、未看关键报告、路径只覆盖入口 / 列表 | 只能作为方向信号，不能和 `valid` 同权重 |
| `invalid` | 工具阻断、样本污染、模式错配或证据不足 | 不纳入产品体验结论，按规则补跑 |

`valid` 只代表这轮样本整体可用，不代表每个体验结论都是高强度证据。若某个细项依赖 XML 屏外、页面历史残留、误点路径或 Agent 推断，必须在 `lab_run_manifest.md` 和 `lab_report.md` 标注 caveat，并在聚合时降权。

目标有效样本数默认要求 `valid`。如果用 `partial_valid` 抵扣有效样本，必须在 `lab_run_manifest.md` 和 `lab_report.md` 明确降权，并说明为什么没有补跑。

需要补跑：

| 情况 | 处理 |
|---|---|
| ADB / MCP / 模拟器 / App 启动失败导致无法观察 | 补跑 |
| 工具失败明显改变路径或结论 | 补跑 |
| 起点污染严重且无法校正 | 补跑 |
| 指定路径模式跑成自由探索 | 补跑 |
| 报告缺少关键契约且证据无法支撑 | 补跑或重跑 |

不默认补跑：

| 情况 | 处理 |
|---|---|
| 用户真实找不到目标 | 纳入体验结果 |
| 用户真实看不懂、犹豫、放弃 | 纳入体验结果 |
| 安全边界附近停止但已有有效体验证据 | 可纳入，报告中说明边界影响 |
| 报告写法不合格但证据完整 | 优先重写报告，不重跑 App |

## 聚合报告

最终报告不要堆单轮流水账。它应该回答：

- 这批用户整体遇到了什么体验问题？
- 哪些问题跨角色 / 跨任务重复出现？
- 哪些只是单轮线索？
- 哪些机会点最值得产品推进？
- 哪些结论受工具、样本、起点或路径限制影响？
- 哪些结论有截图可见证据，哪些只是 XML/推断辅助？
- 每个结论对应哪些轮次和证据？

## 与其他能力的边界

| 能力 | 边界 |
|---|---|
| `user-chance` | 单轮真实 App 执行和单轮体验报告 |
| `user-chance-lab` | 批量设计、任务卡生成、清单维护、补跑判断、聚合报告 |
| subagent | 第一版只建议用于报告外审或聚合复核，不并发控制同一设备 |
| Claude CLI / 外部审核 | 仅在少爷要求交叉审核时使用 |
| 本地脚本 | 只做契约校验或模板辅助，不承担 App 操作 |

# Lab Workflow

本文档用于 `user-chance-lab` 在 Codex 当前对话里连续推进批量真实 App 实验。

## 执行原则

- 每轮都必须真实跑 App。
- 第一版串行执行，不并发控制同一台设备或模拟器。
- 失败自动补跑，但不无限重试。
- 用 `lab_run_manifest.md` 做轻量实验清单，不做复杂状态机。
- 最终聚合只使用有效样本。

## 目录建议

默认在当前工作区建立本次实验目录：

```text
user-chance-lab-runs/<lab_run_id>/
├── batch_plan.md
├── lab_run_manifest.md
├── runs/
│   ├── round-01-attempt-01/
│   │   ├── task_card.md
│   │   └── report.md
│   └── round-02-attempt-01/
│       ├── task_card.md
│       └── report.md
└── lab_report.md
```

如果少爷指定目录，按少爷指定路径保存。

## 批量流程

1. 生成 `lab_run_id`。
2. 用 `templates/batch_plan.md` 输出批量计划。
3. 除非少爷明确说“直接跑”，否则等待确认。
4. 创建 `lab_run_manifest.md`。
5. 逐轮生成 `task_card.md`。
6. 使用 `user-chance` 执行该任务卡。
7. 单轮结束后写入或收集 `report.md`。
8. 判断单轮是否有效。
9. 更新 `lab_run_manifest.md`。
10. 如果有效样本数不足且未超过最大尝试次数，继续补跑。
11. 达到有效样本数或最大尝试次数后，生成 `lab_report.md`。

## 单轮收口规则

`user-chance-lab` 的目标是批量实验闭环，不是让单轮无限探索。每一轮一旦满足以下条件，应优先收口生成 `report.md`：

| 条件 | 说明 |
|---|---|
| 有候选 | 用户已经打开或比较过至少一个与任务相关的候选 |
| 有关键证据 | 已覆盖影响判断的价格、状态、风险、保障、参数、时效或对比中的主要项 |
| 有用户状态 | 用户已经形成买前继续考虑、暂缓、拒绝、放弃或未形成判断的可解释状态 |
| 有停止证明 | 能说明为什么此刻停止像真实用户，而不是 Agent 偷懒 |

如果证据还不足，可以继续真实操作；但继续操作必须服务于明确未闭合的问题，例如“还不知道低价原因”“还没有看保障范围”“显著对比候选可能改变判断”。不能因为“也许还能再看看”而无边界延长单轮。

单轮收口不等于强结论。证据不足时也可以写成：

- `decision_closure=partial | open`
- `user_decision=defer_ready | not_formed`
- `conclusion_level=directional_signal`

## 证据可见性分级

单轮报告和清单必须区分“工具读到”和“用户看见”。证据分级：

| 类型 | 含义 | 聚合用法 |
|---|---|---|
| `visual_seen` | 截图中可见，且路径上用户自然到达 | 可作为用户已看到的强证据 |
| `xml_visible` | UI XML 可见且 bounds 在屏幕内，但截图不清晰或需辅助读取 | 可辅助截图证据，单独使用时不宜标高 |
| `xml_offscreen` | XML 中存在但不在当前屏幕、不可见或疑似隐藏 | 只能说明页面可能存在该信息，不能写成用户已看到 |
| `inferred` | Agent 根据上下文推断 | 只能作为解释假设，不能作为强结论证据 |
| `tool_noise` | XML 滞后、坐标误点、历史页面残留、模拟器 / MCP 摩擦 | 只能写入样本限制或执行噪声，不得写成产品问题 |

写 `report.md` 或更新 `lab_run_manifest.md` 时，如果关键结论依赖 `xml_offscreen`、`inferred` 或 `tool_noise`，必须标注 caveat，并在聚合时降权。

## 角色最低证据门槛

不同角色可以自由探索，但收口时要检查与角色相关的最低证据是否覆盖。未覆盖时不一定重跑，但要降级为 `partial_valid`、方向信号或在 caveat 中说明。

| 角色 / 任务倾向 | 最低证据门槛 |
|---|---|
| 价格敏感 | 覆盖价格、同类 / 同型号对比、低价原因或价格行情中的至少两类 |
| 风险敏感 | 覆盖成色 / 功能状态、验机 / 质检、售后保障、关键风险标签中的主要项 |
| 急用 / 时效敏感 | 覆盖配送时效、到手时间或履约限制 |
| 理性比较 | 至少比较两个相关候选，或说明为什么无法形成候选池 |
| 平台新手 / 品类小白 | 记录哪些标签、术语、入口或规则造成理解负担 |
| 指定路径测试 | 覆盖指定路径的核心节点；偏离路径时说明偏离是否符合用户动机 |

最低证据门槛不是硬性操作步骤。它只用于收口判断：如果用户真实没有看到这些证据，本身可能就是体验问题；如果 Agent 只是没去取证，则需要补充操作或降权。

## 静默超时规则

主线程协调 subagent 时，不要让执行者长时间静默。

默认建议：

| 情况 | 主线程处理 |
|---|---|
| subagent 5 分钟无结果 | 继续等待一次，除非任务很轻 |
| 连续 10 分钟无结果 | 要求短状态回报：是否仍在真实操作、完成到第几轮、是否产出报告、是否卡住 |
| 已有足够证据但未写报告 | 要求停止继续操作 App，先基于现有证据收口 |
| 状态回报含糊或反复不收口 | 关闭该 subagent，另派执行者接手证据收口 |

短状态回报只需要回答进度和卡点，不要写长篇复盘。

## 接手规则

如果前一个执行者已经真实操作 App 并留下截图、XML、任务卡或部分清单，但没有生成报告，新的执行者可以接手。

如果任务里已经明确“接手”“收口”“读取现有目录”“不要继续操作 App”，执行者不要再输出计划或请求确认；应直接开始读取证据并收口。只有遇到证据缺失、目录不存在、边界风险或必须真实补跑时才向少爷说明。

接手顺序：

1. 读取 `batch_plan.md`、`lab_run_manifest.md`、相关 `task_card.md`。
2. 检查该轮证据是否真实、连续、能支撑用户状态。
3. 若证据足够，基于既有真实证据生成 `report.md`，并在报告中说明是“基于既有真实证据补写”。
4. 若证据不足，说明缺口，再按补跑规则继续真实操作 App。
5. 更新 `lab_run_manifest.md`，再判断是否生成 `lab_report.md`。

接手不是用想象补报告。只有存在真实 App 证据时，才能基于既有证据收口。

## 有效样本判断

样本有效性分为 `valid`、`partial_valid`、`invalid` 三档，不要把“有一些真实证据”直接写成完整有效样本。

| 档位 | 条件 | 聚合处理 |
|---|---|---|
| `valid` | 真实执行；模式有效；起点可接受；工具未阻断；关键证据足以支撑用户状态；报告可聚合；关键结论的证据可见性已标注 | 可作为完整有效样本纳入，但具体结论仍可有 caveat |
| `partial_valid` | 真实执行且有方向性证据，但覆盖不完整，例如只到入口 / 列表、未进详情、未看关键报告、未形成充分对比，或关键结论主要依赖屏外 XML / 推断 | 只能作为方向信号；不能和 `valid` 同权重 |
| `invalid` | 工具阻断、样本污染、模式错配、证据不足或报告无法支撑用户状态 | 不纳入产品体验结论，按规则补跑 |

目标有效样本数默认统计 `valid`。如果因时间、边界或少爷明确要求，把 `partial_valid` 也纳入迷你复测，必须在 `lab_run_manifest.md` 和 `lab_report.md` 明确降权，并说明没有补跑的原因。

最低有效条件：

| 条件 | 要求 |
|---|---|
| 真实执行 | 有真实 App 操作和证据，不是纯推理 |
| 模式有效 | 自由目标型或指定路径型执行方式与计划一致 |
| 起点可接受 | 起点清洁或已校正；污染影响已说明并可降级 |
| 工具未阻断 | 工具问题未改变核心路径或结论 |
| 报告可聚合 | 至少有样本有效性、用户状态、体验问题、机会点、证据索引 |
| 证据可见性清楚 | 关键结论区分截图可见、XML 辅助、屏外 / 推断和工具噪声 |

## 补跑规则

默认：

```text
目标有效样本数 = 5
最大尝试次数 = 8
```

少爷可以调整。

补跑类型：

| 类型 | 是否补跑 | 说明 |
|---|---|---|
| `tool_failure` | 是 | ADB / MCP / 模拟器 / App 启动失败或严重影响路径 |
| `invalid_start_state` | 是 | 起点污染严重且无法校正 |
| `mode_invalid` | 是 | 指定路径跑成自由探索，或自由目标被错误约束 |
| `report_contract_failure` | 先重写，必要时补跑 | 证据完整则重写报告；证据不足则补跑 |
| `natural_failure` | 否 | 用户真实找不到、看不懂、犹豫或放弃 |
| `boundary_stop_with_evidence` | 视情况 | 已有有效体验证据可纳入，必须说明边界影响 |

补跑时优先保持原样本意图。如果同一角色连续因工具失败无法完成，可以生成同类替补角色，但必须在清单中说明替换原因。

## 轻量清单

`lab_run_manifest.md` 是实验目录页，不是数据库。

它只记录：

- 本次实验目标
- 计划有效样本数和最大尝试次数
- 每轮任务卡路径
- 每轮报告路径
- 单轮结果
- 是否纳入汇总
- 剔除或补跑原因
- 关键证据 caveat

不要在清单里记录每一步点击。点击、截图、UI 树、录屏和动作证据属于单轮 `user-chance` 报告和证据目录。

建议为每轮补充一段“证据可见性 / Caveat 记录”，说明哪些结论可完整纳入，哪些只能方向支持。这样后续聚合不需要重新猜证据强弱。

## 中断与继续

第一版不承诺后台无人值守。若 Codex 对话中断，可以用 `lab_run_manifest.md` 人工或半自动恢复，但这不是核心能力。

恢复时只需要读取：

1. `batch_plan.md`
2. `lab_run_manifest.md`
3. 已完成轮次的 `report.md`

然后继续补足有效样本或直接聚合。

## subagent 使用

第一版不让多个 subagent 同时控制同一设备。

可用场景：

- 单轮报告外审
- 聚合报告复核
- 竞品对比报告交叉检查

如果少爷要求 Claude CLI 或其他外部审核，可以在单轮全部完成后调用，不参与 App 操作。

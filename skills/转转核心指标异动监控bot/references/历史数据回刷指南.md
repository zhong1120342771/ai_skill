# 历史数据回刷指南

底表 `hdp_zhuanzhuan_tmp_global.tmp_dws_zz_core_dataagent_zmt_v2_di` 的历史日期回刷操作手册。当需要补某段历史日期的数据（表里缺 dt 分区，或需重刷某区间）时按本文操作。

## 一句话用法

```bash
cd ~/.claude/skills/转转核心指标异动监控bot/scripts
python3 run_backfill.py --start <起始日> --end <结束日> --parallel 4
```

给一个日期区间，脚本自动查这段里**缺哪些 dt**，只补缺失日期（已有分区跳过，不覆写）。默认走**单天模式**：一个缺失日一个单天 job，只写它自己那一个分区，各 job 天然不重叠、可自由并发。区间闭合，含两端。

## 两种回刷模式（`--mode`）

| 模式 | 单批读取 | 单批写出 | 何时用 |
|------|---------|---------|--------|
| `single`（默认，推荐） | 只扫 `dt=该天` 单分区 | 只写 `dt=该天` **1 个**分区 | 补最近缺失日、补孤立缺口——绝大多数场景 |
| `window` | 扫 `[右端-30,右端]` 31 分区 | 覆写这 **31 个**分区 | 仅当要用后续更新的快照**修正较早历史的退款口径**时 |

> **为什么默认单天**：曝光/商详/下单是事件流，输出分区 dt = 事件日，只读单天即可完全准确；净支付按 `dt=该天`（当天快照）+ `to_date(pay_time)=该天` 归集，与滚动版在 `outFileSuffix=该天` 那一批对该天的读数一致。所以补一个缺失日只需读写这一天，`window` 模式那种"补 1 天顺带重刷 30 天"纯属浪费。单天版放弃的只是"后续批用更新快照反复修正历史退款"，对日更补漏无影响。

## 涉及文件（都在 `scripts/`）

| 文件 | 作用 |
|------|------|
| `run_backfill.py` | 回刷批量提交器：查缺口 →（单天/滚动）切批 → 并发提交星河 → 逐批校验分区非空 |
| `backfill_single_day.sql` | **单天回刷模板**（默认用），占位符 `${targetDay}`（要补的那天）、`${infoSnapshotDt}`（商品维度快照 dt）。所有事件窗口塌缩成 `dt between targetDay AND targetDay` |
| `backfill_history.sql` | 31 天滚动回刷模板（`--mode window` 用），占位符 `${outFileSuffix}`（窗口右端）、`${infoSnapshotDt}` |

## 工作原理

- **只补缺口（默认）**：先查区间内已有 dt，`missing_ranges` 找出缺失日期。单天模式把每个缺失日展开成独立单天批；滚动模式把缺失日聚合成连续段各自切 31 天窗口。两种模式都**绝不覆写已有好数据**（单天只写缺失日本身；滚动窗口左端夹在缺口内）。
- **单天批天然并发安全**：每个单天 job 只写各自 1 个分区，互不重叠，`--parallel` 直接并发拉满即可。滚动模式因末批裁剪可能产生重叠批，由 `run_pool` 的 overlap 守卫自动串行化，不会两个 job 抢写同一 dt。
- **引擎**：`SQL_ENGINE=2`（SparkSQL）。单天批很轻，Spark 秒级到分钟级；滚动批 31 天全量重算**必须用 Spark 不能用 Hive**——会撞 Hive 6 小时执行上限被 kill。
- **商品维度快照**：`info` 全量快照表只留最近约 3 周，历史日期取不到当时快照，统一钉到运行日 t-1 这份最新映射（品类映射相对稳定）。两种模板共用 `${infoSnapshotDt}`。
- **逐批校验**：每批 SUCCESS 后自动 `count(1)` 校验目标分区行数，为 0 记为空分区异常（通常是 info join 未命中）。正常量级约 3000+ 行/天。

## 参数

| 参数 | 默认 | 说明 |
|------|------|------|
| `--start` / `--end` | 必填 | 回刷区间闭区间端点（YYYY-MM-DD），是「区间」不是「窗口右端」 |
| `--parallel` | 4 | 并发在跑 job 数上限 |
| `--max-wait` | 7200 | 单 job 本地等待上限秒。超时只放弃本地跟踪，**不 kill 远程 job**（可能还在跑） |
| `--mode` | single | `single`=逐个缺失日单天回刷（只写各自1分区，最省）；`window`=31天滚动窗口 |
| `--dry-run` | 关 | 只查缺口+打印批次计划，不提交 |
| `--smoke` | 关 | 只跑第一批并校验非空（首次验证模板可用性时用） |
| `--force-all` | 关 | 关闭缺口探测，强制重刷整个区间（single=逐天覆写，window=滚动覆写，慎用） |

## 标准操作流程

1. **先 dry-run 看缺口和批次计划**：
   ```bash
   python3 run_backfill.py --start 2026-06-01 --end 2026-07-13 --dry-run
   ```
   确认缺哪几天符合预期。区间内无缺口会直接提示"无需回刷"。单天模式会逐个列出"写分区 dt=某天"。

2. **正式跑**（后台）：
   ```bash
   nohup python3 run_backfill.py --start 2026-06-01 --end 2026-07-13 --parallel 4 --max-wait 7200 > /tmp/backfill.log 2>&1 &
   tail -f /tmp/backfill.log
   ```

3. **完成后校验缺口归零**：重新 dry-run 同一区间，应显示"缺 0 天，无需回刷"。

## 性能与注意事项

- **单天批很轻**：单天模式一批只扫写一天，SparkSQL 下通常几分钟内完成，补最近几天缺口很快。滚动模式（`--mode window`）31 天一批约 80–150 分钟（实测最慢约 2.4 小时），务必后台跑。
- **`--max-wait` 超时 ≠ 失败**：脚本只放弃本地跟踪，星河 job 仍在跑。可用 `xinghe_client.get_progress([execute_id])` 单独查真实状态，或稍后重新 dry-run 看缺口是否已补。
- **并发放心用**：单天批只写各自 1 分区，永不冲突，`--parallel` 可拉满。若要回刷多个不连续大段，也可拆成多个 `--start/--end` 命令各自后台并行。
- **凭证**：只走环境变量 `XINGHE_CLIENT_USER/SECRET/OA`，脚本不硬编码。

## SQL 模板改动（改口径时）

**默认改单天模板 `backfill_single_day.sql`**，保留两个占位符不动：
- `${targetDay}`：要回刷的那天，脚本逐日替换。所有事件表窗口都是 `dt between targetDay AND targetDay`，净支付块 `aa.dt=targetDay and to_date(pay_time)=targetDay`。
- `${infoSnapshotDt}`：商品维度快照分区 dt，脚本自动填 t-1（**info CTE 独立于 targetDay，改口径时别把它也改成 targetDay**）。

滚动模板 `backfill_history.sql` 用 `${outFileSuffix}`（窗口右端），单批区间 `[date_sub(outFileSuffix,30), outFileSuffix]`。**两份模板口径要同步改**，否则单天/滚动结果会不一致。单天版是从滚动版做文本替换生成的（`date_sub('${outFileSuffix}',30)` → `'${targetDay}'`，其余 `${outFileSuffix}` → `${targetDay}`），改口径后可照此重新生成保证一致。

两份模板末尾 `insert overwrite table ... PARTITION(dt)` 与 select 末列的 `dt` 都不能删，动态分区靠它写入。

# 字段映射与指标口径

> 数据源：`hdp_zhuanzhuan_tmp_global.tmp_dws_zz_core_dataagent_zmt_v2_di`（转转全局数据_分维度聚合，分区 `dt`，格式 `yyyy-MM-dd`）
> 飞书口径真源：https://zhuanspirit.feishu.cn/wiki/EwQVwmVsvigG0pkU023ci4mBnOc
> 这是一张**已预聚合**的底表：每一行 = 某个维度组合（`tag_01` + `wd`）在某天的漏斗指标 + 该维度匹配到的 DAU 分母。不需要再 join 明细，直接按 `tag_01` 筛维度族、按 `wd` 取具体维度值即可。

## 一、原子字段清单（与建表 DDL 一一对应）

| 字段 | 类型 | 中文 | 含义 |
|---|---|---|---|
| `tag_01` | string | 口径 | 维度组合的"族"，决定这一行是几维交叉、按什么拆。见 [维度体系与样例数据.md](维度体系与样例数据.md) |
| `wd` | string | 维度 | 具体维度值组合，用 `_` 拼接，如 `转转APP_品类消费电子手机_新媒体召回` |
| `exp_pv` | int | 曝光pv | 商品曝光次数（sum） |
| `exp_uv` | int | 曝光uv | 曝光去重人数（count distinct token） |
| `detail_pv` | int | 商详pv | 商详页访问次数 |
| `detail_uv` | int | 商详uv | 商详去重人数 |
| `order_pv` | int | 下单pv | 下单订单数（count distinct order_id） |
| `order_uv` | int | 下单uv | 下单去重人数 |
| `pay_pv` | int | 净支付pv | 当日下单且当日无退款的订单量（count distinct 净支付 order_id，剔除换货）＝**业务口径「单量」** |
| `matched_dau_uv` | int | 活跃uv | 该维度组合**匹配到的 DAU 分母**，见下方「口径核心」。可能为 NULL，见「口径陷阱」 |
| `matched_duan` | string | 端归属 | 该行 DAU 分母匹配到的端（`ALL`=未按端细分），NULL=分母降级失败被置空 |
| `matched_source` | string | 用户来源归属 | 同上，用户来源维度 |
| `matched_type` | string | 用户资产分层归属 | 同上，资产分层维度 |
| `dt` | string | 日期 | 分区字段 `yyyy-MM-dd` |

漏斗链路：**曝光 → 商详 → 下单 → 净支付**。下单（order）与净支付（pay）是两个口径，净支付更严格（剔除换货、限当日净支付）。

## 一·补：「新用户/新增」量级怎么从本表取

本表没有独立的「新用户数」字段，但**新用户口径落在两个已有维度上**，取对应行的 `matched_dau_uv`（该维度匹配到的活跃 UV）即为量级：

| 新用户口径 | 落在哪个 `tag_01` | 取哪几行 `wd` | 量级 = |
|---|---|---|---|
| **来源口径（首次访问）** | `单维度-拆分用户来源` | `自然新增` + `新媒体新增` 两行 | 两行 `matched_dau_uv` 相加 |
| **资产口径（无交易新客）** | `单维度-拆分用户资产分层` | `z0` 一行 | 该行 `matched_dau_uv` |

> 业务定义：**新用户 = 自然新增用户 + 新媒体新增用户 = z0 用户（无交易）**。两个口径视角不同——来源口径按「本次访问是不是首次进站」拆（`自然新增`/`新媒体新增`），资产口径按「历史有没有交易」拆（`z0`=无交易）。日常问「新用户量级」两者都可答，需注明用的是哪个口径；若用户未指定，默认用**资产分层 z0**（无交易新客，业务最常用），并在结论里点明口径。
>
> 想看某端的新用户（如「APP 新用户」），用交叉族 `2维度交叉-端_用户来源`（`wd LIKE '转转APP%新增'`）或 `3维度交叉-端_业务/品类_资产分层`（`wd LIKE '转转APP%z0'`）。
>
> ⚠️ 本表口径边界：只有漏斗（曝光/商详/下单/净支付 pv·uv）+ 匹配 DAU + 各环节转化率，按人/场/货/端拆。**没有** GMV / 客单价 / 退款 / 停留时长 / 次日留存等字段——问到这些直说「本底表不含该指标」，不臆造、不擅自串其他表。

## 二、口径核心：`matched_dau_uv` 是「分维度匹配」的 DAU，不是全局常数

⚠️ **这是本表与旧表 `tmp_dws_all_app_zhibiao_zmt_v2_di` 最关键的区别，务必记牢。**

旧表的 `uv_all` 是「全局当日 DAU」，同一天所有行都是同一个常数，导致 `pay_pv/uv_all` 这类比率跨维度不可比、只能表"贡献占比"。

**新表的 `matched_dau_uv` 是按维度降级匹配的 DAU 分母**：建表逻辑把 DAU 按（端×来源×资产分层）8 种组合预聚合成 `dau_cube`，再对每条 `wd` 匹配到最细可用的分母格。例如：
- `单维度-拆分端` 的 `转转APP` 行 → `matched_dau_uv` = 转转APP 端的 DAU；
- `单维度-拆分用户来源` 的 `新媒体召回` 行 → `matched_dau_uv` = 新媒体召回来源的 DAU；
- `整体` 行 → `matched_dau_uv` = 全站 DAU。

后果（与旧表相反）：

> **`净支付pv / matched_dau_uv`（dau-净支付pv转化率）现在是「该维度用户的真实转化率」，可以跨维度比大小。** 这是产品侧的**北极星指标**。

## 三、计算字段口径（漏斗链路，飞书口径真源）

除原子字段外的派生指标，分子分母都在同一行/同一维度，**跨维度可比**：

| 计算字段 | 计算口径 | 补充说明 |
|---|---|---|
| 曝光渗透率 | `exp_uv / matched_dau_uv` | 活跃用户里有多少被曝光 |
| 商详到达率 | `detail_uv / exp_uv` | 曝光的人里有多少点进商详 |
| 下单率 | `order_uv / detail_uv` | 商详的人里有多少下单 |
| 支付率 | `pay_pv / order_uv` | 下单后真正付钱的比例（净支付pv=当日下单且当日无退款） |
| 商详渗透率 | `detail_uv / matched_dau_uv` | ＝曝光渗透率 × 商详到达率 |
| 商详转化率 | `pay_pv / detail_uv` | ＝下单率 × 支付率 |
| 提袋率 | `pay_pv / exp_uv` | ＝商详到达率 × 商详转化率 ＝ 商详到达率×下单率×支付率 |
| **dau-净支付pv转化率** | `pay_pv / matched_dau_uv` | **北极星指标**。＝商详渗透率×商详转化率＝曝光渗透率×商详到达率×下单率×支付率＝曝光渗透率×提袋率。**对外呈现统一百分比三位小数 `X.XXX%`（全局强制规则）**，读 tidy 的 `dau_pay_rate_pct` 列（已按 3 位产出）。 |

链式分解（异动归因用这条链逐环节拆）：

```
dau-净支付pv转化率
  = 曝光渗透率 × 商详到达率 × 下单率 × 支付率
    (exp_uv/dau) (detail_uv/exp_uv)(order_uv/detail_uv)(pay_pv/order_uv)
```

北极星波动时，沿这 4 个环节逐一对比同环比，定位是哪个环节在拉动。

## 四、结构类字段（占比，流量/支付分布）

| 计算字段 | 计算口径 | 用途 |
|---|---|---|
| 曝光pv占比 | 特定维度 `exp_pv` / sum(父维度总 `exp_pv`) | 流量分布，看某维度占多少曝光盘子 |
| 支付pv占比 | 特定维度 `pay_pv` / sum(父维度 `pay_pv`) | 支付分布，看某维度贡献多少单量 |

> 占比看的是"盘子大小/贡献结构"，转化率看的是"效率"。异动归因时两者结合：某维度北极星跌了，先看它占多大盘子（够不够拉动大盘），再看跌在哪个漏斗环节。

## 五、口径陷阱：`matched_dau_uv` 为 NULL 的行不能算 DAU 转化率

建表逻辑有个**完整性闸门**：只有当匹配到的 DAU 分母格覆盖了 `wd` 里实际含有的**全部**用户属性（`n_specific = required`）才保留分母；若精确格缺失、被迫跨维度回退（`n_specific < required`），则 `matched_dau_uv` 及 `matched_duan/source/type` 全部置 **NULL**。

后果与处理：
- **NULL 行不能计算任何以 `matched_dau_uv` 为分母的指标**（曝光渗透率、商详渗透率、dau转化率）。遇到 NULL 一律按"该维度 DAU 分母不可用"处理，跳过 DAU 类指标；但漏斗内部比率（商详到达率/下单率/支付率/提袋率，分母都不是 DAU）仍可算。
- 实测每天约 6~8 行 NULL（占 ~3300 行的极小比例），主要出现在高维交叉里精确 DAU 格缺失的组合。质检脚本统计 NULL 率，异常升高（如 > 2%）才告警。
- **绝不把 NULL 当 0**，否则转化率会算出无穷大或异常值。

## 六、空值与脏值

- `matched_dau_uv` 为 NULL：见上，按分母不可用处理。
- 维度值组合里可能出现 `XX-其他`（如 `奢侈品-其他`、`兴趣N-其他`、`消费电子N-其他`、`其他`），是兜底类目，分析时单列或归并，不当成具体品类/场景。
- 比率在分母为 0 时按缺失处理，不当成"率=0"。小分母（`exp_uv` 很小）下比率剧烈抖动，异动定位默认剔除 `exp_uv < 1000` 的行。
